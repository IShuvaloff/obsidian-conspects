Дата: 2026-04-03

Проект: partners-admin (October CMS)


Контекст: доработка конструктора блоков для коммерческих страниц (SEO), добавление и стабилизация нового блока со списком вложенных элементов.

  

---

  

## 1) Что это за система в проекте

  

В проекте есть единая сущность страниц на базе модели Page, которая используется для нескольких типов контента:

  

- blog: блоговые страницы

- seo: коммерческие страницы

- offer: страницы спецпредложений

  

Системно это одна таблица posts.pages с полем type, которое определяет сценарий использования страницы.

  

В админке это один backend-контроллер Pages, который:

  

- показывает разные списки (blog, seo, offers)

- открывает одну и ту же форму редактирования страницы

- подмешивает поведение на уровне формы

  

Ключевой момент: контент конструктора блоков хранится не в отдельных таблицах по блокам, а в JSON-поле content (колонка posts.pages.content).

  

То есть YAML-файлы описывают только форму (какие блоки доступны и какие поля у блока), а сами данные лежат в JSON.

  

---

  

## 2) Как устроен конструктор блоков в October здесь

  

Базовый form-конфиг страницы содержит поле content типа repeater с displayMode: builder.

Это значит:

  

- редактор в админке видит список добавленных блоков

- кнопка Добавить открывает список доступных типов блоков

- список типов блоков берется из groups YAML-файла

  

В проекте базовый путь groups для Page задан как:

  

$/platform/posts/models/page/builder_blocks.yaml

  

Дальше уже runtime-логика контроллера подменяет этот файл для SEO-страниц на отдельный:

  

$/platform/posts/models/page/builder_blocks_seo.yaml

  

Именно это позволяет добавить новый блок только для коммерческих страниц, не трогая блог и offer.

  

---

  

## 3) Финальная цель доработки и что в итоге реализовано

  

Цель:

  

- добавить блок только для SEO-страниц

- блок должен содержать список вложенных элементов

- в каждом вложенном элементе: title, text, cover, preview

- title и text обязательные

- cover не обязательный (и не должен визуально светиться как required)

- API должен отдавать нормализованные поля title, text, cover, preview

  

Реализация достигнута:

  

- SEO использует отдельный builder-конфиг

- новый блок называется Список вложенных элементов

- внутри блока есть repeater items

- в элементе обязательны title и text

- для медиа в форме используются технические ключи media_cover и media_preview

- на API-выходе эти ключи нормализуются в cover и preview

## 4) Перечень итоговых изменений по файлам

  

### 4.1 Pages controller (backend)

  

Файл: plugins/platform/posts/controllers/Pages.php

  

Добавлен formExtendFields.

  

Назначение:

  

- на этапе сборки backend-формы определяет фактический тип страницы (из модели, POST, query)

- для type=seo подменяет groups на builder_blocks_seo.yaml

- для остальных оставляет builder_blocks.yaml

  

Зачем:

  

- отдельный набор блоков только для SEO

- без дублирования отдельных контроллеров/форм

  

Это изменение ключевое и нужное: без него SEO-блок не будет ограничен только SEO-страницами.

  

### 4.2 SEO builder groups

  

Файл: plugins/platform/posts/models/page/builder_blocks_seo.yaml

  

Сделан SEO-специфичный файл групп (отдельный от общего).

Добавлен блок:

  

- ключ группы: unfolding

- название: Список вложенных элементов

- структура: items (repeater)

- поля item:

  - title (required)

  - text (required, rich editor)

  - media_cover (optional)

  - media_preview (optional)

  

Зачем media_* вместо cover/preview:

  

- избежать конфликта с модельным правилом Page.cover required

- убрать ложный визуальный required-индикатор у поля Обложка внутри элемента

  

### 4.3 Page model validation and normalization

  

Файл: plugins/platform/posts/models/Page.php

  

В beforeSave оставлена и расширена логика:

  

- генерация slug для блоков конструктора, если пустой

- валидация блока unfolding:

  - title обязателен

  - text обязателен (с проверкой пустого rich text через strip_tags + trim)

  - при нарушении бросается ValidationException

  

Также добавлена мягкая совместимость ключей медиа в items:

  

- если есть cover и нет media_cover, копируется в media_cover

- если есть preview и нет media_preview, копируется в media_preview

  

Важно:

  

- логика не удаляет массив items

- не удаляет данные соседних элементов

- не делает destructive-перезаписи

  

Это сделано именно чтобы избежать ситуации, когда при сохранении второго элемента очищались данные первого.

  

### 4.4 Commercial API normalization

  

Файл: plugins/platform/api/http/controllers/CommercialPageController.php

  

Добавлена обработка группы unfolding в processSeoEntry:

  

- для каждого item читается media_cover, fallback на cover

- для каждого item читается media_preview, fallback на preview

- в API-результат пишутся cover и preview как готовые URL через processMediaImage

- временные media_cover/media_preview удаляются из ответа

  

Итог для фронта:

  

- контракт удобный и стабильный: title, text, cover, preview

- внутренняя структура формы и хранения остается гибкой

## 5) Как это связано с блогом и статическими страницами

  

### Blog

  

Blog API использует ту же модель Page, но выбирает type=blog.

Обработка блоков в BlogController похожа на CommercialPageController, но отдельная.

  

Вывод:

  

- изменения unfolding сейчас применены в коммерческом API-контроллере

- блог не затронут, пока не добавлять unfolding в общий builder и не расширять BlogController

  

### Static pages

  

StaticPage хранит свой content тоже как JSON (jsonable), но backend-форма статических страниц сейчас смотрит на общий builder_blocks.yaml.

  

Вывод:

  

- текущая доработка не меняет static-поток

- при желании переноса блока в static нужно:

  1) добавить группу в используемый static groups YAML

  2) расширить StaticPageController API-обработку для unfolding

## 6) Почему возникла проблема с красной required-точкой у cover

  

Причина неочевидная, но типичная для October backend-форм:

  

- у модели Page есть глобальное правило валидации cover required

- внутри repeater item тоже использовался ключ cover

- из-за совпадения имени backend UI помечал поле как required визуально

  

Это была не обязательность конкретно item-поля по бизнес-логике, а побочный эффект пересечения имен.

  

Решение:

  

- в форме item-поле переименовано в media_cover

- аналогично preview -> media_preview

- API после обработки возвращает привычные cover/preview

  

Таким образом одновременно достигнуто:

  

- визуально поле не выглядит обязательным

- фронт получает ожидаемые имена полей

## 7) Где сохраняются данные и где только рендерятся

  

Сохранение (backend):

  

- через стандартный onSave поведения FormController

- модель Page принимает данные формы

- beforeSave в модели валидирует и нормализует content

- запись уходит в posts.pages.content (JSON)

  

Преобразование для фронта (read path):

  

- CommercialPageController читает Page.content

- по _group выполняет пост-обработку медиа

- возвращает JSON по маршруту api/v4/commercial/{segments}

  

Важно: API-контроллер не сохраняет контент блока, он только читает и преобразует.

## 8) Глобальное влияние изменений

  

Положительное влияние:

  

- SEO-конструктор теперь может развиваться отдельно от blog/offer

- добавлен новый сложный блок без изменения схемы БД

- введена серверная валидация обязательных полей в JSON-блоке

- убран ложный required-маркер у необязательного поля медиа

  

Потенциальные риски:

  

1. Избыточная логика в beforeSave

   - при росте числа сложных блоков проверка может стать тяжелой

   - лучше вынести в отдельный сервис-валидатор блоков

  

2. Разделение логики API по контроллерам

   - BlogController, CommercialPageController, StaticPageController содержат похожие ветки по _group

   - при масштабировании лучше сделать общий normalizer/mapper

  

3. Совместимость ключей

   - сейчас есть fallback media_* и legacy cover/preview

   - это хорошо для миграции, но со временем стоит зафиксировать единый внутренний формат

## 9) Рекомендации по масштабированию

  

### 9.1 Для новых блоков

  

- описывать UI в отдельном YAML-групп файле для нужного типа страниц

- в модели вводить серверную валидацию только для реально обязательных полей

- в API-контроллере добавлять _group-нормализацию в одном стиле

  

### 9.2 Для уменьшения дублирования

  

- вынести обработку content blocks в отдельный класс, например ContentBlockNormalizer

- вызывать его из BlogController, CommercialPageController, StaticPageController

- держать единые правила преобразования медиа

  

### 9.3 Для безопасных миграций ключей

  

- временно поддерживать два формата (старый и новый)

- возвращать наружу только каноничный API-контракт

- постепенно добавить миграцию данных и убрать fallback

## 12) Краткий итог

  

Система доработана так, чтобы:

  

- новый блок работал только в SEO-конструкторе

- обязательность полей была корректной (title/text yes, cover no)

- API отдавал удобный контракт для фронта

- данные разных вложенных элементов не затирались при повторных сохранениях

  

Главная инженерная идея: разделить внутреннее имя form-полей и внешний API-контракт.

Именно это позволило убрать ложный required-индикатор и при этом сохранить красивый выходной формат cover/preview.

# При расширении использования блока
> Если я захочу, чтобы у меня во всех типах постов (seo, blog, commercial) был одинаковый набор доступных к добавлению блоков конструктора, мне нужно будет просто убрать функцию `formExtendFields` из Pages.php? если не так, поясни, в чем я ошибся, а если прав, дополни нужной на твой взгляд информацией.

Почти верно, но есть нюанс.

Если убрать `formExtendFields`, все типы будут использовать путь, который прописан в `fields.yaml` напрямую — это `builder_blocks.yaml`. Блок `unfolding` ("Список вложенных элементов") в этом файле **отсутствует**, он только в `builder_blocks_seo.yaml`.

Итого при удалении функции:

- blog и offer — без изменений, их набор блоков останется прежним
- seo — **потеряет** блок `unfolding` из попапа

Поэтому правильная последовательность, если хочешь одинаковый набор везде:

1. Скопировать блок `unfolding` из `builder_blocks_seo.yaml` в `builder_blocks.yaml`
2. Убрать `formExtendFields` из `Pages.php`
3. Файл `builder_blocks_seo.yaml` после этого можно удалить — он больше не нужен

И отдельный вопрос, который нужно решить параллельно: сейчас API-обработка блока `unfolding` есть только в `CommercialPageController.php`. Если блок появится у blog-страниц, нужно добавить аналогичный кейс и в API-контроллер блога — иначе `media_cover`/`media_preview` будут приходить во фронтенд сырыми путями без конвертации в URL.
