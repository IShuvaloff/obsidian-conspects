==Особенности==:
1. схема строго однонаправленная: pages -> modules -> components -> UI;
2. содержит простейшие визуальные элементы кода - **UI**^[кнопки, инпуты, селекты и т.д.]. Запрещено добавлять в эти компоненты бизнес-логику;
3. компоненты в общем списке блоков - **components** - это несамостоятельные блоки кода^[карточка товара, карточка пользователя, комментарий, таблица и т.д.], которые можно использовать в разных частях программы. Используют внутри себя UI-элементы;
4. смысловые модули **modules** со своей бизнес-логикой, задачей и ответственностью, включая свои папки *components*/*routes*/*store*/*helpers*/*api* и т.д., связанные между собой^[список пользователей, список комментариев к определенной статье, форма для регистрации, дерево регионов для выбора, форма для отзывов и т.д.]. Используют внутри себя компоненты, составляют главную смысловую единицу проекта:
   
   ![[Pasted image 20231025120150.png|300]]
	* важно, чтобы компоненты внутри модуля решали какую-то одну конкретную задачу под модуль!
	* если *компонент внутри модуля* решает схожую задачу с общим компонентом из проекта, то тем не менее в модуле *он должен быть независим* и заточен именно под проблему модуля;
4. страницы **pages**, использующие модули для формирования полноценного сайта. Сама по себе страница - это тоже модуль, схема которого схожа со схемой модуля из п. 3, т.е. со своими глобальными *api*/*components*/*store* и т.д.^[профиль пользователя, страница администратора, страница настроек и т.д.]:
   
   ![[Pasted image 20231025122052.png|250]]] ![[Pasted image 20231025122248.png|300]]]
	* в блоке components должны содержаться отдельные модули, спроектированные по правилам п. 3!
	* как итог, html-страница должна оставаться максимально "тонкой" с точки зрения своего содержимого - только модули и компоненты.

==Важные требования==:
1. требуется как-то изолировать содержимое модуля от внешних модулей. Для этого в корне модуля создается файл `index.ts(js)` c Public API, в котором делаются доступными только определенные части кода:
	```js
	   export { <modulePublicFunctionOrObject> } from './<moduleRequiredFile>';
	```

==Преимущества и недостатки:==

- [+] поддерживается **инкапсуляция** - аналог таковой в ООП, - когда лишний код не засоряет глобальную область видимости;
- [+] в силу однонаправленности использования данных удается избежать кольцевых зависимостей;
- [+] легко редактировать страницы, просто добавляя/удаляя отдельные модули;
- [ ] возможно дублирование кода в разных модулях;
- [ ] не всегда понятно, как разделять код на модули и компоненты;
- [ ] как следствие, сложно в случаях, если требуется использовать использовать один модуль в другом;
- [ ] сложно разделять компоненты с бизнес-логикой и технические данные;
- [ ] из-за наличия глобальных функций на страницах могут все равно формироваться взаимные зависимости, если модули эти функции используют.

==Когда лучше использовать==:
1. в 99% случаев лучше, чем классический подход;
2. более крупная команда разработки от 4 человек и выше;
3. не очень широкая и разнообразная бизнес-логика.
