#merge #rebase

Варианты слияния:
1. **`git merge`** - последовательное вливание ветки-источника в целевую ветку в ==хронологическом== порядке с созданием в целевой ветке нового мердж-коммита с полными результатами изменений:
	- `git checkout target-branch` - переключиться на ветку, в которую будем вливать данные;
	- `git merge source-branch` - втянуть данные из ветки-источника;
	- `git merge --abort` - отменить процесс слияния и откатить все коммиты в текущей ветке;
2. **`git rebase`** - вливание всех коммитов из ветки-источника поверх коммитов в целевой ветке без создания лишней мердж-ветки. Это позволяет в целевой ветке впоследствии видеть все коммиты из всех веток-источников и отслеживать изменения пошагово. Главные 3 правила выполнения **rebase**:
	1. ~~Запретите себе `git push --force` навсегда~~! Использовать только ==`git push --force-with-lease`== (позволит проверить, если ли на сервере новые коммиты, которые ты не выкачал, иначе в противном случае ты бы их просто затер без предупреждения);
	2. Запомните команду спасения: ==`git rebase --abort`== (консоль начала сыпать конфликтами, ты запутался, можешь откатить все назад до исходного состояния, очистив конфликты);
	3. Используйте интерактивный режим ==**только локально**== (склеивать коммиты, только если они не были до этого отправлены на сервер!) - например, склейка трех последних коммитов через `git rebase -i HEAD~3`. 

	Если сложить эти два трюка вместе, ваш рабочий процесс в консоли сокращается всего до трех понятных шагов:
	- `git reset --soft HEAD~3` + `git commit -m "сообщение"` (склеили код 3 последних лок. коммитов)
	- `git pull --rebase origin main` (подтянули чужие изменения с *main* и накатили свои поверх)
	- `git push origin my-branch --force-with-lease` (отправили на сервер, там, если ветка была запушена до этого, произойдет проверка и перезапись хэшей коммитов и запись пройдет успешно)

4. **`git pull [origin remote-branch]`** - "вливание" ветки-источника, расположенного в удаленном репозитории, в целевую локальную ветку (аналогично `git merge`). Если используется просто `git pull`, идет подтягивание изменений в одноименной удаленной ветке.

## Ошибки слияния (merge conflicts)
#conflict

Если при форсированной заливке данных в предыдущий коммит (например, при использовании `git commit --amend --no-edit` и последующем `git push --force`) мы исправили уже залитый ранее файл, то при создании запроса на слияние (merge request) возникнет конфликт, т.к. система не может понять, какое из изменений в данном коммите является превалирующим:

![[Pasted image 20240405114219.png]]

В этом случае мы имеем:
* строку **HEAD** - это ==новые изменения==, которые мы закидываем в merge request. Она показывает, какая строчка теперь расположена в коде над выполненным изменением (в нашем случае была удалена строка, поэтому *отображается та строка, что располагалась над удаленной*, выделено зеленой границей);
* строку **origin** - содержимое файла на сервере, закинутое в одноименный коммит ранее. Она показывает выше аналогичную информацию - в нашем случае ту самую строку, которая была удалена (выделено красной границей). 

Выбор требуемого результата изменений предполагает нажатие на нужную кнопку в правой части и сохранение изменений (разрешение конфликта) с опциональной передачей комментария:

![[Pasted image 20240405114643.png|230]] ![[Pasted image 20240405114740.png|400]]

Отсеченные изменения будут безвозвратно удалены. Если была выбрана не та сторона конфликта, можно вновь на локальном устройстве выполнить команду `git push --force`, в результате чего на сервере вновь появится тот же самый неразрешенный конфликт. 

#### Ошибки слияния в VSCode

Если производится слияние веток в VSCode, то ошибки слияния можно посмотреть в модуле "**Resolve Merge**", который разделяет экран на 2 половины: изменения из подтягиваемой ветки и контент текущей ветки. При этом следует иметь в виду:
1. *Current Change* - это содержимое ==подтягиваемой== ветки;
2. *Incoming Change* - это содержимое ==текущей== ветки (внутрь которой мы пуллим или ребейзим данные из другой ветки);
3. Можно выбрать контент только одной из них, а можно ==комбинировать== контент путем выбора *Combine Changes*.

## Отмена слияния, не выложенного в облако
Если был произведен мердж, но необходимо откатить это действие, пока не был выполнен пуш, действия такие:
![[Pasted image 20260522145445.png]]
1. `git origin fetch` - обновление ссылки на удаленный репозиторий;
2. `git branch backup/before-remove-wrong-merge` - создать бэкап текущего мерджа;
3. `git reset --hard origin/develop` - сброс до состояния удаленного репозитория;
4. `git status` - проверка синхронизации с удаленным репозиторием;
5. `git rev-list --left-right --count origin/develop...develop` - Ожидаемо:
	- status: working tree clean
	- rev-list: 0 0

Если вдруг надо восстановить откатанный merge, он останется в backup-ветке - `backup/before-remove-wrong-merge-2026-05-22`
