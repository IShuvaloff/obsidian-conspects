# ДОП. Стилизация email-писем в Laravel

#laravel #mail #markdown #blade #css #email

> [!summary]
> Markdown Mail отделяет смысл письма от его готового HTML-оформления. Содержимое живёт в Mailable template, `<x-mail::...>` задают компоненты, published mail views — layout/components, а theme CSS описывает стиль, который Laravel inline-ит для email clients. Менять нужно минимальный подходящий слой.

## Зачем это нужно

Письмо может хорошо выглядеть в браузере и сломаться в Gmail или Outlook: у клиентов разная поддержка CSS, блокируются внешние ресурсы и стили часто должны оказаться inline. Поэтому «добавить class и подключить CSS» не равно web frontend styling.

Эта глава продолжает [[12. Laravel Mail и Markdown Mail]] и сверена с [Laravel Mail 13](https://laravel.com/docs/13.x/mail).

## Четыре уровня Markdown Mail

```text
Mailable Content(markdown: ...)
↓
content template: текст, Blade data, <x-mail::...>
↓
mail components + HTML layout
↓
theme CSS → CSS inlining
↓
готовые HTML и text email parts
```

| Слой | Что меняет |
|---|---|
| Содержимое шаблона | Текст, variables, Markdown, button URL. |
| Компонент | Поведение/markup button, panel, message. |
| Layout | Каркас HTML письма. |
| Theme CSS | Цвета, шрифты, container, button, spacing. |

Начинать стоит с contents и theme; полную замену layout/components оправдывает только реальная потребность.

## Стандартные компоненты и публикация

Laravel даёт `<x-mail::message>`, `<x-mail::button>`, `<x-mail::panel>`, `<x-mail::table>` и другие Markdown mail components. Чтобы переопределять их локально, публикуют resources:

```bash
php artisan vendor:publish --tag=laravel-mail
```

Появляется `resources/views/vendor/mail`, обычно с HTML component/layout views и темами CSS. После публикации проект может менять локальные copies; обновление Laravel больше не обновляет их автоматически, поэтому не нужно публиковать всё ради одного текста.

Собственную theme добавляют как CSS-файл в опубликованный каталог тем. В Laravel 13 конкретный Markdown Mailable выбирает её свойством Mailable, например `public $theme = 'brand';`; default задаёт `mail.markdown.theme` / `MAIL_MARKDOWN_THEME` в mail configuration. `Content` выбирает template (`markdown:`), а не theme. Laravel переносит CSS в inline styles при рендеринге Markdown Mail.

## Что обычно безопасно менять

- Theme CSS: brand colors, base font, ширина container, margins, button color.
- Content template: wording, логотип как надёжный absolute image URL, action button.
- Component/layout override: только если стандартная разметка действительно не покрывает требование.

В email нельзя рассчитывать на современные browser defaults: external styles могут быть удалены, поддержка flex/grid, media queries и background images неодинакова, remote images часто блокируются до явного разрешения. Проверка HTML в браузере нужна для быстрой диагностики, но финальная проверка — в целевых клиентах или SMTP sandbox.

## Markdown, Blade и autoformatting

В HelpMeIn был реальный сбой: formatter добавил четыре пробела к Markdown внутри `<x-mail::message>`. В Markdown это обычно означает code block, поэтому обычный текст в итоговом письме стал моноширинным/кодовым.

```blade
{{-- blade-formatter-disable --}}
<x-mail::message>
# Заголовок

Обычный Markdown без четырёх пробелов в начале.
</x-mail::message>
{{-- blade-formatter-enable --}}
```

Это узкое отключение форматирования оправдано: оно сохраняет семантически значимые отступы. Комментарии понимает конкретный Blade formatter, который используется в проекте; они не являются синтаксисом Laravel и не гарантируют поведение любого formatter. `.prettierignore` и `.bladeignore` тоже зависят от конкретного расширения и его документации, поэтому не считаются универсальным решением без проверки.

Подсветка Blade и форматирование — независимые возможности редактора. Если файл отображается как Plain Text, нужно проверить language mode в status bar VS Code и расширение подсветки; если template меняет отступы, проверяют default formatter и format-on-save. Отключать formatter для целого проекта ради одного Markdown template обычно слишком широко.

## Безопасная проверка

1. Использовать `MAIL_MAILER=log` или sandbox, не production recipient.
2. Смотреть subject, escaping, URL и HTML output.
3. Не вставлять действующий invitation token в screenshots, commits или documentation.
4. Проверять реальные target clients до большого design rollout.

## Границы

Эта глава не превращает email в полноценную web page. Accessibility, localization, dark mode и client-specific fallbacks развиваются по подтверждённой потребности. Основная архитектура Mailable — в [[12. Laravel Mail и Markdown Mail]].

## Для проверки знаний

### Термины
- Markdown Mail, mail component, layout, theme CSS, CSS inlining.
- Blade formatter, syntax highlighting, language mode.

### Что нужно уметь объяснить
- На каком из четырёх уровней менять цвет button и почему.
- Почему четыре пробела меняют смысл Markdown внутри mail template.
- Почему browser preview не равен Gmail/Outlook verification.

### Типичные ошибки
- Передавать Markdown-ссылку вместо URL в `:url`.
- Переопределять весь layout ради одной CSS-правки.
- Считать formatter comment частью Laravel runtime.

### Мини-практика
- Выбери минимальный слой для изменения brand color и объясни выбор.
- Найди Markdown code-block bug в шаблоне с четырьмя начальными пробелами.
