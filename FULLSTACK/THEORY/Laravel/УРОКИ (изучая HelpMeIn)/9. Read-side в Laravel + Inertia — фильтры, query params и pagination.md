# Read-side в Laravel + Inertia: фильтры, query params и pagination

#laravel #eloquent #inertia #postgresql #pagination #tanstack-table

> [!summary]
> Страница Clients не должна получать все `User` и фильтровать их в браузере. Read-side начинается от current teacher, строит один выразительный Eloquent query, eager-load-ит нужного student, применяет server-side filters и возвращает paginator как Inertia prop. Vue хранит состояние фильтров в URL и отображает только уже подготовленную page data.

## Зачем это нужно

После [[6. Eloquent Models и Relations|models и relations]] и [[7. HTTP flow, Services и Authorization|write-side use case]] следующий реальный вопрос — как учителю увидеть именно своих клиентов, найти нужного и не загрузить всю таблицу сразу. В раннем прототипе это могло выглядеть как `User::all()`. Такой запрос не выражает ownership, не знает о relationship и не масштабируется.

В HelpMeIn read-side Clients page строится от current actor:

```text
Request + query params
↓
$request->user()
↓
teacherRelationships()
↓
filters + eager loading + paginate
↓
Inertia props
↓
Vue table + paginator
```

Главный принцип: query отвечает на вопрос **«какие relationships имеет право и нужно увидеть этому teacher?»**, а не «как отфильтровать уже выданные браузеру данные».

## Короткая карта

| Задача | Инструмент в HelpMeIn |
|---|---|
| Ограничить данные teacher | `$request->user()->teacherRelationships()` |
| Получить student без N+1 | `with('student')` |
| Добавить фильтр только при наличии value | `when(...)` |
| Искать по related student | `whereHas('student', ...)` |
| Case-insensitive поиск PostgreSQL | `ILIKE` |
| Вернуть часть результата | `paginate(3)` |
| Сохранить фильтры в ссылках paginator | `withQueryString()` |
| Синхронизировать фильтры с URL | `router.get(..., { preserveState, replace })` |

Основные API описаны в [Eloquent relationships Laravel 13](https://laravel.com/docs/13.x/eloquent-relationships), [query builder](https://laravel.com/docs/13.x/queries) и [pagination](https://laravel.com/docs/13.x/pagination).

## От `User::all()` к relation query

У `User` есть relation method:

```php
public function teacherRelationships(): HasMany
{
    return $this->hasMany(TeacherStudentRelationship::class, 'teacher_id');
}
```

Скобки здесь важны:

```php
$user->teacherRelationships(); // HasMany / relation query: можно продолжать строить SQL
$user->teacherRelationships;   // уже загруженная Collection моделей
```

Для страницы списка нужен первый вариант. Он сразу ограничивает будущий SQL `teacher_id` текущим user и остаётся query builder, к которому можно добавить фильтры и pagination:

```php
$relationships = $request->user()->teacherRelationships();
```

Dynamic property полезна, когда records уже нужны как результат. Но выражение `$request->user()->teacherRelationships->filter(...)` сначала загрузило бы все relationships в память и лишь потом фильтровало их PHP-кодом. Это не замена SQL filtering и pagination.

## Eager loading: `with('student')`, а не N+1

Каждая строка Clients table показывает student. Если получить relationships, а потом в таблице обращаться к `relationship.student`, lazy loading может сделать один query за relationships и ещё по query на каждого student — N+1.

```php
->with('student')
```

просит Eloquent заранее загрузить relation для всего набора relationships. Это **eager loading**, а не ручной SQL `JOIN`: Eloquent сам выбирает стратегию загрузки и hydrates связанные Models. Цель здесь не «обязательно написать один SQL», а избежать количества запросов, растущего с числом строк.

В типе frontend уже отражена подготовленная форма строки:

```ts
export interface TeacherStudentRelationship {
    id: number;
    activity_status: 'active' | 'paused';
    started_at: string | null;
    ended_at: string | null;
    student: User;
}
```

`student` появляется не магически на frontend: его добавил backend через `with('student')` и serialisation Inertia response.

> [!note]
> `users.full_name` в HelpMeIn — generated PostgreSQL column. Это database-derived value, а не поле, которое следует класть в `$fillable` или вручную собирать в PHP при поиске.

## Server-side filters: состояние запроса, а не локальный массив

Текущий `ClientController` читает search как объект `Stringable`:

```php
$search = $request->string('search')->trim();
```

Это не гарантирует, что строка непустая, поэтому следующий шаг — `$search->isNotEmpty()`. `when()` добавляет фрагмент к query только когда условие истинно:

```php
$relationships = $request
    ->user()
    ->teacherRelationships()
    ->when(
        $request->boolean('only_current'),
        fn ($query) => $query->whereNull('ended_at'),
    )
    ->when(
        $search->isNotEmpty(),
        fn ($query) => $query->whereHas('student', function ($studentQuery) use ($search) {
            $studentQuery->where('full_name', 'ILIKE', "%{$search}%");
        }),
    )
    ->with('student')
    ->paginate(3)
    ->withQueryString();
```

`whereHas('student', ...)` означает: оставить только такие parent relationships, у которых related student удовлетворяет условию. Здесь `ILIKE` — PostgreSQL-оператор case-insensitive pattern matching. Это осознанная привязка к PostgreSQL, а не переносимый на все SQL engines Laravel API.

### Две независимые оси состояния

`only_current` добавляет `WHERE ended_at IS NULL`: это lifecycle period relationship.

```text
ended_at IS NULL / IS NOT NULL
→ current / ended
```

`activity_status` — другая ось: current relationship может быть `active` или `paused`.

```text
activity_status
→ active / paused
```

Завершённость не нужно подменять status case: relationship может закончиться, сохранив последний activity status. Поэтому checkbox «только текущие» фильтрует `ended_at`, а не `activity_status`.

## Query params — часть состояния списка

Controller возвращает и data, и нормализованные filters:

```php
return inertia('Clients', [
    'relationships' => $relationships,
    'filters' => [
        'search' => (string) $search,
        'onlyCurrent' => $request->boolean('only_current'),
    ],
]);
```

В Vue есть две близкие, но разные values: `searchInputValue` — то, что пользователь печатает, а `search` — уже применённый server filter. При Enter или смене checkbox строится URL:

```ts
const query = computed(() => ({
    ...(onlyCurrent.value ? { only_current: true } : {}),
    ...(search.value ? { search: search.value } : {}),
}));

router.get('/clients', {
    ...query.value,
    ...(isPageValid(page) ? { page } : {}),
}, {
    preserveState: true,
    replace: true,
});
```

`router.get()` — Inertia visit: browser не делает full document reload, но Laravel снова строит props для URL. При обновлении страницы или переходе по paginator filters восстанавливаются из query params, а не только из реактивной памяти компонента.

`preserveState` оставляет локальное состояние той же page component; `replace` заменяет текущую history entry, поэтому серия применений фильтра не засоряет кнопку Back. Это UX choices, а не обязательные флаги для каждого запроса.

> [!tip]
> При изменении search или lifecycle filter нужно запрашивать первую страницу. Иначе пользователь может остаться на `page=4`, когда отфильтрованный результат содержит только одну страницу.

## Pagination: `get()` и `paginate()` возвращают разные формы

```php
->get();
```

выполняет query и возвращает Collection всех найденных records. Для малых технических наборов это нормально, но у него нет total, links и ограничения страницы.

```php
->paginate(3);
```

возвращает `LengthAwarePaginator`: текущий срез `data` и metadata о всём результате. В Inertia prop frontend описывает минимально нужную shape generic-типом:

```ts
interface Paginated<T> {
    data: T[];
    per_page: number;
    total: number;
    current_page: number;
    last_page: number;
    prev_page_url: string | null;
    next_page_url: string | null;
}
```

`withQueryString()` добавляет текущие query params к URLs, которые paginator генерирует. Даже если UI сам строит `router.get`, это полезная server-side гарантия для paginator links и будущих вариантов представления.

```text
/clients?search=мишин&only_current=1&page=2
↓
Request
↓
filters + page
↓
LengthAwarePaginator
↓
relationships.data + total/current_page/per_page
```

## Table и paginator: кто владеет чем

TanStack Table получает уже paginated rows:

```vue
<DataTable
    :columns="clientColumns"
    :data="props.relationships.data"
/>
```

В `clientColumns.ts` column definition задаёт способ достать и показать value:

| Поле | Когда использовать |
|---|---|
| `id` | Технический устойчивый ID колонки, если нет прямого поля. |
| `accessorKey` | Прямой attribute, например `activity_status` или `started_at`. |
| `accessorFn` | Вычисленное значение, например `student.full_name`. |
| `cell` | Custom render. `getValue()` даёт value текущей ячейки; `row.original` — исходную relationship row. |

Paginator component не владеет HTTP logic. Он сообщает выбранную страницу через `v-model:page`; page component вызывает `reload(page)`. Внутри paginator scoped slots получают values от базового `Pagination` component:

```vue
<Pagination v-slot="{ page }">
    <PaginationContent v-slot="{ items }">
        <PaginationItem
            v-for="item in items"
            :is-active="item.value === page"
        />
    </PaginationContent>
</Pagination>
```

`v-slot="{ page }"` и `v-slot="{ items }"` — destructuring slot props. Они не создают новое глобальное состояние: parent component передаёт их в slot, а template даёт им локальные имена.

## Цельный flow Clients page

```text
Teacher вводит search / меняет only_current / выбирает page
↓
Clients.vue → router.get('/clients', query)
↓
ClientController
↓
current user → teacherRelationships()
↓
when(...) → whereNull / whereHas
↓
with('student') → нет N+1 для table
↓
paginate() + withQueryString()
↓
Inertia props: relationships + filters
↓
DataTable получает relationships.data
Paginator получает total, per_page, current_page
```

## Границы и связи

Эта глава о server-driven read-side. Она не вводит отдельный JSON API, client-side filtering всех records или бесконечную прокрутку. Sorting, reusable Filter DTO, query scopes, индексы под поиск и измерение фактического SQL — следующие отдельные улучшения, когда появится продуктовая причина.

Смена статуса одной строки — write-side и asynchronous UI concern: [[10. Inertia mutations, useHttp и Optimistic UI]]. Основание для relation query и eager loading разобрано в [[6. Eloquent Models и Relations]].

## Краткое резюме

```text
relation method ()
→ query builder

relation dynamic property
→ loaded Model / Collection

with('student')
→ eager load, защита от N+1

when + whereHas
→ условный server-side filter

paginate + withQueryString
→ срез данных и устойчивый URL состояния
```

Формулировка для повторения: **read-side Clients page начинается с relation query current teacher, а не с `User::all()`; Laravel формирует paginated data, Inertia переносит её как props, а Vue отображает и синхронизирует filter state с URL.**

## Для проверки знаний

### Термины

- Relation method, dynamic relation property, eager loading, N+1.
- `when`, `whereHas`, `ILIKE`, query params.
- `LengthAwarePaginator`, `withQueryString`, scoped slot props.

### Что нужно уметь объяснить

- Почему `$request->user()->teacherRelationships()` безопаснее и точнее стартовой точки `User::all()` для Clients page.
- Чем `teacherRelationships()` отличается от `teacherRelationships`, и почему для filters нужен первый вариант.
- Как `with('student')` предотвращает N+1, не будучи обязательным ручным SQL `JOIN`.
- Почему `ended_at` и `activity_status` — разные оси domain state.
- Почему при смене filters надо вернуться на первую страницу.

### Типичные ошибки

- Загружать relation property и фильтровать Collection в PHP вместо построения query.
- Считать, что `only_current` означает `activity_status = active`.
- Передавать table весь результат `get()` и называть это pagination.
- Терять filters при переходе на следующую страницу.

### Мини-практика

- Добавь условный filter `only_paused` к relation query. Критерий: он применяется через `when`, не смешивается с `ended_at` и сохраняется в query params.
- Объясни, сколько запросов потенциально сделает список из 20 relationships при обращении к `student` без и с `with('student')`.
