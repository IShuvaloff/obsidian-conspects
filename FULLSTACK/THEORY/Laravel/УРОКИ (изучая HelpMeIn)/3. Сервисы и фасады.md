## **Сервис**

**Сервис** — прикладной класс с определённой ответственностью: например, отправить приглашение, получить данные из внешней системы или выполнить операцию с доменной моделью. Laravel не требует обязательной директории `app/Services`: это удобная договорённость проекта, а не правило framework. Поэтому рядом могут существовать `app/Services`, `app/Repositories`, `app/Support` и `app/Actions` — название выбирают по ответственности класса, а не ради соответствия Laravel.

==Пример сервиса==:

```php
// app/Services/StudentService.php
class StudentService
{
    public function createForTeacher(...): void
    {
        // прикладной use case
    }
}
```

Сам класс ещё не обязан иметь ручную регистрацию в container. Если это **concrete class**^[Concrete class — обычный создаваемый класс, а не interface и не abstract class.] и все его зависимости в constructor тоже разрешимы, Laravel создаст его автоматически. Ручное правило нужно тогда, когда container не может вывести способ создания сам или когда архитектура намеренно задаёт этот способ.

## **Сервис-контроллер**

**Controller** — класс HTTP-слоя, который принимает request, вызывает нужную прикладную логику (из сервиса) и возвращает response.

**Service** — класс с прикладной или бизнес-логикой (см. раздел выше), который не должен быть жёстко привязан к HTTP.

```text
Request
  ↓
Controller
  ↓
Service
  ↓
Model / Repository / API
  ↓
Controller
  ↓
Response
```

==Пример==:

```php
class StudentController extends Controller
{
    public function __construct(
        private StudentService $students,
    ) {
    }

    public function store(Request $request)
    {
        $student = $this->students->createForTeacher(...);
        return redirect()->route('students.show', $student);
    }
}
```

## [**Сервис-контейнер**](https://laravel.com/docs/13.x/container)

Service Container — механизм Laravel для **dependency injection** и разрешения зависимостей. Laravel Application одновременно является container: вне provider к нему можно обратиться через [[Функции-хэлперы#Глобальные функции-хелперы|helper app()]], а внутри provider — через `$this->app`.

Контейнер не «хранит все сервисы заранее». Когда Laravel создаёт controller, middleware, job или другой container-resolved class, он читает type hints его constructor или метода и строит нужный объектный граф. Поэтому контейнер связывает два разных случая.

### Automatic resolution без binding

Если зависимости — concrete classes, Laravel обычно не нужно подсказывать правило:

```php
class StudentService
{
}

class StudentController extends Controller
{
    public function __construct(
        private StudentService $service,
    ) {
    }
}
```

Container видит `StudentService`, может создать этот class и передать его в `StudentController`. Если у `StudentService` есть constructor dependencies, тот же процесс продолжается рекурсивно, пока каждая зависимость разрешима.

### Explicit binding

Binding нужен, когда container не может создать требуемое сам — прежде всего для interface, если в параметре конструктора задан именно он, а не класс, — или когда мы сознательно задаём правило создания (внутри провайдера, см. [[3. Сервисы и фасады#[**Сервис-провайдер**](https //laravel.com/docs/13.x/providers)|Сервис-провайдер]]).

```php
interface StudentRepository
{
}

class DatabaseStudentRepository implements StudentRepository
{
}

// внутри provider
$this->app->bind(
    StudentRepository::class,
    DatabaseStudentRepository::class,
);
```

Здесь `StudentRepository` нельзя инстанцировать напрямую. Binding говорит: «когда consumer запрашивает этот contract, передай `DatabaseStudentRepository`».

Это не означает, что у каждого interface обязательно должна быть одна default implementation. Выбор зависит от use case:

```text
Нужен contract в consumer?
│
├── одна реализация для всего приложения
│   └── обычный binding interface → implementation
│
├── разным consumers нужны разные реализации
│   └── contextual binding
│
├── реализация выбирается в runtime по business rule
│   └── factory / strategy / registry
│
└── нужна ровно одна concrete implementation
    └── inject concrete class напрямую
```

## [**Сервис-провайдер**](https://laravel.com/docs/13.x/providers)

Service Provider — центральная точка bootstrap/configuration приложения. Через providers Laravel регистрирует container bindings, настраивает framework или package services и связанные bootstrap-настройки. Поэтому provider — не просто «загрузчик, который пишет правило доступа к сервису».

User-defined providers перечислены в `bootstrap/providers.php`. Laravel также использует providers для своих core services: cache, queue, mail и других.

### `register()` и `boot()`

Provider объявляет только те методы, которые ему нужны.

- `register()` предназначен прежде всего для registrations bindings в container. Внутри него не следует запускать обычную functionality приложения, регистрировать routes, listeners и подобные вещи: часть других providers ещё может не завершить registration.
- `boot()` вызывается после registration phase всех providers. Здесь настраивают приложение и сервисы, когда нужные bindings уже зарегистрированы.

Например, provider может содержать только `register()`, если его единственная задача — binding. И наоборот, provider может не иметь собственных bindings, а в `boot()` настраивать package или framework behavior. Это типичная роль `FortifyServiceProvider`: он может настраивать Fortify actions, views и rate limiting без обязательного собственного binding.

### Способы регистрации сервиса

Регистрация обычно находится в `register()`:

1. `bind`: container создаёт объект по правилу при каждом **resolve**^[`bind` означает правило создания при разрешении зависимости. Это не означает «новый объект при каждом вызове любого метода»: речь идёт именно о том, что происходит, когда container резолвит binding]:
   
```php
$this->app->bind(StudentRepository::class, DatabaseStudentRepository::class);
```

2. `singleton`: после первого **resolve** возвращается та же instance в lifetime container^[`singleton` кэширует resolved instance в рамках lifetime container]:
   
```php
$this->app->singleton(ReportGenerator::class, ReportGenerator::class);
```

3. `instance`: в container кладётся уже созданный объект^[`instance` сразу кладёт туда существующий объект]:
   
```php 
$client = new ExternalSchoolClient(config('services.school.token'));
$this->app->instance(ExternalSchoolClient::class, $client);
```

> [!info]- TODO: `scoped`
> `scoped` похож на `singleton`, но сохраняет один объект только в пределах request/job lifecycle, а затем Laravel очищает его перед следующим lifecycle. Этот нюанс особенно важен для Octane и queue workers; вернуться к нему при изучении long-lived workers.

### Связный пример: repository для HelpMeIn

```php
// app/Contracts/StudentRepository.php
interface StudentRepository
{
    public function findForTeacher(int $studentId, int $teacherId): Student;
}

// app/Repositories/DatabaseStudentRepository.php
class DatabaseStudentRepository implements StudentRepository
{
    public function findForTeacher(int $studentId, int $teacherId): Student
    {
        return Student::query()
            ->whereKey($studentId)
            ->where('teacher_id', $teacherId)
            ->firstOrFail();
    }
}

// app/Services/StudentService.php
class StudentService
{
    public function __construct(
        private StudentRepository $students,
    ) {
    }
}

// app/Providers/AppServiceProvider.php
public function register(): void
{
    $this->app->bind(
        StudentRepository::class,
        DatabaseStudentRepository::class,
    );
}
```

Цепочка здесь следующая: `StudentService` требует `StudentRepository`; container не может создать interface; provider уже зарегистрировал binding; container создаёт `DatabaseStudentRepository` и передаёт его через DI в `StudentService`.

Контрпример важен не меньше. Если приглашение можно послать по email, Telegram или SMS, то binding вида `InvitationSender → EmailInvitationSender` как глобальное правило может оказаться ошибкой: нужный sender выбирается в runtime по business rule. Здесь естественнее factory, strategy или registry, которые делают выбор явно.

### Создание и deferred providers

`php artisan make:provider NameServiceProvider` создаёт provider и добавляет его в `bootstrap/providers.php`. Если provider создан вручную, его класс нужно добавить туда самостоятельно.

> [!info]- TODO: deferred provider
> Laravel поддерживает deferred providers: они загружаются, когда реально требуется предоставляемый ими service. Для этого provider реализует `DeferrableProvider` и сообщает bindings через `provides()`. Это optimisation bootstrap, а не базовый механизм, который нужно применять к каждому custom service.

## [**Фасад**](https://laravel.com/docs/13.x/facades)

Laravel Facade — static proxy к объекту/service, который разрешается через Service Container. Встроенные фасады легко узнать по namespace `Illuminate\Support\Facades\...`, например `DB`, `Cache`, `Log` или `Route`.

Когда код вызывает `DB::table(...)`, это не обычный независимый static API и не обход container:

```text
DB::table(...)
	↓
Facade::__callStatic(...)
	↓
getFacadeAccessor()
	↓
container binding / service
	↓
real object method
```

Facade даёт короткий static-like syntax, но underlying object всё равно приходит из container. Helper functions — другой удобный интерфейс к framework functionality: они не являются фасадами, хотя иногда приводят к тем же underlying services. Например, `view(...)` и `View::make(...)` могут выполнять одинаковую задачу, но один вызов — helper, другой — Facade.

### Создание и привязка custom facade

Custom facade использует `getFacadeAccessor()`, который возвращает ключ или class name для resolution:

```php
namespace App\Facades;

use App\Services\Logger;
use Illuminate\Support\Facades\Facade;

class Log extends Facade
{
    protected static function getFacadeAccessor(): string
    {
        return Logger::class;
    }
}
```

Тогда `Log::info(...)` в конечном счёте просит `Logger` у container. Но custom facade не нужен для каждого custom service. Для domain/application services по умолчанию предпочтительнее explicit DI: зависимости consumer видны в constructor. Facade оправдан, если действительно нужен такой статический интерфейс, а не только потому, что он короче.

### Фасады «на лету» (real-time facades)

Real-time facade создаётся без отдельного класса: достаточно импортировать class с префиксом `Facades`.

```php
use Facades\App\Services\Logger;

Logger::info('Student was invited');
```

Он тоже разрешает underlying class через Service Container. Это справочный инструмент, а не причина заменить explicit DI во всём domain code.

### Тестирование фасадов

Laravel позволяет mock/stub Facade, потому что вызов проксируется к объекту из container. Подробное testing сейчас не разворачиваем — **TODO: вернуться при изучении Testing**. Для внутренне согласованного микро-примера используются один и тот же Facade и route:

```php
use Illuminate\Support\Facades\Cache;

Route::get('/cache', function () {
    return Cache::get('key');
});

public function test_cache_value_is_rendered(): void
{
    Cache::shouldReceive('get')
        ->with('key')
        ->andReturn('value');

    $response = $this->get('/cache');

    $response->assertSee('value');
}
```

## Запрос на получение объекта сервиса

Сервисом пользуются несколькими способами. Базовый способ для custom domain/application code — запросить dependency через type hint и получить её через DI:

```php
class StudentController extends Controller
{
    public function __construct(
        private StudentService $students,
    ) {
    }
}
```

В composition root, provider или редком инфраструктурном месте можно обратиться к container напрямую:

```php
app(StudentService::class)->createForTeacher(...);
```

А Facade остаётся альтернативным удобным способом доступа к некоторым container services:

```php
use Illuminate\Support\Facades\DB;

DB::transaction(function () {
    // ...
});
```

```text
DEPENDENCY INJECTION

StudentController
«мне нужен StudentService»
        ↓
Service Container
        ↓
concrete resolvable class
        ↓
automatic resolution

StudentService
«мне нужен StudentRepository»
        ↓
Service Container
        ↓
interface
        ↓
ищется binding
        ↓
StudentRepository → DatabaseStudentRepository
        ↓
DatabaseStudentRepository передаётся через DI

Где регистрируется binding?
→ Service Provider / register()

Где выполняется bootstrap/configuration?
→ Service Provider / boot()
```

```text
                SERVICE CONTAINER
                 /             \
                /               \
              DI              Facade
              ↓                 ↓
$service->method()           DB::method()
```

Facade — не обязательный следующий этап после Container или Provider, а альтернативный интерфейс для некоторых container services. Поэтому итоговая схема не «мимо container», а такая:

```text
ЗАПРОС → FACADE → [CONTAINER → SERVICE] → ЦЕЛЬ
```

## Для проверки знаний

### Термины

- Service, concrete class, Service Container и automatic resolution.
- Binding, `bind`, `singleton`, `instance`, Service Provider, `register()` и `boot()`.
- Interface, implementation, contextual binding, Facade и helper.

### Что нужно уметь объяснить

- Почему `StudentService` может быть внедрён без явного binding, а `StudentRepository` interface требует правила разрешения.
- Как provider связывает interface с implementation и почему `register()` не используют для routes/listeners.
- Почему Facade использует container, а не обходит его, и когда DI делает зависимости понятнее.

### Типичные ошибки

- Регистрировать вручную каждый concrete class или считать, что у каждого interface обязана быть одна глобальная реализация.
- Считать `bind` созданием объекта при каждом вызове метода, а `singleton` — объектом «на всю жизнь приложения» независимо от lifecycle container.
- Приравнивать Laravel helper functions к Facades либо считать custom facade обязательной обёрткой для каждого service.

### Мини-практика

- Предскажи: `StudentController` получает `StudentService`, а тот получает `StudentRepository`. Какой объект container сможет создать автоматически, где он остановится и какое правило потребуется добавить?
- МикроТЗ: добавь в `register()` binding `StudentRepository::class → DatabaseStudentRepository::class`. Критерии: service type-hint-ит interface, provider содержит binding, а controller не создаёт repository через `new`.
