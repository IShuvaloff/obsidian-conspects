# Laravel migrations: схема БД HelpMeIn

#laravel #migration #postgresql #schema #constraint #index

## Зачем нужен этот урок

PostgreSQL хранит реальную структуру и данные, но Laravel-проекту нужен воспроизводимый способ менять эту структуру. Migration — это **версия изменения schema БД**, а не модель и не сама таблица. Благодаря migrations новая локальная среда, CI и production получают один и тот же путь от пустой database к ожидаемой структуре.

```text
PostgreSQL
→ хранит реальную schema и данные

Laravel migration
→ описывает изменение schema

Eloquent model
→ представляет данные таблицы в PHP
```

Подключение к PostgreSQL, server/database/schema/role и timezone уже разобраны в [[4. PostgreSQL и миграции|уроке 4]]. Здесь важен следующий слой: как Laravel надёжно создаёт и меняет объекты этой database.

## Короткая карта

```text
migration file
↓
php artisan migrate
↓
Laravel проверяет таблицу migrations
↓
выполняет только pending migrations
↓
фиксирует выполненную migration
```

## [Что такое migrations](https://laravel.com/docs/13.x/migrations)

Migration похожа на commit для структуры БД: она фиксирует, **какое изменение** нужно внести и как его по возможности отменить. Это решает обычную проблему команды: не нужно вручную пересказывать коллеге, какую колонку или constraint добавить после pull.

Механизм нужен не только в разработке. Он восстанавливает schema с нуля, применяется на deployment, делает test/CI database воспроизводимой и оставляет историю того, как проект пришёл к текущей структуре.

### Таблица `migrations`

Laravel хранит применённые migration-файлы в служебной таблице `migrations`. В ней записываются имя migration и batch, в котором она была выполнена. Поэтому `php artisan migrate` не запускает всю историю заново, а находит только pending migrations.

На совершенно пустой database `php artisan migrate:status` может сообщить, что migration table ещё не существует. Это нормальное состояние до первого `php artisan migrate`: первая команда создаёт `migrations`, после чего она становится обычной служебной таблицей проекта.

## Создание и структура migration

```bash
php artisan make:migration create_teacher_student_relationships_table
```

Laravel создаёт файл в `database/migrations`. Timestamp в имени определяет порядок выполнения; название по соглашению описывает действие и помогает Laravel угадать таблицу и тип заготовки.

Новая migration имеет такую форму:

```php
return new class extends Migration
{
    public function up(): void
    {
        // переход schema вперёд
    }

    public function down(): void
    {
        // возврат schema назад
    }
};
```

`up()` создаёт или изменяет объекты БД, а `down()` отменяет именно это изменение. Поэтому rollback — не магическое «вернуть код назад», а выполнение обратных операций из migration.

### `Schema::create()` и `Schema::table()`

`Schema::create()` нужен для новой таблицы, `Schema::table()` — для изменения существующей. Оба получают `Blueprint`, в котором описываются columns, indexes и foreign keys.

```php
Schema::create('teacher_student_relationships', function (Blueprint $table) {
    // новая таблица
});

Schema::table('teacher_student_relationships', function (Blueprint $table) {
    // новая колонка или индекс в уже существующей таблице
});
```

## Главный пример: `teacher_student_relationships`

Эта таблица хранит не «ученика вообще», а отдельный период отношений teacher ↔ student.

```text
teacher_student_relationships
─────────────────────────────
id
teacher_id
student_id
activity_status
custom_name nullable
note nullable
started_at nullable
ended_at nullable
created_at
updated_at
```

- Одна запись — один отдельный период отношений.
- Завершённая связь не открывается повторно: следующий период создаёт новую запись.
- `teacher_id` и `student_id` указывают на двух разных `User`.
- Один User может одновременно быть teacher в одной связи и student в другой.
- Глобальные данные User преподаватель не меняет; `custom_name` и `note` принадлежат конкретной relationship.

### Комплексная migration

```php
use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('teacher_student_relationships', function (Blueprint $table) {
            $table->id();

            $table->foreignId('teacher_id')
                ->constrained('users')
                ->restrictOnDelete();

            $table->foreignId('student_id')
                ->constrained('users')
                ->restrictOnDelete();

            $table->string('activity_status');
            $table->string('custom_name')->nullable();
            $table->text('note')->nullable();
            $table->timestampTz('started_at')->nullable();
            $table->timestampTz('ended_at')->nullable();
            $table->timestampsTz();

            $table->index('teacher_id');
            $table->index('student_id');
        });

        DB::statement(
            'ALTER TABLE teacher_student_relationships
             ADD CONSTRAINT teacher_student_relationships_different_users
             CHECK (teacher_id <> student_id)'
        );

        DB::statement(
            "ALTER TABLE teacher_student_relationships
             ADD CONSTRAINT teacher_student_relationships_activity_status_check
             CHECK (activity_status IN ('active', 'paused'))"
        );

        DB::statement(
            'ALTER TABLE teacher_student_relationships
             ADD CONSTRAINT teacher_student_relationships_dates_check
             CHECK (
                ended_at IS NULL
                OR (
                    started_at IS NOT NULL
                    AND ended_at >= started_at
                )
             )'
        );

        DB::statement(
            'CREATE UNIQUE INDEX teacher_student_relationships_active_unique
             ON teacher_student_relationships (teacher_id, student_id)
             WHERE ended_at IS NULL'
        );
    }

    public function down(): void
    {
        Schema::dropIfExists('teacher_student_relationships');
    }
};
```

Это цельный учебный пример структуры, а не замена чтению реального migration-файла проекта. В доступных папках исходники HelpMeIn не найдены, поэтому фрагмент не выдаётся за извлечённый из репозитория код.

### Blueprint: небольшой нужный набор типов

| Метод | Роль в HelpMeIn |
|---|---|
| `$table->id()` | surrogate primary key записи. |
| `$table->string(...)` | короткие значения: статус, custom name. |
| `$table->text(...)` | note произвольной длины. |
| `$table->boolean(...)` | флаг, когда он действительно двухсостоятелен. |
| `$table->timestamp(...)` / `timestampTz(...)` | момент времени без / с timezone-aware смыслом. |
| `$table->foreignId(...)` | колонка для внешнего ключа. |
| `$table->timestamps()` / `timestampsTz()` | технические `created_at` и `updated_at`. |

### `nullable()` — решение модели данных

```php
$table->string('custom_name')->nullable();
```

`nullable()` разрешает `NULL` в PostgreSQL. Это не просто удобство формы, а утверждение модели: значение может объективно отсутствовать. В HelpMeIn `custom_name` и `note` могут быть не заполнены; `started_at` и `ended_at` могут отсутствовать, пока отношения ещё не перешли в соответствующее бизнес-состояние.

### Primary key

```php
$table->id();
```

Это отдельный surrogate PK. Не используется composite PK из `teacher_id + student_id + started_at`: отдельный `id` проще для Eloquent, последующих foreign keys, ссылок из истории и обычной работы с одной записью relationship.

## Foreign keys, indexes и constraints

### Два независимых foreign keys

```php
$table->foreignId('teacher_id')
    ->constrained('users')
    ->restrictOnDelete();

$table->foreignId('student_id')
    ->constrained('users')
    ->restrictOnDelete();
```

Это две отдельные ссылки:

```text
teacher_id → users.id
student_id → users.id
```

Foreign key защищает referential integrity: нельзя записать ID несуществующего User. Сам по себе он не создаёт composite key и не говорит, как быстро искать relationships.

### Почему в HelpMeIn нет `ON DELETE CASCADE`

Для этих связей выбран `->restrictOnDelete()`. История домена не должна исчезать вместе с User: удаление аккаунта будет реализовано через soft delete и anonymization, исторические FK сохранятся, а повторная регистрация создаст нового User с новым `id`.

### Index и foreign key — разные обязанности

```text
FOREIGN KEY
→ integrity

INDEX
→ performance
```

```php
$table->index('teacher_id');
$table->index('student_id');
```

Эти indexes нужны для списка учеников преподавателя и списка преподавателей ученика. Наличие FK не заменяет осознанный index на referencing column.

### CHECK constraints

Часть бизнес-инвариантов должна защищаться не только Laravel validation, но и самой БД.

```sql
CHECK (teacher_id <> student_id)
```

Пользователь не может быть собственным преподавателем.

```sql
CHECK (activity_status IN ('active', 'paused'))
```

БД принимает только допустимые значения статуса.

```sql
CHECK (
    ended_at IS NULL
    OR (
        started_at IS NOT NULL
        AND ended_at >= started_at
    )
)
```

Последняя проверка задаёт допустимые состояния:

| `started_at` | `ended_at` | Смысл |
|---|---|---|
| `NULL` | `NULL` | Связь существует, обучение ещё не началось. |
| не `NULL` | `NULL` | Обучение идёт. |
| не `NULL` | не `NULL` | Период завершён. |
| `NULL` | не `NULL` | Запрещено constraint. |

## `DB::statement()` и PostgreSQL-specific SQL

Laravel Schema Builder покрывает большинство таблиц, columns, indexes и foreign keys. Но PostgreSQL-specific или более сложное правило иногда яснее выразить обычным SQL. Поэтому одна migration может сочетать `Schema::create()` и `DB::statement(...)` — как в `CHECK` constraints и partial unique index выше.

### Partial unique index

```sql
CREATE UNIQUE INDEX teacher_student_relationships_active_unique
    ON teacher_student_relationships (teacher_id, student_id)
 WHERE ended_at IS NULL;
```

Обычный `UNIQUE (teacher_id, student_id)` запретил бы всю историю отношений. Нужна другая инварианта: у пары может быть сколько угодно завершённых периодов, но не более одного текущего незавершённого.

```text
10 → 20 | ended_at = 2026-05-01    ✓
10 → 20 | ended_at = 2026-08-01    ✓
10 → 20 | ended_at = null          ✓
10 → 20 | ended_at = null          ✗
```

`UNIQUE (teacher_id, student_id, ended_at)` не решает задачу ожидаемым образом: в PostgreSQL `NULL` не равен другому `NULL` для обычной unique-проверки. Partial unique index явно ограничивает только строки текущего периода.

## Timestamps и время

```php
$table->timestamps();
$table->timestampsTz();
```

Это технические `created_at` и `updated_at`. Eloquent обычно обновляет их при работе с model; сама PostgreSQL не меняет `updated_at` автоматически без отдельного trigger.

Их нельзя путать с бизнес-временем:

```text
created_at
→ технический момент создания записи

started_at
→ бизнес-момент начала обучения

ended_at
→ бизнес-момент завершения периода
```

Для HelpMeIn используются timezone-aware timestamps: `timestampTz()` и `timestampsTz()`. PostgreSQL хранит абсолютный момент времени, а UI позже показывает его в timezone пользователя. Полная модель `timestamptz` остаётся в [[4. PostgreSQL и миграции|уроке PostgreSQL]].

## Изменение уже выполненной migration

Если migration уже применена, старый файл не редактируют задним числом. Создают новую migration:

```bash
php artisan make:migration update_teacher_student_relationships_dates_check
```

Constraint обычно нельзя «поправить внутри»; его удаляют и создают с новым определением.

```php
public function up(): void
{
    DB::statement(
        'ALTER TABLE teacher_student_relationships
         DROP CONSTRAINT teacher_student_relationships_dates_check'
    );

    DB::statement(
        'ALTER TABLE teacher_student_relationships
         ADD CONSTRAINT teacher_student_relationships_dates_check
         CHECK (
            ended_at IS NULL
            OR (
                started_at IS NOT NULL
                AND ended_at >= started_at
            )
         )'
    );
}

public function down(): void
{
    // Удалить новую проверку и вернуть точное предыдущее определение.
}
```

Так migration history остаётся честной: уже развёрнутые database получают отдельный переход, а не зависят от того, отредактировал ли кто-то прошлое.

## Запуск, rollback и проверка результата

```bash
php artisan migrate
php artisan migrate:status
php artisan migrate:rollback
```

`migrate:rollback` откатывает последний batch, а не произвольный файл по его имени. Перед рискованной операцией полезно посмотреть статус.

## Краткое резюме

| Вопрос | Короткий ответ |
|---|---|
| Что такое migration? | Версия изменения schema БД. |
| Что фиксирует `migrations`? | Какие migrations уже выполнены и в каком batch. |
| `up()` / `down()` | Переход schema вперёд / обратная операция. |
| FK / index | Целостность ссылок / скорость запросов. |
| Partial unique index | Ограничение уникальности только для строк, удовлетворяющих условию. |
| Почему не править старую migration? | Уже применённые database не увидят изменение; нужна новая версия перехода. |

Формулировка для повторения: **Migration описывает воспроизводимое изменение schema, а PostgreSQL constraints и indexes защищают инварианты и производительность независимо от PHP-кода.**

## Для проверки знаний

### Термины

- Migration, pending migration, batch, `up()` и `down()`.
- Schema Builder, Blueprint, foreign key, index, CHECK constraint, partial unique index.
- `timestampTz`, `nullable`, `DB::statement()`.

### Что нужно уметь объяснить

- Как `php artisan migrate` использует таблицу `migrations`, чтобы не повторять уже применённые изменения.
- Почему `teacher_id` и `student_id` — два independent FK, а FK и index решают разные задачи.
- Почему для истории relationship нужен partial unique index, а обычный unique с `ended_at` не задаёт нужное правило.
- Почему уже применённую migration меняют новой migration, а не редактируют её прошлую версию.

### Типичные ошибки

- Считать migration моделью или самой таблицей.
- Ожидать, что FK автоматически делает composite key или полностью заменяет index для запросов.
- Использовать `ON DELETE CASCADE` для исторических domain records либо разрешать `ended_at` без `started_at`.
- Считать `created_at` временем начала обучения.

### Мини-практика

- Предскажи: для пары `teacher_id = 10`, `student_id = 20` уже есть строка с `ended_at = NULL`. Разрешит ли DB вторую незавершённую строку и почему?
- МикроТЗ: напиши migration, которая добавит nullable `note` в `teacher_student_relationships` через `Schema::table()`, а в `down()` удалит эту колонку. Критерий: новая migration, симметричные `up()` и `down()`, без редактирования create migration.
