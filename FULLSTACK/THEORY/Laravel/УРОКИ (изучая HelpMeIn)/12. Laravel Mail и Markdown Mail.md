# Laravel Mail и Markdown Mail

#laravel #mail #mailable #blade #markdown #queue

> [!summary]
> Mailable — PHP-объект, описывающий email: metadata, содержимое и attachments. В HelpMeIn `StudentInvitationMail` получает безопасно подготовленные данные и рендерит Markdown Mail template; отдельный Job решает, когда выполнить отправку. Rendering письма, постановка в очередь и реальная SMTP-доставка — три разные проверки.

## Зачем это нужно

Email — внешний канал: он требует subject, transport и представление для разных почтовых клиентов. Нельзя строить HTML строкой в controller. Mailable отделяет описание письма от use case, а Blade/Markdown template — от PHP orchestration.

```text
business data
↓
Mailable (Envelope + Content + attachments)
↓
Markdown / Blade rendering
↓
HTML + plain-text versions
↓
Mail transport
```

Материал сверён с [Laravel Mail 13](https://laravel.com/docs/13.x/mail). Оформление и специфичные ограничения email вынесены в [[ДОП. Стилизация email-писем в Laravel]].

## Короткая карта

| Конструкция | Ответственность |
|---|---|
| `Mailable` | Описывает одно сообщение. |
| `Envelope` | Subject, from/reply-to/tags и другие metadata. |
| `Content` | Обычный Blade `view:` или Markdown Mail `markdown:`. |
| `Attachment` / `attachments()` | Файлы во вложении. |
| `Mail::to(...)->send(...)` | Отправить сейчас в текущем процессе. |
| `Mail::to(...)->queue(...)` | Поставить отправку Mailable в queue. |

Создать базовый класс можно так:

```bash
php artisan make:mail StudentInvitationMail --markdown=emails.student-invitation
```

## Mailable как явный контракт письма

Текущая форма HelpMeIn:

```php
class StudentInvitationMail extends Mailable
{
    use Queueable, SerializesModels;

    public function __construct(
        public string $teacherEmail,
        public string $actionUrl,
        public ?string $userName = null,
    ) {}

    public function envelope(): Envelope
    {
        return new Envelope(
            subject: 'Приглашение на обучение в ' . config('app.name'),
        );
    }

    public function content(): Content
    {
        return new Content(markdown: 'emails.student-invitation');
    }

    public function attachments(): array
    {
        return [];
    }
}
```

Constructor property promotion делает значения public properties Mailable; Blade template может читать `$teacherEmail`, `$actionUrl` и `$userName`. `?string $userName = null` одновременно допускает `null` **и** позволяет опустить аргумент. Подробнее о nullable/optional PHP — в [[2. PHP Base]].

`attachments(): array` возвращает массив `Attachment`, даже если он пуст. Это не string HTML и не отправка; фактический rendering/transport произойдёт позже.

## `view:` и `markdown:` — это разные rendering paths

```php
new Content(view: 'emails.simple');
```

рендерит обычный Blade view, которому разработчик сам задаёт HTML.

```php
new Content(markdown: 'emails.student-invitation');
```

запускает Markdown Mail pipeline Laravel: Blade variables и mail components превращаются в email-friendly HTML, а Laravel также создаёт plain-text counterpart. Поэтому template с `<x-mail::message>` нельзя воспринимать как обычный HTML Blade view: это Laravel Markdown component, а не HTML custom element браузера.

В реальном template:

```blade
<x-mail::message>
# Здравствуйте{{ $userName !== null ? ', ' . $userName : '' }}!

Вы приглашены на обучение в **{{ config('app.name') }}**.

<x-mail::button :url="$actionUrl">
    Принять приглашение
</x-mail::button>
</x-mail::message>
```

`#`, `**...**` и link — Markdown. `{{ ... }}` — Blade expression. `<x-mail::button>` — Blade component. `:url="$actionUrl"` передаёт в prop реальное URL-string; не нужно передавать туда заранее собранный Markdown вроде `[Принять](...)`.

## Отправка сейчас, очередь Mailable или отдельная Job

```php
Mail::to($recipient)->send($mail);
```

синхронно выполняет transport в текущем PHP process. Это используется внутри текущего `SendStudentInvitationMail::handle()`: Job уже вынесен в queue, поэтому дополнительный queued Mailable не требуется.

Есть два других допустимых решения:

```php
Mail::to($recipient)->queue($mail);
```

или `Mailable implements ShouldQueue`. Тогда Laravel поставит отправку **самого Mailable** в queue. Не стоит одновременно делать Mailable queued и ещё оборачивать его в queued Job с `Mail::send()` без явной причины: получится два слоя очередей, сложнее retries и tracing.

```text
Текущий HelpMeIn
queued SendStudentInvitationMail
→ внутри handle(): Mail::send(StudentInvitationMail)

Альтернатива
Mail::queue(QueuedMailable)
→ Laravel queue wrapper для Mailable
```

## Transport и честная проверка

Transport берётся из mail configuration и env. Для безопасной local проверки применялся:

```dotenv
MAIL_MAILER=log
```

В этом режиме Laravel пишет rendered email в logs вместо SMTP connection. Это удобно, чтобы проверить subject, URL и HTML, не отправляя сообщение. Для ручного rendering также можно открыть сформированный HTML из log без действующего token; в конспектах и скриншотах реальные plain token не публикуются.

Типовые уровни проверки:

| Проверка | Что подтверждает | Чего не подтверждает |
|---|---|---|
| Mailable render | Blade/Markdown, data, subject. | Queue и SMTP. |
| Log mailer + Worker | Job вызвал Mail и письмо сформировано. | Доставка на внешний ящик. |
| SMTP sandbox / provider | Transport принял письмо. | Открытие и отображение у всех клиентов. |

## Практический flow invitation

```text
CreateStudentInvitation
→ создаёт StudentInvitation и возвращает DTO с plain token
↓
будущий orchestration service dispatch-ит Job после commit
↓
SendStudentInvitationMail::handle()
→ повторно проверяет invitation и token hash
↓
new StudentInvitationMail(teacherEmail, actionUrl)
↓
Mail::to(invitation email)->send(...)
```

Сейчас Create service, Mailable и Job существуют и практическая queue/mail проверка сделана. Orchestration service, HTTP wiring dispatch и accept route ещё не завершены; схема выше показывает следующий intended flow, а не завершённый end-to-end feature.

## Ошибки и границы

- Неверное имя view, route или config обычно проявится при render/send; не маскируй эту ошибку пустым `catch`.
- URL строится как обычная строка URL; Markdown syntax принадлежит body template, не route helper.
- Mailable отвечает за представление сообщения, но не за Policy, создание invitation или domain conflict.
- Mailer log не заменяет SMTP test; email client не равен обычному browser.

## Краткое резюме

**Mailable описывает письмо; `Content(markdown: ...)` запускает Markdown Mail pipeline; Job определяет момент асинхронной отправки.** Для текущего HelpMeIn один queued Job + synchronous `Mail::send()` внутри него — один слой очереди, а не два.

## Для проверки знаний

### Термины
- Mailable, Envelope, Content, Attachment, mail transport.
- Blade, Markdown Mail, HTML version, plain-text version.
- `send`, `queue`, `ShouldQueue`, log mailer.

### Что нужно уметь объяснить
- Чем `view:` отличается от `markdown:`.
- Почему `:url="$actionUrl"` получает URL, а не Markdown-link.
- Почему текущая Job не нуждается в ещё одном queued Mailable.
- Почему log mailer не доказывает SMTP delivery.

### Типичные ошибки
- Рендерить template с `<x-mail::message>` как обычный HTML view.
- Смешивать отправку, domain logic и transport configuration в controller.
- Публиковать plain invitation token в logs или документации.

### Мини-практика
- Добавь nullable optional `$userName` в constructor Mailable и объясни вызовы с двумя и тремя аргументами.
- Определи, какой вариант выбрать для slow email: `send`, `queue($mailable)` или отдельный Job — и почему.
