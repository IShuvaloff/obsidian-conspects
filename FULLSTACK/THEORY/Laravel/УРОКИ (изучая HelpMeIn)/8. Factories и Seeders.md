# Factories и Seeders: demo-данные HelpMeIn

#laravel #eloquent #factory #seeder #database

> [!summary]
> Factory — reusable recipe, которая описывает, как создать одну Model с осмысленными default values. Seeder — сценарий, который комбинирует factories и создаёт набор данных для конкретной задачи: demo, локальной проверки или позже tests. В HelpMeIn `ClientDemoSeeder` создаёт teachers и relationships, чтобы проверить Clients page, filtering и pagination.

## Зачем это нужно

Без factories и seeders для каждой проверки пришлось бы вручную создавать Users и relationships через UI, SQL или Tinker. Это долго и не даёт повторяемого сценария. Factories автоматизируют создание отдельных моделей, а seeders собирают из них полезную картину данных.

```text
Factory
→ как создать одну Model

Seeder
→ какой набор Models нужен приложению

ClientDemoSeeder
→ два teachers и relationships для проверки Clients page
```

Factories полезны для local demo data, seeders и будущих automated tests. Они не заменяют [[5. Миграции|migrations]]: migration создаёт schema, factory/seeder создают rows в уже существующей schema.

## Короткая карта

| Вопрос | Короткий ответ |
|---|---|
| Где живёт factory? | `database/factories`. |
| Где живёт seeder? | `database/seeders`. |
| Что возвращает `Model::factory()`? | Factory object — ещё не Model и не row в DB. |
| Когда появляется row? | После `create()`. |
| Что делает state? | Меняет будущие attributes factory, но ещё ничего не сохраняет. |
| Зачем seeder? | Описывает сценарный набор связанных demo/test records. |

## Factory: recipe для одной Model

Factory — класс, который задаёт default attributes для создания конкретной Eloquent Model. Laravel обычно хранит такие классы в `database/factories`.

`UserFactory` HelpMeIn использует `definition()` и `fake()`:

```php
public function definition(): array
{
    return [
        'name' => fake()->name(),
        'surname' => fake()->lastName(),
        'email' => fake()->unique()->safeEmail(),
        'email_verified_at' => now(),
        'password' => static::$password ??= Hash::make('password'),
        'phone' => '+7' . fake()->numerify('##########'),
        'address' => fake()->address(),
        'is_admin' => false,
    ];
}
```

`fake()` даёт доступ к Faker: он генерирует realistic-looking, но тестовые значения. Default values не запрещают override при создании:

```php
$teacher = User::factory()->create([
    'name' => 'Людмила',
    'surname' => 'Шувалова',
    'email' => 'tiare_white@mail.ru',
]);
```

В текущем `UserFactory` общий dev password вычисляется один раз и затем переиспользуется. Поэтому demo user можно предсказуемо использовать при локальной разработке; конкретный пароль не должен попадать в production-практику.

### `HasFactory`: связь Model с Factory

Model получает static method `factory()` через trait `HasFactory`:

```php
class User extends Authenticatable
{
    use HasFactory;
}

class TeacherStudentRelationship extends Model
{
    use HasFactory;
}
```

Laravel по convention находит `Database\Factories\UserFactory` для `App\Models\User` и `TeacherStudentRelationshipFactory` для соответствующей relationship model. Новую factory можно создать командой:

```bash
php artisan make:factory TeacherStudentRelationshipFactory --model=TeacherStudentRelationship
```

## Factory object и реальная Model

Это ключевое различие:

```text
User::factory()
→ Factory object / инструкция на создание User

User::factory()->state([...])
→ всё ещё Factory object, но с изменёнными будущими values

User::factory()->create([...])
→ User model уже создана и сохранена в database
```

```php
User::factory()->create();
User::factory(10)->create();
```

Первый вызов создаёт одного User, второй — десять. Если созданная model нужна следующей строке кода, нужно вызвать `create()` и сохранить результат. Если она нужна только как dependency для foreign key, можно передать Factory object: Laravel сам создаст нужную model и подставит её `id`.

### Два корректных способа создать student

**A.** Student нужен дальше в коде — создаём его явно:

```php
$student = User::factory()->create([
    'name' => 'Станислав',
]);

TeacherStudentRelationship::factory()->create([
    'student_id' => $student->id,
]);
```

**B.** Student нужен ровно один раз как related model — передаём Factory object:

```php
TeacherStudentRelationship::factory()->create([
    'student_id' => User::factory()->state([
        'name' => 'Станислав',
    ]),
]);
```

В массиве relationship используются `teacher_id` и `student_id`, потому что это реальные FK-колонки таблицы `teacher_student_relationships`. `teacher` и `student` — relation properties, а не database attributes для mass assignment.

Во втором варианте не надо вручную писать `User::factory()->create()`: передан Factory object, и Laravel создаёт User в нужный момент, берёт его `id` и записывает его в `student_id`. Ручной `create()` здесь нужен только тогда, когда object должен быть сохранён в переменной или переиспользован.

## Factory relationship HelpMeIn

Текущий `TeacherStudentRelationshipFactory` задаёт безопасный default scenario:

```php
public function definition(): array
{
    return [
        'teacher_id' => User::factory(),
        'student_id' => User::factory(),
        'activity_status' => ActivityStatus::Active,
        'custom_name' => null,
        'note' => null,
        'started_at' => now(),
        'ended_at' => null,
    ];
}
```

`teacher_id` и `student_id` получают Factory objects: если caller не задал их сам, Laravel создаст двух Users. `started_at = now()` и `ended_at = null` выражают current relationship.

Status передаётся как enum case `ActivityStatus::Active`, без `->value`. Eloquent enum cast сам преобразует case в строку `'active'` при записи в PostgreSQL `varchar`; factory и application code остаются type-safe и не повторяют storage detail.

## Factory states: вариации recipe

State — маленькое изменение default definition. Его можно задать разово:

```php
User::factory()->state([
    'is_admin' => true,
]);
```

Для часто повторяющихся бизнес-состояний лучше дать factory выразительные methods. В HelpMeIn уже есть:

```php
public function paused(): static
{
    return $this->state(fn () => [
        'activity_status' => ActivityStatus::Paused,
    ]);
}

public function ended(): static
{
    return $this->state(fn () => [
        'ended_at' => now(),
    ]);
}
```

`public function paused(): static` — обычный instance method factory. `: static` означает return type «object текущего класса»; это не `public static function`. `paused()` и `ended()` вызываются на Factory object и возвращают Factory object для дальнейшей настройки.

```text
TeacherStudentRelationship::factory()
→ Factory

->paused()
→ всё ещё Factory

->ended()
→ всё ещё Factory

->create()
→ уже TeacherStudentRelationship Model
```

После `create()` factory-state methods вызвать нельзя: chain закончилась Model object. В текущем проекте `ended()` ставит только `ended_at`; `activity_status` остаётся default `active`. Это соответствует текущей data model: завершённость периода выражена `ended_at`, а не отдельным enum case `Ended`.

## Seeder: сценарий набора данных

Seeder не отвечает на вопрос «как создать одну model». Он отвечает на вопрос «какая картина данных нужна для конкретной проверки». Seeder classes находятся в `database/seeders`.

```bash
php artisan make:seeder ClientDemoSeeder
php artisan db:seed --class=ClientDemoSeeder
```

`ClientDemoSeeder` HelpMeIn создаёт сценарий для Clients page:

```text
Teacher A
├── 5 students
│   ├── active/current
│   ├── paused/current
│   ├── ended
│   └── несколько active/current

Teacher B
└── отдельный student
```

Этот набор нужен, чтобы проверить, что current teacher видит только `teacherRelationships`, а также подготовить данные для server-side filtering и pagination.

```php
$teacher1 = User::factory()->create([
    'name' => 'Людмила',
    'surname' => 'Шувалова',
    'email' => 'tiare_white@mail.ru',
]);

TeacherStudentRelationship::factory()->paused()->create([
    'teacher_id' => $teacher1->id,
    'student_id' => User::factory()->state([
        'name' => 'Дмитрий',
        'surname' => 'Мишин',
    ]),
]);
```

Teacher создан явно, потому что один и тот же object повторно нужен для пяти relationships. Student передан factory напрямую, потому что он нужен только для одной relationship. Для demo users полезно явно задавать email: легче войти под известным account или быстро найти его в database.

### Повторный запуск и idempotency

`ClientDemoSeeder` сейчас — demo scenario, а не идемпотентный import. Повторный запуск неидемпотентного seeder может создать повторные records или упасть на unique constraint: здесь у Teacher A задан один и тот же email. Это допустимо для локального одноразового demo seed, но требует сознательной очистки или другой strategy при регулярном запуске.

Для сравнения, текущий `DatabaseSeeder` создаёт admin через `updateOrCreate` по email — это уже ближе к idempotent behaviour. Полную тему idempotent seeders оставляем на потом.

## Factory и Seeder: не конкуренты

| Factory | Seeder |
|---|---|
| Как создать одну model. | Какой набор данных создать. |
| Reusable recipe. | Application/demo scenario. |
| Может использоваться в Tinker, seeders и tests. | Обычно использует factories или Eloquent/Query Builder. |
| Например: default `TeacherStudentRelationship`. | Например: два teachers для проверки Clients page. |

## Tinker: быстрая проверка Factory

```bash
php artisan tinker
```

```php
User::factory()->create();
User::factory(10)->create();
TeacherStudentRelationship::factory()->create();
```

Tinker полезен, чтобы быстро проверить, что factory обнаружена, `HasFactory` подключён, FK models создаются и enum/timestamps проходят в PostgreSQL. Это исследовательский инструмент; повторяемый набор demo data должен жить в seeder, а не оставаться только в истории Tinker-команд.

## Краткое резюме

| Вопрос | Короткий ответ |
|---|---|
| Что делает `definition()`? | Задаёт default attributes для будущей Model. |
| Что возвращает `factory()`? | Factory object, не DB row. |
| Что делает `state()`? | Меняет будущие attributes и возвращает Factory. |
| Что делает `create()`? | Создаёт и сохраняет Model в database. |
| Когда передавать `User::factory()` в FK? | Когда related User нужен только как dependency. |
| Почему teacher создаётся отдельно? | Он переиспользуется несколькими relationships. |
| Что делает seeder? | Собирает целевой набор данных из factories и других операций. |

Формулировка для повторения: **Factory описывает способ создать одну корректную model, а Seeder описывает полезный сценарий из многих models. Factory chain создаёт данные только на `create()`.**

## Для проверки знаний

### Термины

- Factory, `definition()`, Faker, `HasFactory`, Factory object, `create()`.
- State, `: static`, `paused()`, `ended()`.
- Seeder, demo data, idempotency, `updateOrCreate`.

### Что нужно уметь объяснить

- Чем Factory отличается от Seeder и почему они не конкурируют.
- Чем `User::factory()`, `User::factory()->state(...)` и `User::factory()->create()` отличаются по результату.
- Почему FK attributes называются `teacher_id` / `student_id`, а не `teacher` / `student`.
- Почему Teacher A создаётся явно, а одноразовый student может быть Factory object внутри `student_id`.
- Почему `ended()` меняет `ended_at`, но не обязан менять `activity_status`.

### Типичные ошибки

- Считать, что `factory()` или `state()` уже вставили row в database.
- Вызывать `create()` для factory, которую нужно передать только как FK dependency.
- Ожидать, что demo seeder безопасно запустится повторно без idempotent strategy.
- Путать `: static` у instance method с `public static function`.

### Мини-практика

- Предскажи: сколько Users и relationships создаст `TeacherStudentRelationship::factory()->create()` при пустой DB и почему?
- МикроТЗ: создай через factory paused relationship для существующего `$teacher`, а student передай Factory object с фиксированным `name`. Критерии: указан `teacher_id`, отсутствует ручной `student_id` из `create()`, вызван `paused()` до `create()`.
- Объясни, почему повторный запуск `ClientDemoSeeder` с фиксированным email Teacher A не является надёжным reset workflow.
