# PostgreSQL — разворачивание, структура и подключение к Laravel

#postgresql #database #laravel #migration #role #schema

> Этот конспект относится к фазе изучения **PostgreSQL + migrations**. Цель блока — понимать не только, как подключить Laravel к PostgreSQL, но и что именно находится между приложением и таблицей: сервер БД, database, schema, role, драйвер PHP и служебные каталоги PostgreSQL.

## Общая схема

```text
Laravel
   ↓
PHP
   ↓
PDO
   ↓
pdo_pgsql
   ↓
PostgreSQL Server
   ↓
Database
   ↓
Schema
   ↓
Tables / Views / Indexes / Constraints
```

Отдельно существует **role** — пользователь PostgreSQL, от имени которого приложение подключается к серверу и получает права на работу с объектами базы данных.

## Разворачивание PostgreSQL локально

Для локальной разработки на Windows достаточно установить:

- PostgreSQL Server;
- Command Line Tools (`psql`);
- pgAdmin — необязательно, если используется DBeaver;
- PHP-драйвер `pdo_pgsql`.

После установки сервер PostgreSQL обычно слушает стандартный адрес:

```text
127.0.0.1:5432
```

Проверка установленного клиента:

```powershell
psql --version
```

Проверка PHP-драйвера:

```powershell
php -m | findstr /I "pgsql pdo_pgsql"
```

Для Laravel критически нужен `pdo_pgsql`.

```text
psql
→ консольный клиент для человека

pdo_pgsql
→ драйвер, через который PHP/Laravel работает с PostgreSQL
```

Если `pdo_pgsql` отключён, его нужно включить в используемом CLI-файле `php.ini`:

```ini
extension=pdo_pgsql
extension=pgsql
```

Проверить, какой именно `php.ini` используется:

```powershell
php --ini
```

## PostgreSQL Server, Database, Schema и Role

Эти понятия относятся к разным уровням.

```text
PostgreSQL Server
│
├── Roles
│   ├── postgres
│   └── help_me_in_app
│
├── Database postgres
│
└── Database help_me_in
    │
    ├── Schema public
    │   ├── users
    │   ├── migrations
    │   └── teacher_student_relationships
    │
    ├── Schema information_schema
    │
    └── Schema pg_catalog
```

### Database

**Database** — крупный изолированный контейнер данных внутри PostgreSQL Server.

Например:

```text
help_me_in
```

Laravel выбирает нужную database через конфигурацию подключения:

```dotenv
DB_DATABASE=help_me_in
```

Внутри одной PostgreSQL database уже находятся schemas, tables, views, indexes, constraints и другие объекты.

### Schema

**Schema** — пространство имён внутри конкретной database.

Например:

```text
public.users
public.teacher_student_relationships
```

В разных schemas могут существовать таблицы с одинаковыми именами:

```text
public.users
archive.users
```

Это будут разные объекты.

Для обычного Laravel-приложения основная рабочая schema чаще всего `public`.

Поэтому запрос:

```sql
SELECT * FROM users;
```

обычно обращается к `public.users`. Это определяется параметром `search_path`.

Проверить его можно так:

```sql
SHOW search_path;
```

### Role

**Role** — субъект доступа PostgreSQL.

Role не хранит бизнес-данные и не является schema или database.

Например `help_me_in_app` может использоваться Laravel для подключения к database `help_me_in`.

У role могут быть права `CONNECT`, `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE` и другие.

```text
Database
→ где находятся данные

Schema
→ как организованы объекты внутри database

Role
→ кто имеет право работать с этими объектами
```

Для приложения лучше использовать отдельную role, а не подключаться от имени административного пользователя `postgres`.

```sql
CREATE ROLE help_me_in_app
WITH LOGIN PASSWORD 'password';

CREATE DATABASE help_me_in
OWNER help_me_in_app;
```

## Подключение Laravel к PostgreSQL

В Laravel уже существует connection `pgsql` в `config/database.php`.

Само окружение переключается через `.env`:

```dotenv
DB_CONNECTION=pgsql
DB_HOST=127.0.0.1
DB_PORT=5432
DB_DATABASE=help_me_in
DB_USERNAME=help_me_in_app
DB_PASSWORD=...
DB_SSLMODE=prefer
```

Логика подключения:

```text
.env
DB_CONNECTION=pgsql
        ↓
config/database.php
connections.pgsql
        ↓
PDO / pdo_pgsql
        ↓
PostgreSQL Server
        ↓
database help_me_in
```

После изменения `.env` полезно очистить config cache:

```bash
php artisan config:clear
```

## `public`, `information_schema` и `pg_catalog`

В PostgreSQL мы обращаемся не всегда только к `public`, потому что разные schemas имеют разное назначение.

### `public`

`public` — обычная рабочая schema приложения.

Здесь находятся реальные объекты HelpMeIn:

```text
public.users
public.teacher_student_relationships
public.migrations
```

То есть:

```sql
SELECT * FROM public.users;
```

читает реальные пользовательские данные.

### `information_schema`

`information_schema` — служебная schema, содержащая стандартизированное описание структуры database.

Например:

```sql
SELECT *
FROM information_schema.columns;
```

не читает данные из таблиц приложения. Этот запрос читает **метаданные о колонках**.

Пример результата по смыслу:

```text
table_schema = public
table_name   = users
column_name  = email
data_type    = character varying
is_nullable  = NO
```

Поэтому запрос:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public';
```

означает: «прочитать каталог таблиц и показать только те, которые находятся в schema `public`».

### `pg_catalog`

`pg_catalog` — системные каталоги PostgreSQL.

По смыслу он похож на `information_schema`, но содержит более подробные и PostgreSQL-specific метаданные.

```text
information_schema
→ стандартный SQL-интерфейс к метаданным

pg_catalog
→ внутренние каталоги PostgreSQL
```

Например:

```sql
SELECT *
FROM pg_tables;
```

использует PostgreSQL-specific представление таблиц.

## Основные служебные запросы

### Текущая database и role

```sql
SELECT current_database(), current_user;
```

### Версия PostgreSQL

```sql
SELECT version();
```

или:

```sql
SHOW server_version;
```

### Timezone текущей session

```sql
SHOW timezone;
```

### Список roles

```sql
SELECT
    rolname,
    rolsuper,
    rolcreatedb,
    rolcreaterole,
    rolcanlogin
FROM pg_roles
ORDER BY rolname;
```

### Список databases

```sql
SELECT
    datname,
    datdba,
    encoding,
    datcollate,
    datctype
FROM pg_database
ORDER BY datname;
```

### Список schemas

```sql
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;
```

### Таблицы schema `public`

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_type = 'BASE TABLE'
ORDER BY table_name;
```

### Колонки таблицы

```sql
SELECT
    column_name,
    data_type,
    is_nullable,
    column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'users'
ORDER BY ordinal_position;
```

### Constraints таблицы

```sql
SELECT
    constraint_name,
    constraint_type
FROM information_schema.table_constraints
WHERE table_schema = 'public'
  AND table_name = 'users'
ORDER BY constraint_type, constraint_name;
```

### Индексы

```sql
SELECT
    indexname,
    indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'teacher_student_relationships';
```

### Sequences

```sql
SELECT
    sequence_schema,
    sequence_name
FROM information_schema.sequences
ORDER BY sequence_schema, sequence_name;
```

### Views

```sql
SELECT
    table_schema,
    table_name
FROM information_schema.views
WHERE table_schema = 'public'
ORDER BY table_name;
```

### Materialized Views

```sql
SELECT
    schemaname,
    matviewname
FROM pg_matviews
ORDER BY schemaname, matviewname;
```

### Текущие подключения

```sql
SELECT
    pid,
    usename,
    datname,
    client_addr,
    application_name,
    state
FROM pg_stat_activity
ORDER BY pid;
```

## PostgreSQL и Laravel migrations

Migration — это не сама database и не модель Eloquent.

```text
PostgreSQL
→ хранит реальные таблицы и данные

Laravel migrations
→ описывают изменение schema

Eloquent models
→ дают PHP-коду объектный интерфейс к данным
```

Например:

```php
Schema::create('users', function (Blueprint $table) {
    $table->id();
    $table->string('email')->unique();
});
```

описывает изменение структуры database.

А:

```php
class User extends Authenticatable
```

не создаёт таблицу `users`, а представляет записи этой таблицы в PHP-коде.

### Проверка доступности PostgreSQL в Laravel

1. ==Подключиться к базе данных в терминале== (для выполнения noSQL-запросов)^[для отключения использовать Ctrl+C, Ctrl+D (Linux/MacOS) или команду `exit`/`quit`]:

	```
	php artisan tinker
	```

2. Выполнить запрос-обращение к БД:

	```php
	DB::connection()->getPdo();
	```

Если все ОК, вернется PDO-объект без ошибок. Доп. команды:
- `DB::connection()->getDatabaseName()`;

Только после проверки можно выполнить команду миграции - все файлы миграции отработают в порядке очереди и структура БД будет восстановлена на новом адресе.

### Таблица `migrations`

Laravel хранит историю выполненных migrations в отдельной таблице `migrations`.

Она позволяет понять:

```text
какие migration-файлы уже применены
→ повторно не выполнять

какие ещё не применены
→ выполнить при php artisan migrate
```

На новой пустой PostgreSQL database Laravel создаёт эту таблицу сам при первом запуске migrations.

==Запуск миграций==:

```
php artisan migrate
```

## Типы времени и timezone

Для реальных моментов времени в коммерческом приложении лучше использовать timezone-aware timestamps.

В PostgreSQL:

```text
timestamp with time zone
```

или:

```text
timestamptz
```

В Laravel migration:

```php
$table->timestampTz('started_at')->nullable();
$table->timestampTz('ended_at')->nullable();
$table->timestampsTz();
```

PostgreSQL не хранит исходное название зоны вроде `Europe/Moscow` внутри `timestamptz`. Он хранит абсолютный момент времени, а отображение происходит согласно timezone текущей session.

```text
Database
→ хранит абсолютный момент времени

Application / User settings
→ знают нужный timezone

UI
→ показывает локальное время пользователю
```

## Generated columns

PostgreSQL поддерживает вычисляемые поля — **generated columns**.

Например:

```sql
CREATE TABLE products (
    price numeric(10,2),
    quantity integer,

    total numeric(12,2)
        GENERATED ALWAYS AS (price * quantity) STORED
);
```

Тогда приложение записывает `price` и `quantity`, а PostgreSQL сам вычисляет `total`.

Generated column полезна, когда значение полностью определяется другими полями этой же строки. Но её не следует добавлять просто ради удобства, если выражение и без неё легко вычисляется в запросе.

## Constraints и целостность данных

PostgreSQL должен защищать важные бизнес-инварианты независимо от Laravel-кода.

Например:

```sql
CHECK (teacher_id <> student_id)
```

не позволяет пользователю стать собственным преподавателем.

```sql
CHECK (
    ended_at IS NULL
    OR started_at IS NULL
    OR ended_at >= started_at
)
```

не позволяет сохранить окончание периода раньше его начала.

```text
Laravel validation
→ защищает нормальный application flow

PostgreSQL constraints
→ защищают сами данные
```

## Partial unique index

PostgreSQL позволяет сделать уникальность только для части строк.

Для HelpMeIn это нужно, чтобы одна пара teacher/student могла иметь много исторических периодов, но только одну текущую связь.

```sql
CREATE UNIQUE INDEX teacher_student_relationships_active_unique
ON teacher_student_relationships (teacher_id, student_id)
WHERE ended_at IS NULL;
```

```text
10 → 20 | ended_at = 2026-05-01    ✓
10 → 20 | ended_at = 2026-08-01    ✓
10 → 20 | ended_at = null          ✓

ещё одна:
10 → 20 | ended_at = null          ✗
```

## Foreign Key и Index — не одно и то же

Foreign Key отвечает за **целостность**:

```text
teacher_id
должен ссылаться на существующий users.id
```

Index отвечает за **скорость поиска**:

```text
WHERE teacher_id = ?
WHERE student_id = ?
```

Поэтому наличие FK само по себе не заменяет осознанное проектирование индексов.

## Удаление пользователей в HelpMeIn

Для доменных таблиц HelpMeIn принято правило: никакого `ON DELETE CASCADE`.

Удаление аккаунта пользователя не должно физически уничтожать историю приложения.

```text
User удаляет аккаунт
↓
deleted_at != null
↓
login запрещён
↓
PII очищаются / обезличиваются
↓
техническая запись users.id остаётся
↓
исторические FK продолжают существовать
```

Если человек позже снова зарегистрируется с тем же email, создаётся новый `users.id`. Старый User автоматически не восстанавливается.

## Ежедневный минимум

Ниже — короткий набор команд, которого достаточно для повседневной проверки PostgreSQL во время разработки HelpMeIn.

```sql
-- Где я сейчас нахожусь и под какой role подключён
SELECT current_database(), current_user;

-- Какие roles существуют
SELECT rolname
FROM pg_roles
ORDER BY rolname;

-- Какие databases существуют на сервере
SELECT datname
FROM pg_database
ORDER BY datname;

-- Какие schemas есть в текущей database
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;

-- Какие пользовательские таблицы есть в public
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_type = 'BASE TABLE'
ORDER BY table_name;

-- Как устроена конкретная таблица
SELECT
    column_name,
    data_type,
    is_nullable,
    column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'users'
ORDER BY ordinal_position;

-- Какие индексы есть в public
SELECT
    tablename,
    indexname,
    indexdef
FROM pg_indexes
WHERE schemaname = 'public'
ORDER BY tablename, indexname;
```

Короткая памятка по смыслу:

```text
current_database / current_user
→ куда и кем подключён

pg_roles
→ кто существует в PostgreSQL

pg_database
→ какие databases существуют

information_schema.schemata
→ какие namespaces есть внутри database

information_schema.tables
→ какие таблицы существуют

information_schema.columns
→ как устроена таблица

pg_indexes
→ какие индексы реально созданы
```
