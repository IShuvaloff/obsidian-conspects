# Eloquent Models и Relations: HelpMeIn

#laravel #eloquent #postgresql #orm #relations

> [!summary]
> Eloquent связывает строку PostgreSQL с PHP-объектом. Model знает, как читать и сохранять свои attributes, casts превращают DB values в удобные PHP-типы, а relations дают объектную навигацию по уже существующим foreign keys. В HelpMeIn эта связка описывает `User`, период отношений teacher ↔ student и историю его статусов.

## Зачем это нужно

После [[5. Миграции|migration]] в PostgreSQL есть таблицы, foreign keys и constraints. Но PHP-коду неудобно постоянно собирать SQL и вручную превращать результаты запросов в объекты. Eloquent — ORM Laravel: он даёт модели объектный интерфейс к persistence, не отменяя PostgreSQL как источник данных и целостности.

```text
PostgreSQL table / row
↓
PDO / SQL query
↓
Eloquent hydration
↓
Model object
↓
casts / relations / CRUD
```

**Hydration** — процесс, в котором Eloquent берёт данные строки результата и создаёт Model object, заполняя его attributes и применяя casts при обращении к ним. Обратный путь выглядит так:

```text
Model object
↓
save() / create() / update()
↓
SQL
↓
PostgreSQL
```

Этот урок опирается на [Eloquent Laravel 13](https://laravel.com/docs/13.x/eloquent), [relations](https://laravel.com/docs/13.x/eloquent-relationships) и [casts](https://laravel.com/docs/13.x/eloquent-mutators). В нём используется текущая реальная модель HelpMeIn, а не абстрактные `Post` и `Comment`.

## Короткая карта

```text
users
  ↑ teacher_id / student_id
teacher_student_relationships
  ↑ relationship_id
teacher_student_status_history

users
  ↑ changed_by
teacher_student_status_history
```

| Сущность | Роль в HelpMeIn |
|---|---|
| `User` | Общая auth-entity; в разных relationships может быть teacher или student. |
| `TeacherStudentRelationship` | Самостоятельная domain entity: один период отношений teacher ↔ student. |
| `TeacherStudentStatusHistoryEvent` | Append-only событие истории статуса relationship. |
| `ActivityStatus` | Backed enum для `active` / `paused`. |

## Model, table и DTO — разные вещи

| Сущность | За что отвечает |
|---|---|
| Database row | Физически хранит состояние в PostgreSQL. |
| Eloquent Model | ORM-объект: persistence, queries, casts и relations. |
| DTO | Переносит данные между слоями, не обязан знать о БД. |

Типичный application flow может быть таким:

```text
Request
↓
Validation
↓
DTO (если нужен)
↓
Service / Use Case
↓
Eloquent Model
↓
PostgreSQL
```

DTO не обязателен для каждого CRUD-действия. Он полезен, когда данные нужно явно передать через границу слоя, отделить входные данные от HTTP Request или собрать сложную операцию. Простая модель не становится DTO только потому, что её передали в метод.

## Конвенции Eloquent: имя таблицы, ключ и timestamps

Eloquent следует соглашениям, чтобы не требовать настройки в каждом классе. `TeacherStudentRelationship` автоматически сопоставляется с `teacher_student_relationships`: имя класса переводится в `snake_case` и множественное число. Аналогично `User` → `users`; для неправильных форм Laravel использует pluralization, например `Person` → `people`.

Если таблица не следует соглашению, имя задают явно. В текущей history model HelpMeIn это сделано так:

```php
class TeacherStudentStatusHistoryEvent extends Model
{
    protected $table = 'teacher_student_status_history';
}
```

Имя класса намеренно отражает domain-смысл события, а имя таблицы уже выбрано в migration. Поэтому convention не подходит и нужна явная настройка.

### Primary key

```php
$table->id();
```

в migration создаёт стандартный primary key `id`; Eloquent ожидает его по умолчанию. Для нестандартного ключа это можно задать явно:

```php
protected $primaryKey = 'key';
```

При UUID или другом строковом ключе также указывают:

```php
public $incrementing = false;
protected $keyType = 'string';
```

В текущей модели HelpMeIn это не требуется: у `users`, `teacher_student_relationships` и history есть обычный numeric `id`.

### Timestamps и append-only history

Обычная Eloquent model ожидает `created_at` и `updated_at` и автоматически выставляет их при создании и обновлении. Если timestamps отсутствуют полностью, можно отключить это ожидание:

```php
public $timestamps = false;
```

`teacher_student_status_history` устроена точнее: у события есть `created_at`, но нет `updated_at`. Поэтому реальная model содержит:

```php
class TeacherStudentStatusHistoryEvent extends Model
{
    public const UPDATED_AT = null;
}
```

```text
history event
↓
добавился один раз
↓
прошлое не переписывается
```

Это выражает архитектурное правило append-only. Отсутствие `updated_at` само по себе не запрещает `UPDATE` в PostgreSQL: защита от нежелательного изменения остаётся обязанностью application logic и, при необходимости, отдельного database rule.

## Mass assignment: Fillable, Hidden, validation и authorization

Mass assignment — создание или обновление model массивом attributes, например `Model::create($data)`. Чтобы случайно не записать поля, которые не должны приходить из request, Eloquent использует allow-list `$fillable`:

```php
protected $fillable = [
    'teacher_id',
    'student_id',
    'activity_status',
];
```

Альтернатива — deny-list `$guarded`, например `protected $guarded = ['is_admin'];`. `fillable` перечисляет разрешённые поля и для request-driven CRUD обычно читается безопаснее: новый attribute не станет mass-assignable случайно. В HelpMeIn выбран именно этот подход.

В HelpMeIn используется новый attribute-синтаксис Laravel 13:

```php
use Illuminate\Database\Eloquent\Attributes\Fillable;
use Illuminate\Database\Eloquent\Attributes\Hidden;

#[Fillable(['name', 'surname', 'email', 'password', 'phone', 'address', 'photo'])]
#[Hidden(['password', 'two_factor_secret', 'two_factor_recovery_codes', 'remember_token'])]
class User extends Authenticatable
{
    // ...
}
```

`#[Fillable(...)]` и `#[Hidden(...)]` — PHP attributes: metadata, прикреплённые к классу. Laravel читает эти metadata и применяет ту же идею, что обычные `$fillable` и `$hidden`. Свойства удобны, когда нужно быстро увидеть настройку рядом с телом класса; attribute-синтаксис собирает настройки декларативно над классом. В одном проекте лучше придерживаться уже выбранного стиля.

`Hidden` не запрещает чтение поля из model и не является security boundary. Он исключает attribute из обычной serialization, например не позволяет случайно отдать `password` через `toArray()` или JSON response.

| Механизм | Вопрос, на который отвечает |
|---|---|
| Validation | Корректны ли входные данные? |
| Authorization | Имеет ли текущий пользователь право выполнить действие? |
| Fillable | Разрешено ли это поле для mass assignment? |
| Hidden | Следует ли показывать поле при serialization? |

Они дополняют друг друга: `fillable` не заменяет validation или authorization.

## CRUD уже есть в базовой Model

`Illuminate\Database\Eloquent\Model` уже даёт стандартные операции, поэтому собственные CRUD-методы не нужны, пока не появилась отдельная business responsibility:

```php
TeacherStudentRelationship::create($attributes);
TeacherStudentRelationship::find(1);
TeacherStudentRelationship::where('teacher_id', $teacherId)->get();

$relationship->save();
$relationship->update(['note' => 'Созвон по пятницам']);
$relationship->delete();
```

`create()` и `update([...])` используют mass assignment, поэтому зависят от `Fillable`. `save()` сохраняет текущее состояние конкретного object. Когда операция должна одновременно изменить relationship и создать history event, этого набора методов недостаточно как архитектурного описания: следующий шаг — отдельный Service / Use Case и transaction.

## Casts: мост между PostgreSQL и PHP

Casts не меняют тип колонки в БД. Они говорят Eloquent, какой PHP value/object нужно дать коду при чтении attribute и как подготовить его к записи.

```text
PostgreSQL type / value
↓
Eloquent cast
↓
PHP type / object
```

В реальной `TeacherStudentRelationship`:

```php
protected function casts(): array
{
    return [
        'activity_status' => ActivityStatus::class,
        'started_at' => 'datetime',
        'ended_at' => 'datetime',
    ];
}
```

Datetime cast обычно даёт объект `Carbon`, расширяющий PHP `DateTime`. Поэтому с моментом времени можно работать предметно:

```php
$relationship->started_at?->addDays(7);
$relationship->started_at?->isPast();
$relationship->started_at?->diffForHumans();
$relationship->started_at?->timezone('Europe/Moscow');
```

PostgreSQL `timestamptz` хранит абсолютный момент; Carbon удобно показывает этот момент в timezone, нужной application или пользователю. `timezone(...)` меняет представление объекта, а не переписывает сам факт времени в database.

### Enum cast

`ActivityStatus` уже разобран в [[2. PHP Base#PHP enums: фиксированные значения|PHP Base]]:

```php
enum ActivityStatus: string
{
    case Active = 'active';
    case Paused = 'paused';
}
```

Для backed enum Eloquent при чтении преобразует scalar value в enum case:

```text
PostgreSQL 'active'
↓
Eloquent enum cast
↓
ActivityStatus::Active
```

При записи действует обратный путь:

```text
ActivityStatus::Paused
↓
Eloquent
↓
'paused'
↓
PostgreSQL
```

Поэтому код model layer сравнивает статус с case, а не со строкой:

```php
$relationship->activity_status === ActivityStatus::Active;
```

PHP enum защищает application layer от произвольных значений. PostgreSQL `CHECK (activity_status IN ('active', 'paused'))` защищает database, включая записи не через Eloquent. В HelpMeIn сознательно используется:

```text
PHP backed enum
+
PostgreSQL varchar
+
CHECK constraint
```

Для одного reusable status в PostgreSQL возможны ещё два варианта:

| Вариант | Плюс | Компромисс |
|---|---|---|
| `varchar` + `CHECK` | Простая migration, правило видно рядом с таблицей. | Повторяющийся набор значений нужно синхронизировать между таблицами. |
| PostgreSQL `ENUM` | Тип и допустимые values принадлежат самой БД. | Изменение набора values требует отдельного DB-level type migration. |
| PostgreSQL `DOMAIN` | Можно переиспользовать базовый type и constraints в нескольких колонках. | Реже встречается в Laravel-проектах; добавляет отдельный уровень DB-абстракции. |

Архитектуру HelpMeIn сейчас не меняем: выбран первый вариант. Native PostgreSQL types — отдельная тема, не повод преждевременно усложнять текущую модель.

## Relations: FK в БД и навигация в PHP

Foreign key существует на уровне PostgreSQL и обеспечивает integrity. Eloquent relation существует на уровне PHP и позволяет пройти от одного Model object к другому.

```php
$relationship->teacher_id; // scalar attribute, например 12
$relationship->teacher;    // related User object
```

Это разные вещи: `teacher_id` — значение колонки текущей строки, `teacher` — результат relation. Методы relations возвращают реальные объекты классов из `Illuminate\Database\Eloquent\Relations`:

```php
public function teacher(): BelongsTo
public function statusHistory(): HasMany
```

Relation object умеет строить query, поэтому на него можно накладывать constraints. Например, method может вернуть `hasMany(...)->where(...)`; фактические records будут получены только при выполнении query.

### `belongsTo`: relationship принадлежит User

В `TeacherStudentRelationship` есть две ссылки на `users.id`:

```php
public function teacher(): BelongsTo
{
    return $this->belongsTo(User::class, 'teacher_id');
}

public function student(): BelongsTo
{
    return $this->belongsTo(User::class, 'student_id');
}
```

```text
teacher_student_relationships.teacher_id = users.id
teacher_student_relationships.student_id = users.id
```

Полная форма метода — `belongsTo(User::class, 'teacher_id', 'id')`. Третий аргумент обычно не пишут: Laravel берёт primary key target model, то есть `id`.

### `hasMany`: User имеет много relationships

С другой стороны той же physical FK-связи `User` определяет:

```php
public function teacherRelationships(): HasMany
{
    return $this->hasMany(TeacherStudentRelationship::class, 'teacher_id');
}

public function studentRelationships(): HasMany
{
    return $this->hasMany(TeacherStudentRelationship::class, 'student_id');
}
```

SQL-смысл `teacherRelationships()`:

```sql
SELECT *
FROM teacher_student_relationships
WHERE teacher_id = current_user_id;
```

```text
User
↓ hasMany
TeacherStudentRelationship

TeacherStudentRelationship
↓ belongsTo
User
```

Это одна FK-связь, рассмотренная с двух направлений. В обычной терминологии `User → many relationships` — one-to-many, а `relationship → one User` — many-to-one. В Eloquent им соответствуют `hasMany()` и `belongsTo()`.

### История статусов

```text
TeacherStudentRelationship
↓ hasMany
TeacherStudentStatusHistoryEvent

TeacherStudentStatusHistoryEvent
├── belongsTo → TeacherStudentRelationship
└── belongsTo → User (changedBy)
```

Реальные методы моделей:

```php
// TeacherStudentRelationship
public function statusHistory(): HasMany
{
    return $this->hasMany(TeacherStudentStatusHistoryEvent::class, 'relationship_id');
}

// TeacherStudentStatusHistoryEvent
public function relationship(): BelongsTo
{
    return $this->belongsTo(TeacherStudentRelationship::class, 'relationship_id');
}

public function changedBy(): BelongsTo
{
    return $this->belongsTo(User::class, 'changed_by');
}
```

History event не заменяет основной `activity_status` relationship: первая запись отражает текущее состояние, а history хранит последовательность причин и изменений.

### `hasOne` и `belongsToMany`

`hasOne()` означает, что одна model имеет не более одной связанной записи. В текущей модели HelpMeIn подходящий реальный use case пока не зафиксирован, поэтому искусственно добавлять relation не нужно:

```php
public function profile(): HasOne
{
    return $this->hasOne(Profile::class);
}
```

`belongsToMany()` описывает many-to-many через промежуточную table: много users ↔ много roles/groups/tags. Такая таблица обычно называется **pivot table** и содержит как минимум два FK.

`teacher_student_relationships` не является простой pivot table: у неё свой `id`, `activity_status`, `custom_name`, `note`, `started_at`, `ended_at` и history. Поэтому она стала полноценной domain entity с собственной `Model`, а не просто технической строкой между `users`.

Если промежуточной записи достаточно только для двух FK, обычно хватает обычного pivot. Если у неё появился собственный жизненный цикл, attributes и business rules, нужна отдельная Model; Laravel также позволяет делать custom Pivot Model для случаев, где relation остаётся many-to-many, но pivot требует собственного поведения. Это advanced-деталь до практического use case.

## Relation method и relation property

Скобки меняют смысл:

```php
$relationship->teacher(); // BelongsTo relation object / relation query
$relationship->teacher;   // related User object или null
```

Первый вариант нужен, когда строится или меняется relation query. Второй — когда нужен уже загруженный объект. Аналогично:

```php
$user->teacherRelationships(); // HasMany relation object
$user->teacherRelationships;   // Eloquent Collection моделей
```

## Lazy loading, eager loading и N+1

При первом обращении к `$relationship->teacher` relation может ещё не быть загружен. Тогда Eloquent выполнит SQL query и сохранит результат внутри **текущего instance Model**. Это relation cache конкретного объекта, а не глобальный cache приложения.

```text
$relationship->teacher
↓ relation ещё не loaded
SQL query
↓
User object сохранён в relation cache этого $relationship
```

Это называется lazy loading. Оно удобно для одной записи, но опасно в цикле:

```php
$user->teacherRelationships
    ->map(fn ($relationship) => $relationship->student);
```

Без предварительной загрузки может получиться:

```text
1 query relationships
+
N queries students
=
N+1 queries
```

Eager loading заранее сообщает Eloquent, какие relations нужны:

```php
$user = User::with('teacherRelationships.student')->find(1);
```

Это nested eager loading: сначала загружается `teacherRelationships`, затем их `student`. Количество запросов не растёт линейно от числа relationships. Exact SQL и число запросов полезно смотреть при реальном endpoint; `with()` не заменяет измерение и осознанный выбор data shape.

## Collections

`hasMany` property возвращает Eloquent Collection моделей. Это Laravel-коллекция с удобными operations:

```php
$user->teacherRelationships
    ->pluck('student_id');

$user->teacherRelationships
    ->map(fn ($relationship) => $relationship->student);
```

`pluck('student_id')` возвращает collection scalar IDs. `map(...)` строит новую collection из результата callback. Во втором примере students стоит eager-load, иначе `map` может скрыть N+1.

## Tinker и Artisan workflow

Tinker — интерактивная PHP/Laravel REPL для исследования реальных данных и models:

```bash
php artisan tinker
```

```php
$user = User::find(1);

$user->teacherRelationships;

$user->teacherRelationships
    ->pluck('student_id');

$user->teacherRelationships
    ->map(fn ($r) => $r->student);

$user = User::with('teacherRelationships.student')->find(1);
```

Последняя строка показывает eager-loading variant. Если `find(1)` вернёт `null`, дальше нельзя обращаться к relations без явной проверки: это не ошибка Eloquent, а отсутствие row с таким `id`.

Минимальный terminal workflow вокруг models и schema:

```bash
php artisan make:model TeacherStudentRelationship
php artisan make:migration create_teacher_student_relationships_table
php artisan migrate
php artisan migrate:status
php artisan migrate:rollback
php artisan tinker
php artisan config:clear
```

`make:model -m` создаёт model вместе с migration. Флаги factory, seeder, policy или controller существуют, но их стоит добавлять только когда соответствующий artefact нужен: factories и seeders ещё впереди. Для обзора уже созданной model также полезна команда `php artisan model:show TeacherStudentRelationship`.

## Model, enum, DTO и Service / Use Case

| Конструкция | Роль в HelpMeIn |
|---|---|
| Model | Persisted entity / ORM: `TeacherStudentRelationship`. |
| Enum | Фиксированные допустимые значения: `ActivityStatus`. |
| DTO | Перенос явно собранных данных между слоями, если это оправдано. |
| Service / Use Case | Выполняет business operation, например изменение статуса и запись history event. |

Model не должна становиться контейнером всех сложных сценариев. Изменение activity status затрагивает минимум две таблицы и должно быть одной атомарной бизнес-операцией — это следующий практический шаг.

## Relation types: ориентир на будущее

| Relation class | Когда нужна |
|---|---|
| `BelongsTo` | Текущая запись хранит FK на одну target model. |
| `HasOne` | Одна model имеет одну связанную запись. |
| `HasMany` | Одна model имеет много связанных записей. |
| `BelongsToMany` | Many-to-many через pivot table. |
| `MorphOne` / `MorphMany` | Polymorphic one-to-one / one-to-many: один child type может принадлежать разным parent types. |
| `MorphTo` | Обратная сторона polymorphic relation. |
| `MorphToMany` / `MorphedByMany` | Polymorphic many-to-many через pivot. |

Полноценно применены и проверены сейчас только `BelongsTo` и `HasMany`. Morph relations и сложные custom pivot internals — TODO до появления реальной продуктовой необходимости.

| `teacher()` / `teacher` | Relation query object / related model. |
| Lazy / eager loading | Query по обращению / заранее запланированная загрузка. |
| Почему `TeacherStudentRelationship` не pivot? | У неё самостоятельные attributes, lifecycle и history. |

Формулировка для повторения: **Eloquent Model не заменяет PostgreSQL: она превращает строки базы в PHP-объекты, а relations дают объектную навигацию по foreign keys. Для сложной операции model methods объединяются в явный use case и transaction.**

## Для проверки знаний

### Термины

- Eloquent Model, ORM, hydration, attribute, cast, mass assignment.
- `Fillable`, `Hidden`, serialization, `created_at`, `updated_at`, append-only.
- Foreign key, `BelongsTo`, `HasMany`, pivot table, Eloquent Collection.
- Lazy loading, eager loading, N+1, relation object и relation property.

### Что нужно уметь объяснить

- Чем database row, Eloquent Model и DTO отличаются по ответственности.
- Чем `$relationship->teacher_id`, `$relationship->teacher()` и `$relationship->teacher` отличаются друг от друга.
- Почему `User::teacherRelationships()` и `TeacherStudentRelationship::teacher()` описывают одну FK с разных сторон.
- Как enum cast преобразует PostgreSQL `'active'` в `ActivityStatus::Active` и почему этого недостаточно без PostgreSQL `CHECK`.
- Почему `TeacherStudentRelationship` — самостоятельная domain entity, а не обычный pivot.
- Где возникает N+1 в обходе students и как nested `with()` меняет ситуацию.

### Типичные ошибки

- Считать relation PHP-заменой foreign key или ожидать, что relation создаёт constraint в PostgreSQL.
- Считать `Hidden` validation или authorization, а `Fillable` защитой всех доступов к полю.
- Сравнивать enum cast attribute со строкой либо считать отсутствие `updated_at` DB-запретом на `UPDATE`.
- Вызывать relation в цикле и не замечать N+1.
- Называть любую промежуточную таблицу pivot, игнорируя её собственные attributes и lifecycle.

### Мини-практика

- Для `TeacherStudentRelationship` с `teacher_id = 12` объясни разницу между `teacher_id`, `teacher()` и `teacher`; укажи, где выполняется query при lazy loading.
- МикроТЗ: напиши method `statusHistory(): HasMany` и обратный `relationship(): BelongsTo` для истории статусов. Критерии: `relationship_id` — FK, return types корректны, имена target models и foreign keys соответствуют HelpMeIn.
- Найди N+1 в обходе `$user->teacherRelationships->map(fn ($r) => $r->student)` и перепиши первоначальный query с nested eager loading.
