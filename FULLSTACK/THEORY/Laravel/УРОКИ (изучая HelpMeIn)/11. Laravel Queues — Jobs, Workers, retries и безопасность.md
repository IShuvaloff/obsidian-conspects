# Laravel Queues: Jobs, Workers, retries и безопасность

#laravel #queue #job #worker #database #reliability

> [!summary]
> Queue переносит медленную или внешнюю работу из HTTP request в отдельную обработку. В HelpMeIn `SendStudentInvitationMail` кладётся в database queue, Worker позже проверяет актуальное invitation и отправляет письмо. Queue делает request короче, но не даёт автоматически exactly-once delivery: для неё нужны idempotency, актуальная проверка данных и понятная стратегия ошибок.

## Зачем это нужно

Создание invitation должно быстро вернуть HTTP response. Рендеринг и доставка email зависят от mail transport и могут быть медленными или временно недоступными. Если выполнить их synchronously, пользователь ждёт внешнюю систему, а ошибка сети ломает основной request.

```text
HTTP request                         отдельный Worker
create invitation                    берёт Job
↓                                   ↓
dispatch Job → jobs table → handle() → Mail transport
↓
response пользователю
```

Это не «SQL-задача PostgreSQL»: database driver использует PostgreSQL как durable storage очереди, но PHP Worker выполняет `handle()`. Архитектура, retry и transaction semantics сверены с [Laravel Queues 13](https://laravel.com/docs/13.x/queues).

## Короткая карта

| Термин | Роль |
|---|---|
| Job | Класс с отложенной работой и данными для неё. |
| Queue | Логический поток задач, например `default`. |
| Connection / driver | Где очередь хранится и как с ней работать: `database`, Redis, SQS и др. |
| Worker | Долгоживущий CLI-процесс, который забирает Job и вызывает `handle()`. |
| `ShouldQueue` | Контракт: этот объект нужно поставить в queue, а не выполнить в текущем request. |
| `Queueable` | Trait с fluent-настройками connection, queue, delay и after-commit behaviour. |

Database driver HelpMeIn хранит ожидающие задания в `jobs`. `failed_jobs` — журнал окончательно неудачных Jobs; `job_batches` нужен только для batch API, а не для каждой одиночной Job.

## Жизненный цикл Job

Реальный Job имеет такую форму:

```php
class SendStudentInvitationMail implements ShouldQueue, ShouldBeEncrypted
{
    use Queueable;

    public int $tries = 5;

    public function backoff(): array
    {
        return [60, 300, 600, 1800];
    }

    public function __construct(
        public int $invitationId,
        public string $plainToken,
    ) {}

    public function handle(): void
    {
        // Worker вызывает этот method позднее.
    }
}
```

```text
dispatch(new SendStudentInvitationMail(...))
↓ serialisation payload
queue connection / database driver
↓ INSERT row в jobs
Worker резервирует row
↓
Laravel container вызывает handle()
├── normal return → Job удаляется из jobs
└── exception → retry, release или final failure
```

`handle(): void` не вызывается controller вручную. Его вызывает Worker через Laravel container, поэтому `handle()` может также получать resolvable dependencies в параметрах. Normal return в текущем Job означает успех; ранние `return` для отсутствующего, просроченного или уже неактуального invitation — сознательный no-op, а не подтверждение доставки письма.

### Что лежит в `jobs`

Database row содержит служебные поля очереди: connection/queue, attempts, время доступности, reservation и JSON payload. В payload есть видимая оболочка — например UUID и имя Job. Когда Job implements `ShouldBeEncrypted`, Laravel шифрует сериализованную команду в payload с application encrypter и `APP_KEY`; это не делает невидимыми все outer metadata. Поэтому token нельзя писать в logs или exception message даже при encrypted Job.

## Практика HelpMeIn

Фактически проверенный учебный сценарий:

```bash
php artisan queue:work --once -v
```

При `QUEUE_CONNECTION=database` Job был поставлен в PostgreSQL, Worker обработал его с `DONE`, запись исчезла из `jobs`, а `MAIL_MAILER=log` сформировал HTML письма для проверки в браузере.

Это подтверждает постановку, обработку и рендеринг письма. Это **не** подтверждает SMTP-доставку, получение сообщения реальным ящиком, spam policy или поведение конкретного email client.

Полезная диагностика:

```bash
php artisan queue:work --once -v
php artisan queue:work --tries=3 --timeout=60
php artisan queue:failed
php artisan queue:retry <id-or-uuid>
php artisan queue:retry all
php artisan queue:flush
php artisan queue:restart
```

`queue:flush` удаляет записи failed jobs и применяется осознанно, не как первая реакция на проблему. Для local inspection также полезно посмотреть `jobs` / `failed_jobs` через SQL или DB client.

## Retries: попытки, задержки и пределы

`$tries = 5` задаёт максимум **пяти запусков** Job. Между первой и второй, второй и третьей, третьей и четвёртой, четвёртой и пятой попытками есть четыре интервала — поэтому массив ниже содержит четыре значения:

```text
attempt 1 → exception
wait 60 s
attempt 2 → exception
wait 300 s
attempt 3 → exception
wait 600 s
attempt 4 → exception
wait 1800 s
attempt 5 → exception → failed
```

```php
public int $tries = 5;

public function backoff(): array
{
    return [60, 300, 600, 1800];
}
```

`backoff` можно задать property с одним фиксированным числом или method, возвращающим число/массив. Если число retries превышает длину массива, Laravel использует последнее значение массива для оставшихся ожиданий. Retry имеет смысл для transient failure — timeout сети, временная ошибка SMTP. Неверный адрес, removed route или нарушенный invariant обычно не становятся правильными от пяти повторов.

`retryUntil(): DateTimeInterface` — альтернативный временной предел: пытаться до конкретного момента, а не считать attempts. Job также может иметь `$timeout`; worker option `--timeout` должен быть короче connection `retry_after`. Иначе worker ещё выполняет Job, а очередь сочтёт reservation истёкшим и выдаст ту же Job второму Worker — источник параллельных дублей.

Не надо ловить exception только ради `return`: Worker тогда посчитает Job успешной и не сделает retry/failed record. Catch оправдан, когда ошибка действительно обработана или её переводят в другой осмысленный outcome; иначе exception нужно дать подняться.

## Актуальные данные, idempotency и модели

Job HelpMeIn передаёт `invitationId`, а не готовую Eloquent Model. В `handle()` он снова читает record и проверяет `canBeAccepted()` и hash token.

```text
Job поставлен в queue
↓ время проходит
invitation могла истечь / отмениться / измениться
↓
Worker заново читает БД
↓
решает, имеет ли действие смысл сейчас
```

Это особенно важно, потому что queue даёт практическую семантику **at least once**: внешнее действие иногда может быть повторено после сбоя в неудачный момент. Laravel не может автоматически гарантировать exactly-once отправку во внешний SMTP. Idempotency означает: повторное выполнение либо безопасно, либо распознаётся как уже совершённое.

Trait `SerializesModels` полезен, когда Job/Mailable всё-таки хранит Model: при сериализации Laravel заменяет её идентификатором, а при обработке восстанавливает Model из БД. Это не snapshot business state и не отменяет необходимость перепроверять актуальный status. В текущей Job скалярный ID делает этот факт явным.

## Transaction и `afterCommit()`

Если Job dispatch-ится внутри незавершённой DB transaction, Worker потенциально может начать её до commit: он не увидит row или увидит старое состояние. Если transaction затем rollback, поставленная Job может относиться к несуществующему business event.

```php
DB::transaction(function () use ($job) {
    // create invitation
    dispatch($job)->afterCommit();
});
```

`afterCommit()` просит отложить постановку до успешного commit; такой же default можно включить в queue connection config. При rollback callback не будет dispatch-нут. Когда transaction нет, Job ставится обычным образом: ждать commit просто не от чего.

Текущий `CreateStudentInvitation` уже работает в transaction, но orchestration «создать invitation + dispatch после commit» пока **не подключён к controller**. Это следующий архитектурный шаг, не описание завершённой функциональности.

## `dispatch()` в Tinker и `PendingDispatch`

`SomeJob::dispatch(...)` обычно возвращает `PendingDispatch`: fluent object, который позволяет дописать `->onQueue()`, `->delay()` или `->afterCommit()`. Его destructor завершает dispatch, когда объект перестаёт быть нужен. В интерактивном Tinker отображаемый результат может удерживаться REPL дольше, чем ожидается, поэтому нельзя делать вывод о queue только по тому, что printed `PendingDispatch` ещё виден.

Для явной немедленной постановки при ручной диагностике удобен:

```php
Bus::dispatch(new SendStudentInvitationMail($id, $token));
```

Оба пути используют bus/queue; различие — в fluent deferred wrapper и моменте финализации dispatch, а не в «разных очередях».

## Worker в development и production

`queue:work` — долгоживущий процесс. Он загружает Laravel один раз; после deployment обновленный код не появится в уже запущенном Worker сам. Команда `php artisan queue:restart` даёт Workers сигнал корректно завершиться после текущей Job, после чего process manager запускает свежий экземпляр.

В development можно запускать Worker в отдельном terminal или `--once`. В production он должен работать под Supervisor, systemd или другим process manager: перезапускать упавший процесс, хранить logs и контролировать число Workers. Database queue может жить в той же PostgreSQL database, Redis/SQS — во внешнем broker; требования к latency, availability и monitoring от этого меняются, но model Job остаётся похожей.

## Границы и связи

Queue не заменяет HTTP validation, Policy, transaction и constraints. Она переносит execution во времени, поэтому требует большего внимания к stale state и ошибкам. ## Для проверки знаний

### Термины
- Job, queue, connection, driver, Worker, `ShouldQueue`, `Queueable`.
- `jobs`, `failed_jobs`, retry, backoff, timeout, `retry_after`.
- `ShouldBeEncrypted`, idempotency, at-least-once, `afterCommit`.

### Что нужно уметь объяснить
- Почему database queue не является выполнением SQL-заданий PostgreSQL.
- Почему Job в HelpMeIn повторно читает invitation, а не доверяет старому object state.
- Почему `timeout` должен быть меньше `retry_after`.
- Почему `MAIL_MAILER=log` не тестирует доставку.

### Типичные ошибки
- Глотать exception и тем самым отключать retries.
- Считать очереди exactly-once механизмом.
- Dispatch-ить Job из transaction без анализа after-commit semantics.

### Мини-практика
- Нарисуй timeline для `$tries = 3` и `backoff() => [10, 60]`.
- Объясни, что должно произойти с Job, если invitation истекло до запуска Worker.
