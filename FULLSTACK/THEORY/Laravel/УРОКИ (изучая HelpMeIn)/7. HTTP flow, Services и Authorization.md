# HTTP flow, Services и Authorization: смена статуса в HelpMeIn

#laravel #http #inertia #service #authorization #transaction

> [!summary]
> Одна кнопка Vue не «меняет поле в БД напрямую». В HelpMeIn она запускает HTTP use case: Laravel находит relationship, проверяет input и право actor, затем service атомарно меняет current status и добавляет history event. В конце redirect возвращает Inertia к свежим данным страницы.

## Зачем это нужно

До этого момента отдельные части уже существуют: [[6. Eloquent Models и Relations|models и relations]], [[3. Сервисы и фасады|Service Container]], PostgreSQL constraints и enum. Но архитектура становится понятной только тогда, когда видно, как они работают вместе в одной пользовательской операции.

Реальный use case HelpMeIn: teacher или admin ставит relationship на паузу. Система должна изменить `TeacherStudentRelationship.activity_status`, создать `TeacherStudentStatusHistoryEvent` и не позволить outsider или student выполнить это действие.

```text
Vue / Browser
↓
HTTP PATCH request
↓
Route
↓
auth + verified middleware
↓
Route Model Binding
↓
FormRequest
↓
Controller
↓
Gate / Policy
↓
Service / Use Case
↓
Eloquent Models / Relations
↓
PostgreSQL
↓
redirect / response
↓
Inertia refresh
```

Смысл каждого слоя проще удерживать в отдельной схеме:

```text
Route
→ куда направить HTTP request

FormRequest
→ корректны ли входные данные?

Controller
→ orchestration HTTP-layer

Policy
→ имеет ли actor право?

Service / Use Case
→ что должна сделать система?

Model / Eloquent
→ как работать с persisted entities?

PostgreSQL
→ где и с какими гарантиями хранятся данные?
```

Это не полный курс по routing, Inertia или authorization. Урок фиксирует один проверенный вертикальный срез HelpMeIn; детали остаются в TODO.

## Короткая карта use case

```text
PATCH /teacher-student-relationships/1/activity-status
{
  activity_status: 'paused',
  comment: 'Пауза в обучении'
}
↓
TeacherStudentRelationship #1
↓
authorization: admin или teacher этой relationship
↓
ChangeActivityStatus::execute(...)
↓
UPDATE teacher_student_relationships
+
INSERT teacher_student_status_history
↓
redirect back
```

| Слой | Конкретная роль в HelpMeIn |
|---|---|
| Route | Сопоставляет PATCH URL с `updateActivityStatus`. |
| FormRequest | Принимает только допустимый `ActivityStatus` и optional comment. |
| Controller | Собирает HTTP context и вызывает use case. |
| Policy | Разрешает admin или teacher этой relationship. |
| Service | Сохраняет статус и history как одну операцию. |
| PostgreSQL | Хранит rows, FK и `CHECK` constraints. |

### Vue начинает цепочку

Текущий учебный probe в `Clients.vue` отправляет Inertia request так:

```ts
router.patch('/teacher-student-relationships/1/activity-status', {
    activity_status: 'active',
    comment: 'тестовый UI-change',
});
```

`router.patch(...)` не меняет props локально «в обход backend»: он отправляет HTTP PATCH. Захардкоженный `1` и тестовый comment нужны только для текущей проверки цепочки. В реальном UI relationship будет выбрана из page data, а состояние формы и errors станут отдельным следующим шагом.

## Route: куда приходит PATCH

В `routes/web.php` текущий маршрут находится внутри group `auth`, `verified`:

```php
Route::patch(
    'teacher-student-relationships/{relationship}/activity-status',
    [
        TeacherStudentRelationshipController::class,
        'updateActivityStatus',
    ]
)->name('teacher-student-relationships.activity-status.update');
```

`PATCH` выражает частичное изменение существующего ресурса: здесь меняется activity status relationship, а не создаётся новая relationship. `{relationship}` — URL parameter; например `/teacher-student-relationships/1/activity-status` передаёт значение `1` дальше в Laravel.

`name(...)` даёт route стабильное логическое имя. Named route полезен, когда URL меняется, а backend/tests/route helper могут продолжать ссылаться на intention, а не копировать путь строкой.

Маршрут остаётся в `web.php`: это session-based Inertia endpoint веб-приложения. `web` middleware group даёт session и CSRF protection; сам факт, что Vue отправляет HTTP request, не делает endpoint API. `api.php` нужен для отдельной stateless API-границы, а не для каждой мутации из браузерного UI.

`auth` не пропускает неаутентифицированного пользователя, а `verified` добавляет требование verified account. Они не решают правило «может ли именно этот User менять именно эту relationship» — это работа Policy ниже.

## Route Model Binding: URL превращается в Model

В текущем маршруте parameter называется `{relationship}`, а controller принимает:

```php
TeacherStudentRelationship $relationship
```

Laravel сопоставляет имя parameter с аргументом и type hint с Eloquent Model:

```text
URL
{relationship} = 1
↓
parameter name + Model type hint
↓
Eloquent/database lookup
↓
готовый TeacherStudentRelationship object
↓
Controller
```

Это не дополнительный HTTP/API request. Laravel выполняет внутренний Eloquent/database query в рамках уже идущего request. Если record не найден, Laravel отдаёт 404 до запуска controller и business code. Поэтому controller получает либо реальную model, либо вообще не запускается.

## FormRequest: входная граница HTTP input

`UpdateTeacherStudentActivityStatusRequest` отделяет правила input от controller:

```php
class UpdateTeacherStudentActivityStatusRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true;
    }

    public function rules(): array
    {
        return [
            'activity_status' => [
                'required',
                Rule::enum(ActivityStatus::class),
            ],
            'comment' => [
                'nullable',
                'string',
            ],
        ];
    }
}
```

`Rule::enum(ActivityStatus::class)` проверяет, что incoming scalar value соответствует одному из cases enum. Только после validation controller безопасно превращает строку в case:

```php
$validated = $request->validated();
$activityStatus = ActivityStatus::from($validated['activity_status']);
```

`comment` optional: после validation ключ может отсутствовать или иметь `null`. Поэтому безопасна форма:

```php
$validated['comment'] ?? null
```

Lifecycle FormRequest:

```text
request приходит
↓
FormRequest создаётся
↓
authorize()
↓
validation
↓
ошибка → Controller не запускается
успех → Controller выполняется
```

В текущей request `authorize()` возвращает `true`, потому что authorization явно видна ниже в controller через `Gate::authorize()`. FormRequest может быть и альтернативной HTTP entry point для authorization — это сравнение будет дальше.

## Текущий actor: `$request->user()`

На маршруте с `auth` middleware `$request->user()` получает current authenticated `User` из session/auth context:

```php
$changedBy = $request->user();
```

Клиент не должен присылать actor как business fact:

```text
не доверять клиенту:
changed_by = 7

backend определяет сам:
$request->user()
```

Иначе пользователь мог бы вручную отправить request с чужим `changed_by`. В controller этот User одновременно участвует в authorization и записывается как автор history event.

## Controller: orchestration HTTP-layer

Controller не обязан быть местом всей business logic. Его задача — перевести HTTP context в application use case и сформировать HTTP response. В реальном `TeacherStudentRelationshipController` это выглядит так:

```php
public function updateActivityStatus(
    UpdateTeacherStudentActivityStatusRequest $request,
    TeacherStudentRelationship $relationship,
    ChangeActivityStatus $changeActivityStatus,
) {
    Gate::authorize('updateActivityStatus', $relationship);

    $validated = $request->validated();

    $activityStatus = ActivityStatus::from($validated['activity_status']);

    $changeActivityStatus->execute(
        $relationship,
        $activityStatus,
        $request->user(),
        $validated['comment'] ?? null,
    );

    return back();
}
```

```text
Controller
↓
получил HTTP context
↓
подготовил input
↓
проверил authorization
↓
вызвал application use case
↓
сформировал HTTP response
```

Controller связан с delivery layer: он знает о Request, redirect, status codes, route context и validation response. Service ниже не должен зависеть от конкретного HTTP request.

## Service / Use Case: одна законченная операция

`app/Services/TeacherStudent/ChangeActivityStatus.php` описывает business operation:

```text
изменить current activity status
+
создать history event
+
сделать обе операции атомарно
```

Service не равен «Eloquent query». Eloquent отвечает, **как** читать и сохранять persisted data. Use Case отвечает, **что** должна сделать система, в каком порядке и какие business invariants не должны нарушиться.

Для текущего HelpMeIn полезный pattern — **one use case → one class**:

```text
ChangeActivityStatus
→ одна законченная business operation
→ обычно один public execute()

EndRelationship
AcceptInvitation
→ отдельные законченные operations
```

Private helper methods внутри такого класса нормальны. Правило не механическое «только один метод», а проверка ответственности. Широкий `TeacherStudentService` возможен, но легко превращается в God Service:

```text
TeacherStudentService
├── changeStatus()
├── acceptInvitation()
├── endRelationship()
├── deleteSomething()
└── sendEmail()
```

Если причины изменений у этих методов разные, им лучше стать отдельными use cases.

### Service Container здесь

`ChangeActivityStatus` — concrete class. Laravel может auto-resolve-ить его по type hint controller без отдельного binding/provider:

```php
ChangeActivityStatus $changeActivityStatus
```

В Tinker удобно прямо запросить тот же class у container:

```php
$service = app(ChangeActivityStatus::class);
```

Это direct resolution через Service Container, а не альтернативный `new`. В normal controller code DI предпочтительнее, потому что dependency видна в method signature. Полная модель — в [[3. Сервисы и фасады|уроке о Service Container]].

## `DB::transaction()`: status и history вместе

Суть use case — не дать текущему status измениться без соответствующего history event. Поэтому реальный service оборачивает обе записи в `DB::transaction()`:

```php
public function execute(
    TeacherStudentRelationship $relationship,
    ActivityStatus $status,
    User $changedBy,
    ?string $comment = null,
): void {
    DB::transaction(function () use (
        $relationship,
        $status,
        $changedBy,
        $comment,
    ) {
        if ($relationship->activity_status === $status) {
            return;
        }

        $relationship->activity_status = $status;
        $relationship->save();

        $relationship->statusHistory()->create([
            'activity_status' => $status,
            'changed_by' => $changedBy->id,
            'comment' => $comment,
        ]);
    });
}
```

```text
BEGIN
↓
UPDATE teacher_student_relationships
↓
INSERT teacher_student_status_history
↓
COMMIT

exception
↓
ROLLBACK
```

Atomicity здесь означает: либо status и history event сохранены вместе, либо не сохранено ничего. Если `INSERT` history не удастся, transaction откатит уже выполненный `UPDATE`.

`lockForUpdate()` соответствует SQL `SELECT ... FOR UPDATE` и блокирует выбранные rows для конкурирующих изменений в transaction. В текущем service explicit row lock ещё не используется; concurrency и locking — будущая отдельная тема, особенно если один status могут менять одновременно из нескольких requests.

### No-op при том же status

```php
if ($relationship->activity_status === $status) {
    return;
}
```

UI может disable Save, когда status не менялся, но backend обязан защищать правило самостоятельно: UI можно обойти ручным HTTP request. Если state transition отсутствует, history event не создаётся — иначе история стала бы содержать дубликаты, не отражающие реального изменения.

### `statusHistory()->create()` и automatic FK

```php
$relationship->statusHistory()->create([
    'activity_status' => $status,
    'changed_by' => $changedBy->id,
    'comment' => $comment,
]);
```

Здесь не передают:

```php
'relationship_id' => $relationship->id
```

`HasMany` relation object уже знает parent model, foreign key `relationship_id` и parent key `id`, поэтому проставляет FK автоматически:

```text
$relationship->statusHistory()->create(...)
→ relation выставляет relationship_id

TeacherStudentStatusHistoryEvent::create(...)
→ relationship_id нужно передать вручную
```

Это практический критерий: FK можно не указывать вручную, когда create вызывают через relation, которая уже однозначно связывает child с parent.

## Authentication и Authorization

```text
Authentication
→ кто ты?

Authorization
→ что тебе разрешено?
```

Session authentication устанавливает current User, которого возвращает `$request->user()`. Но authenticated user не получает автоматически право менять любую relationship. Authorization отвечает на этот следующий вопрос.

### Policy: правило вокруг domain entity

`TeacherStudentRelationshipPolicy` хранит authorization rule для модели relationship:

```php
public function updateActivityStatus(
    User $user,
    TeacherStudentRelationship $relationship,
): bool {
    return $user->is_admin
        || $relationship->teacher_id === $user->id;
}
```

| Actor | Решение |
|---|---|
| Admin | allowed. |
| Teacher этой relationship | allowed. |
| Student этой relationship | denied. |
| Outsider | denied. |

Policy группирует rules вокруг model/domain entity. Это не UI-проверка, а server-side security decision.

### Gate: запрос решения у authorization system

Controller использует современный Laravel API:

```php
Gate::authorize(
    'updateActivityStatus',
    $relationship,
);
```

```text
Gate::authorize(...)
↓
authenticated User
↓
TeacherStudentRelationship
↓
Laravel находит Policy
↓
updateActivityStatus(...)
↓
true → continue
false → 403 Forbidden
```

В HTTP request actor уже известен auth system, поэтому его не передают в `Gate::authorize()`. В Tinker или tests actor выбирают явно:

```php
Gate::forUser($user)->allows(
    'updateActivityStatus',
    $relationship,
);
```

`forUser()` нужен именно там, где нет текущей authenticated HTTP session или нужно проверить правило для конкретного test user.

### Gate, Policy и `FormRequest::authorize()`

| Конструкция | Роль |
|---|---|
| Gate | Механизм запроса authorization decision. |
| Policy | Место, где хранится правило вокруг model. |
| `FormRequest::authorize()` | Один из возможных HTTP-layer entry points для authorization. |

Ту же проверку можно поместить в FormRequest:

```php
public function authorize(): bool
{
    return $this->user()->can(
        'updateActivityStatus',
        $this->route('relationship'),
    );
}
```

Для этого учебного use case выбран `Gate::authorize()` в controller: flow явно показывает шаг authorization между validated input и вызовом service. Это выбор читаемости текущей главы, а не единственно верный стиль.

### Backend security и UI

```text
UI
→ скрыть / disable button
→ UX

Backend Policy
→ реальная защита
→ security boundary
```

Пользователь может отправить HTTP request вручную или изменить frontend code в браузере. Поэтому UI permission check улучшает опыт, но никогда не заменяет Policy/Gate на backend.

## `return back()` и Inertia refresh

В конце controller возвращает:

```php
return back();
```

Это redirect response, а не отсутствие ответа. Для Inertia flow по смыслу выглядит так:

```text
PATCH
↓
operation succeeds
↓
redirect back
↓
GET current page
↓
fresh page data
```

Поэтому Network panel после PATCH может показать следующий GET. Browser/Inertia следует redirect и отображает заново полученные props; UI не должен вручную «угадывать» сохранённое server state.

## Практически проверенный сценарий

Во время практики HelpMeIn использовались users:

- `id=1` — admin и teacher этой relationship;
- `id=3` — student;
- `id=2` — outsider.

Практические HTTP-проверки дали такой результат:

```text
outsider
→ 403

student
→ 403

teacher
→ success
→ status updated
→ history event created
```

Повторный PATCH с тем же status проходит authorization, затем service обнаруживает same status, делает no-op и не добавляет duplicate history event.

`id=1` одновременно admin и teacher, поэтому эта конкретная проверка не изолирует admin override. Для него позже нужен отдельный admin user или automated feature test — это честное ограничение текущей практики.

### Первый history event

Первая history event была создана вручную через Tinker:

```text
ActivityStatus::Active
comment: «Начало обучения»
```

В production она должна создаваться автоматически вместе с relationship в одном transaction. Будущий use case выглядит так:

```text
AcceptInvitation
↓
DB::transaction
├── CREATE TeacherStudentRelationship
├── CREATE initial history event
└── mark invitation accepted
```

Он пока не реализуется: здесь важно увидеть, почему initial history — часть создания relationship, а не ручная post-action.

## Краткое резюме

| Вопрос | Короткий ответ |
|---|---|
| Зачем Route Model Binding? | Превращает URL parameter в найденный Model object или 404. |
| Зачем FormRequest? | Отделяет validation HTTP input от controller. |
| Что делает controller? | Orchestration request → use case → response. |
| Что делает Service? | Описывает завершённую business operation, а не одиночный query. |
| Зачем transaction? | Не даёт status измениться без history event. |
| Gate / Policy | Запрашивает решение / хранит правило вокруг model. |
| Почему `$request->user()`? | Actor берётся из auth context, не из client input. |
| Почему `relationship_id` не передаётся? | `statusHistory()` relation автоматически выставляет FK. |
| Зачем `return back()`? | Возвращает redirect; Inertia затем получает свежую страницу. |

Формулировка для повторения: **HTTP controller оркестрирует request, authorization и response; Service атомарно выполняет business use case; PostgreSQL хранит результат и защищает данные независимо от UI.**

## Для проверки знаний

### Термины

- HTTP route, PATCH, URL parameter, named route, Route Model Binding.
- FormRequest, validation, orchestration, authenticated actor.
- Service / Use Case, transaction, atomicity, no-op.
- Authentication, authorization, Gate, Policy, 403 Forbidden.
- Redirect response, Inertia refresh.

### Что нужно уметь объяснить

- Чем authentication отличается от authorization и почему `auth` middleware не заменяет Policy.
- Чем FormRequest отличается от controller, а controller — от Service / Use Case.
- Почему Route Model Binding — внутренний database lookup, а не отдельный HTTP API request.
- Почему Service не равен Eloquent query и зачем `DB::transaction()` для status + history.
- Почему `$relationship->statusHistory()->create()` не требует `relationship_id`, а прямой `TeacherStudentStatusHistoryEvent::create()` требует.
- Почему UI permission check недостаточна как защита.

### Типичные ошибки

- Принимать `changed_by` из тела request вместо получения current actor через `$request->user()`.
- Считать validation проверкой права доступа или считать authenticated user автоматически authorized.
- Создавать history event вне transaction либо создавать его при одинаковом status.
- Путать redirect response с отсутствием ответа и считать следующий GET в Network «лишним API-вызовом».
- Добавлять всю business logic в controller или собирать несвязанные operations в один God Service.

### Мини-практика

- Объясни по шагам, почему request от student с корректным `activity_status = paused` получает 403, а controller не вызывает `ChangeActivityStatus`.
- МикроТЗ: дополни `ChangeActivityStatus`, чтобы `statusHistory()->create()` записывал comment и автора. Критерии: используется relation create, `relationship_id` не передаётся вручную, оба изменения остаются внутри одной transaction.
- Предскажи, что произойдёт при PATCH с тем же status: какие проверки пройдут, какие SQL changes не должны появиться и почему.
