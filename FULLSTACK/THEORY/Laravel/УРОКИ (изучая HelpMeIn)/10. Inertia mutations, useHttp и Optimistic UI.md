# Inertia mutations, useHttp и Optimistic UI

#laravel #inertia #vue #http #optimistic-ui #error-handling

> [!summary]
> Смена `activity_status` — server-authoritative business operation: Laravel валидирует input, проверяет Policy и атомарно пишет status с history. Но UI может выбрать разный транспорт и UX: Inertia visit с redirect и fresh props или request-oriented `useHttp` с `204 No Content`, pending state, optimistic update и rollback при ошибке.

## Зачем это нужно

[[7. HTTP flow, Services и Authorization|Первый HTTP vertical slice]] объяснил, почему кнопка не должна обходить backend. Теперь реальный Clients UI меняет `active ↔ paused` прямо в таблице. Здесь появляются две новые задачи: не позволить двойному клику отправить два запроса и не оставить switch в ложном состоянии, если сервер отказал.

Backend flow остаётся тем же:

```text
PATCH
↓
Route Model Binding
↓
FormRequest
↓
Controller
↓
Gate / Policy
↓
ChangeActivityStatus service + transaction
↓
Eloquent / PostgreSQL
```

Frontend не заменяет этот flow. Он выбирает, как отправить request и как показать результат пользователю.

## Короткая карта: два корректных ответа мутации

| Подход | Когда удобен | Ответ backend |
|---|---|---|
| `router.patch(...)` | Мутация должна привести к новому состоянию страницы. | `return back()` → redirect → новый GET → fresh props. |
| `useHttp(...).patch(...)` | Маленькое локальное действие, где page navigation не нужна. | `response()->noContent()` → HTTP 204. |

В текущем Clients UI выбран второй вариант: `useHttp` отправляет status, UI optimistically меняет одну строку, а Laravel возвращает `204 No Content` при успехе. `204` означает «операция выполнена, тела ответа нет»; это не значит, что backend ничего не сделал.

Для Inertia visits и partial reload см. [Manual visits](https://inertiajs.com/manual-visits), [Partial reloads](https://inertiajs.com/partial-reloads) и [Redirects](https://inertiajs.com/redirects).

## `return back()` — не пустой ответ

Классический Inertia write flow выглядит так:

```text
router.patch(...)
↓
Laravel выполняет use case
↓
return back()
↓
Inertia следует redirect
↓
GET текущей page
↓
fresh server props
```

Это хороший server-authoritative вариант для create/edit/delete, когда после мутации нужно обновить список, flash message или несколько несвязанных props. В Network после PATCH появляется GET не потому, что приложение «случайно дважды вызвало API», а потому что redirect ведёт к стандартному GET page endpoint.

Для текущего inline toggle такой переход по странице лишний. Поэтому controller заканчивается так:

```php
return response()->noContent();
```

Выбор между redirect и `204` — контракт конкретного endpoint и выбранного frontend interaction, а не правило «всегда использовать один ответ».

## Inertia router и HTTP request — разные намерения

`router.get`, `router.post`, `router.patch` и `router.delete` — Inertia visits. Они подходят для navigation-like действий: изменить URL, получить page component и props, применить Inertia callbacks/scroll/state behaviour.

```ts
router.get('/clients', query, {
    preserveState: true,
    replace: true,
});
```

`router.reload()` — visit текущего URL. Например, после операции, когда нужен server-truth для списка:

```ts
router.reload({ only: ['relationships'] });
```

Это partial reload: сервер возвращает только запрошенный top-level prop, а Inertia объединяет его с уже имеющимися props. `only` содержит ключи page props — здесь `relationships`, а не вложенный путь наподобие `relationships.data`.

| Опция | Смысл |
|---|---|
| `preserveScroll` | Не сбрасывать scroll после visit. |
| `preserveState` | Сохранить локальное состояние той же page component. |
| `replace` | Заменить текущую browser history entry. |
| `router.reload()` | Повторно посетить текущий URL. |
| `only` | На same-page visit запросить только выбранные top-level props. |
| `return back()` | Redirect после Inertia mutation к свежему GET page. |

`useHttp` в текущем starter kit — request-oriented API: `await request.patch(url)` возвращает Promise и естественно работает с `try/catch/finally`. Он не является заменой authorization, validation или service: это только другой frontend transport contract.

> [!warning]
> `router` и `useHttp` не стоит смешивать по привычке. Сначала нужно решить, ожидает ли interaction Inertia navigation/fresh props или локальный HTTP result, и затем согласовать controller response с этим выбором.

## Optimistic UI: быстрый интерфейс с честным rollback

**Optimistic UI** сначала показывает ожидаемый успех локально, а затем подтверждает его сервером. В Clients page это делается для конкретной relationship:

```ts
const previousStatus = relationship.activity_status;
const newStatus = previousStatus === 'active' ? 'paused' : 'active';

relationship.activity_status = newStatus; // optimistic update

try {
    await request.patch(updateActivityStatus.url(relationship.id));
    toast.success('Статус активности успешно изменен');
} catch (error) {
    relationship.activity_status = previousStatus; // rollback
    toast.error(getHttpErrorMessage(error, 'Не удалось изменить статус активности'));
}
```

```text
local previous status
↓
UI сразу показывает new status
↓
PATCH
├── 204 success → оставить UI как есть
└── error → вернуть previous status + показать error
```

Это не «доверие браузеру». PostgreSQL остаётся source of truth; optimistic value — временная локальная гипотеза. Такой UX хорош для небольшого, обратимого действия с понятным rollback. Для создания сложной сущности, критичного платежа или мутации, после которой нужно обновить множество props, надёжнее дождаться server response/redirect и показать server-authoritative UI.

## Pending state: защита от double submit

Пока request одной строки выполняется, повторный click не должен начинать второй toggle. Clients page хранит pending IDs в page component:

```ts
const pendingRelationships = ref<Set<number>>(new Set());
const isPending = (id: number) => pendingRelationships.value.has(id);

if (isPending(relationship.id)) return;

pendingRelationships.value.add(relationship.id);
try {
    // request
} finally {
    pendingRelationships.value.delete(relationship.id);
}
```

`Set` подходит, потому что мы храним membership по `relationship.id`, а не один общий boolean. Пока row pending, switch получает `disabled`:

```ts
disabled: relationship.ended_at !== null || isPending(relationship.id),
```

Pending state принадлежит `Clients.vue`: там живут data, request и действие. `clientColumns.ts` остаётся presentation layer. Поэтому columns создаются factory function, которая принимает нужные callbacks:

```ts
const clientColumns = createClientColumns(isPending, changeActivityStatus);
```

```text
Clients.vue
→ state, async action, pending, rollback
↓ передаёт callbacks
clientColumns.ts
→ cell rendering и вызывает callbacks
```

Так `clientColumns.ts` не получает скрытый доступ к page state и не превращается в второй controller.

## Ошибки: один `catch` на локальный request

`try/catch/finally` фиксирует lifecycle asynchronous operation:

```ts
try {
    await request.patch(url);
    toast.success('Статус активности успешно изменен');
} catch (error) {
    relationship.activity_status = previousStatus;
    toast.error(getHttpErrorMessage(error, fallback));
} finally {
    pendingRelationships.value.delete(relationship.id);
}
```

| Вид ошибки | Пример | Что делает UI |
|---|---|---|
| Validation | `422`, значение больше не проходит rules. | Не считать request успехом; показать понятный error. |
| HTTP | `403`, `404`, `500`. | Rollback и сообщение; право или server error не исправляется в браузере. |
| Network | offline, timeout, обрыв сети. | Rollback и сообщение о невозможности подтвердить операцию. |

`router` callbacks, в том числе `onError`, принадлежат Inertia visit protocol; это не универсальный обработчик каждой HTTP/JSON ошибки. Для `useHttp` текущий page code ловит rejection через `catch`.

В starter kit failure приходит как объект наподобие `HttpResponseError` с `response`. Текущий helper не предполагает, что `response.data` уже object: он проверяет строку и безопасно разбирает JSON.

```ts
try {
    const data = JSON.parse(response.data) as { message?: string };
    return data.message || fallback;
} catch {
    return fallback;
}
```

`JSON.parse` здесь — boundary handling конкретной текущей реализации transport, не универсальное правило для любого HTTP client. Если body не JSON или format изменится, fallback предотвращает вторичную ошибку в обработчике ошибки.

## Цельный flow inline toggle

```text
User toggles row #17
↓
Clients.vue проверяет isPending(17)
↓
сохраняет previousStatus и optimistically меняет local row
↓
useHttp PATCH /teacher-student-relationships/17/activity-status
↓
Laravel: FormRequest → Gate/Policy → ChangeActivityStatus → transaction
↓
204
→ toast success, local status остаётся

или error
→ catch: rollback previousStatus + error toast
↓
finally: удалить #17 из pending Set
```

Каждый слой отвечает за своё: UI управляет ожиданием и feedback; controller выбирает HTTP response; service и database подтверждают business invariant. Disable в UI улучшает UX, но backend всё равно обязан защищать authorization и корректный transition.

## Краткое резюме

```text
Inertia router visit
→ navigation / fresh page props / redirect flow

useHttp
→ request-oriented Promise / local async handling

optimistic UI
→ применить локально → подтвердить → rollback при error

pending Set
→ блокировать именно изменяемую row, не всю страницу
```

Формулировка для повторения: **optimistic UI не переносит бизнес-решение на frontend: backend остаётся authoritative, а UI временно показывает предполагаемый результат и обязан уметь откатиться.**

## Для проверки знаний

### Термины

- Inertia visit, redirect, `return back()`, fresh props, partial reload.
- `useHttp`, `204 No Content`, optimistic UI, rollback.
- Pending state, double submit, `try/catch/finally`, `HttpResponseError`.

### Что нужно уметь объяснить

- Почему `return back()` после Inertia PATCH приводит к следующему GET и когда это полезно.
- Чем `router.patch` отличается по намерению от `useHttp(...).patch` в текущем UI.
- Как `previousStatus`, `try/catch/finally` и pending `Set` вместе делают optimistic update безопаснее.
- Почему `only: ['relationships']` — top-level Inertia props, а не путь к `relationships.data`.
- Почему `disabled` в switch не заменяет backend Policy.

### Типичные ошибки

- Считать `204` отсутствием выполненной операции.
- Оставлять optimistic value при ошибке или забывать снять pending state при exception.
- Хранить request state внутри column definition вместо page component.
- Использовать `router` callback как универсальный обработчик произвольного HTTP error.

### Мини-практика

- Допиши pseudo-code toggle так, чтобы при `403` статус откатывался, error показывался, а ID исчезал из `pendingRelationships` даже при исключении.
- Объясни, почему после изменения search filter page нужно сбросить до первой, а после inline `204` toggle это не обязательно.
