## Регистрация маршрутов (страниц для обращения):
1.  маршруты располагаются в файле `/routes/web.php`;
2. способ регистрации маршрута:
	- через функцию обратного вызова: 
	  `Route::get('/', function() { return view('main'); });` (предварительно импортировав класс Route);
	- напрямую:
	  `Route::view('/', 'main');`;
	- маршруту нужно присвоить имя, чтобы вызывать эти маршруты (линки) не по адресу, а по имени: `Route::view('/', 'main')->name('home');` - теперь везде вызов будет по имени `home`, привязку которого можно изменить в любое время только в одном файле (не забывать про добавление переадресаций для SEO);
	- если установлен стартер кит Vue, то регистрация маршрутов будет через Inertia (предварительно импортировать класс Inertia) - с рендерингом компонента страницы из папки `/resources/js/pages/Main.vue` (здесь же перед рендерингом можно предварительно вызвать какой-нибудь php-миддлвар):

		```php
		Route::get('/', function() {
			return Inertia::render('Main');
		})->middleware(['auth', 'verified'])->name('home');
		```

3. файлы страниц располагаются в папке `/resources/views` (либо, если установлен движок Vue, в папке `/resources/js`);
4. вьюшки работают через инструмент Blade, в котором либо пишешь напрямую html-код страницы (отдельный `<name>.blade.php`-файл для каждой страницы), либо, если установлен движок Vue с Inertia, в папке `/resources/views` имеется только blade-обертка над динамически создаваемыми с помощью Inertia страницами, а сам код страниц развернут в структуре Vue-приложения в папке `/resources/js/pages`;
5. если маршрут не зарегистрирован, будет переадресация на страницу 404;
6. если маршрут есть, но не найден файл со страницей, выпадет ошибка php

## Добавление публичных файлов (assets, public)
1. все публичные ресурсы располагаются в папке `/public/build`;
2. например, изображения можно кидать в папку `/public/build/assets` или `/public/build/images`;
3. доступ к публичному файлу из blade-страницы осуществляется через добавление в html строки команды `asset(...)` - по умолчанию указывает на корень папки `/build`:
   `<div> {{ asset('images/img.jpg') }} </div>`;

## Базы данных и миграции
1. базы данных располагаются в папке `/database`;
2. конфигурации баз данных лежат в файле `/config/database.php` (наследуются данные из файла глобальных конфигураций `.env`, а при отсутствии берутся значения по умолчанию);
3. миграция - класс, наследующий системный Laravel-класс `Migration`, выполняет последовательно список действий, указанный во внутренней функции `up()`. Аналог миграции в Git - коммит новой версии приложения:
	- операции внутри миграции = выполненные изменения в коде;
	- запуск миграции (см. п.4) = выполнение коммита;
	- название файла миграции = комментарий к коммиту;
4. команда `php artisan migrate` запускает зарегистрированные миграции;
5. наряду с созданными таблицами в БД создается еще одна таблица `migrations`, в которой записана вся инфа о произведенных миграциях (как в системе версий Git). При следующем запуске идет сравнение новой версии с текущей и если есть изменения, миграция производится. Таблицы и данные при этом не удаляются;
6. нет смысла изменять уже имеющиеся миграции, т.к. они выполняются только 1 раз и помечаются как выполненные. Вместо этого нужно создавать новую миграцию;
7. операции миграции:
	- `php artisan migrate` - скан истории всех миграций и выполнение новых действий;
	- `php artisan migrate:rollback` - откат последней миграции;
	- `php artisan migrate:refresh` - откат всех миграций и запуск их по новой;
	- `php artisan migrate:fresh` - удаление всех таблиц и запуск миграций по новой;
	- флаг `--force` - добавляется, чтобы выполнить изменения на боевой базе (если конфигурация *APP_ENV=production*), т.к. по умолчанию это заблокировано (во избежание ошибок);
8. порядок выполнения миграций на боевом сервере:
	1. остановить трафик пользователей (или перевести сайта в режим обслуживания);
	2. применить миграции;
	3. залить новый программный код (если 2 и 3 пункт не выполнены одновременно, но связаны друг с другом зависимостями, будут ошибки);
