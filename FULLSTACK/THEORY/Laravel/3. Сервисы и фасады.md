## Сервис
**Сервис** - это класс, выполняющий определенный функционал внутри своих методов. Нет строго правила размещения. Можно задать разные директории внутри `/app`, например:
- `/app/Services` - сервисы логгера, платежей и пр.;
- `/app/Repositories` - обертки над запросами к БД;
- `/app/Helpers` / `/app/Support` - различные утилиты;
- `/app/Actions` - классы, выполняющие какое-либо одно действие, и т.д.

==Пример сервиса==:
```php
// файл /app/Services/Logger.php
class Logger {
	public function __construct(...) { ... }
	public function info(string $message) { ... }
}
```

## [**Cервис-контейнер**](https://laravel.com/docs/12.x/container) 
Сервис-контейнер или по-другому **приложение `app`**. Один из вариантов контента - регистрация правил доступа к объектам подключенных сервисов, задаваемые сервис-провайдерами (см. далее):
- объект приложения/контейнера может быть получено [[Функции-хэлперы#Глобальные функции-хелперы|глобальным хелпером]] `app()` либо внутри провайдера через свойство объекта `$this->app`;
- список провайдеров, извлекаемый для регистрации при запуске приложения, находится в файле `/bootstrap/providers.php`^[т.е. в нем мы можем контролировать список подключенных к проекту сервисов, не влезая ни в контейнер, ни в директорию с провайдерами].


## [**Cервис-провайдер**](https://laravel.com/docs/12.x/providers)
Это **загрузчик**, который пишет в контейнер правило доступа к подключенному сервису. Служит для централизованного подключения нужного сервиса к приложению *на старте проекта*.

#### Файл загрузчика
Расположен в директории `/app/providers`, наследует системный класс `ServiceProvider` и должен содержать:
1. *обязательный* метод `register()` - для регистрации сервиса; 
2. *обязательный* метод `boot()` - запуск сервисов;
3. *необязательный* метод `provides()` - для "ленивой" регистрации сервиса (только в момент фактической надобности).

#### Способы регистрации сервиса
Проводится внутри функции `register()`:
* создание нового объекта при каждом запросе:

	```php
	$this->app->bind(...);
	```

* однократное создание нового объекта *только при первом запуске* и далее обращение к созданному ранее объекту:

	```php
	$this->app->singleton(...)
	```

* подключение уже созданного ранее объекта и дальнейшее использование его без преобразований:

	```php
	$this->app->instance(...)
	```

#### Параметры регистрации сервиса
Это аргументы функций *bind*, *singleton*, *instance*, описанных выше:
1. **через класс** (более современный метод):
	```php
	use App\Services\Logger;
	
	...(Logger::class, function() {
		return new Logger(...);
	})
	```
1. **по ключу** (deprecated, из ранних версий Laravel) - к сервису привязывается ключ, который затем можно использовать в фасадах:
	```php
	...('log', function() {
		// + вариант создания объекта напрямую, без импорта класса:
		return new \App\Services\Logger(...)
	})
	```

#### Создание провайдеров
- создание нового провайдера выполняется командой `php artisan make:provider NameServiceProvider`^[на старте приложения в директории `/app/providers` уже имеется файл AppServiceProvider, служащий как раз для подключения своих сервисов, но создание новых файлов ничем не ограничено] - после этого созданный провайдер автоматически добавится в список `/bootstrap/providers.php`;
- провайдер можно сделать ["ленивым"](https://laravel.com/docs/12.x/providers#deferred-providers), т.е. регистрировать его только в момент надобности - для этого класс провайдера следует расширить доп. интерфейсом `DeferrableProvider`, а в классе добавить метод `provides()`.

==Пример провайдера==:
```php
namespace App\Providers;
use Illuminate\Support\ServiceProvider;
use App\Services\Logger;
use App\Helpers\Formatter;
use App\Actions\Action

class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
	    $this->app->singleton(Formatter::class, function() {
		    return new Formatter();
	    })
	    
	    $this->app->bind(\App\Repositories\Api::class, function() {
		    return new \App\Repositories\Api();
	    })
	    
        $logger = new Logger(...);
        $this->app->instance(Logger::class, $logger);
        
        $this->app->bind('action', function() {
	        return new Action();
        })
    }
}
```

## Фасад
Это *обёртка* над функционалом вызова сервисного объекта:
1. отдельный класс, в котором с помощью статического метода можно вызвать любую начинку из объекта требуемого сервиса;
2. расположен в `/app/Facades`;
3. представляет собой в первую очередь прокси для упрощения доступа к объекту сервиса, т.е. не должен иметь внутренний функционал, производящий серьезные изменения (для этой цели служат *middlewares*);
4. встроенные [хелперы Laravel](https://laravel.com/docs/12.x/helpers) представляют собой именно фасады.

#### Создание и привязка фасадов
Класс фасада должен иметь обязательную функцию `getFacadeAccessor()`. Варианты создания  (см. [[3. Сервисы и фасады#Параметры регистрации сервиса|параметры регистрации сервисов]] выше):
- привязка к сервису **по ключу сервиса** (если правило регистрации сервиса включает в себя ключ):
	```php
	namespace App\Facades;
	use Illuminate\Support\Facades\Facade;
	
	class Log extends Facade {
		protected static function getFacadeAccessor(): string {        
			return 'log';
		}
	}
	```
- привязка к сервису **через класс**:
	```php
	namespace App\Facades;
	use Illuminate\Support\Facades\Facade;
	use App\Services\Logger;
		
	class Log extends Facade {
		protected static function getFacadeAccessor(): string {        
			return Logger::class;
		}
	}
	```

#### Фасады "на лету" (real-time facades)
Необязательно создавать фасад как отдельный класс и файл. Можно сделать так, чтобы автоматически генерировался временный фасад при обращении к классу. Для этого нужно:
1. импортировать нужный класс `use App\Services\Logger`;
2. подставить к строке импорта префикс `Facades`: `use Facades\App\Services\Logger`;
3. выполнить вызов метода через фасад `Logger::info(...)`;

#### Тестирование фасадов

1. **проверка выводимых данных** - выполняется через вызов маршрута, в котором вызывается интересующий метод требуемого объекта (должна открыться страница с данными из объекта, привязанного к фасаду):
	```php
	Route::get('/log', function () {
		return Log::get('value'); // получить значение value из объекта Logger
	});
	```
2. **мокирование фасада** (замена вызова реальных данных фасада подменными данными)^[тестирование проводится через добавление тестового класса в `tests/Feature/LoggerTest.php`, например, функции `test_log()`. При вызове в консоли `php artisan test` вызываются все имеющиеся тесты и в консоль выводятся результаты успешного или неуспешного выполнения (см. раздел Тесты)]:
	```php
	// файл с тестом внутри папки /tests/Feature
	public function test_log(): void {
	    Log::shouldReceive('get')
	        ->with('key')
	        ->andReturn('value');
	    $response = $this->get('/cache');
	    $response->assertSee('value');
    }
	```

	Описание этапов:
	1.  **`Log::shouldReceive('get')`**
	    - Здесь используется _Mockery_, встроенный в Laravel через фасады.
	    - Мы говорим: «Фасад `Log` должен перехватить вызов метода `get()`».
	    - Это значит, что настоящий кэш не будет вызван — мы подменяем его «муляжом».
	2. **`->with('key')`**
	    - Указываем: ожидаем вызов `Log::get('key')`.
	    - Если тестируемый код вызовет `Log::get()` с другим аргументом, тест упадёт.
	3.  **`->andReturn('value')`**
	    - Задаём возвращаемое значение.
	    - То есть, при обращении к `Cache::get('key')`, вернётся `'value'`, даже если в кеше пусто.
	4. **`$response = $this->get('/cache');`**
	    - Мы симулируем HTTP-запрос к маршруту `/cache`.
	    - Laravel в тестах поднимает «мини-приложение» и реально прогоняет запрос.
	5. **`$response->assertSee('value');`**
	    - Проверяем, что в HTML-ответе содержится строка `'value'`.
	    - То есть, контроллер правильно использовал кеш, взял `'value'` и отдал в представление.

## Запрос на получение объекта сервиса
Вызов объекта осуществляется по 2 схемам:
- **при отсутствии фасада** - через обращение к контейнеру и сервису напрямую:
	`ЗАПРОС = КОНТЕЙНЕР -> ПРОВАЙДЕР -> СЕРВИС -> ЦЕЛЬ`;
	
	==Пример обращения==:
	```php
	use App\Services\Logger;
	app(Logger::class)->info(...);
	```
- **при наличии фасада** - через фасад, минуя контейнер и сервис:
	`ЗАПРОС -> ФАСАД -> [КОНТЕЙНЕР -> СЕРВИС] -> ЦЕЛЬ`

	==Пример обращения==:
	```php
	use App\Facades\Log;
	Log::info(...);
	```
