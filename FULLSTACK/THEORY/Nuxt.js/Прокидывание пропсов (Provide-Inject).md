#provide #inject #prop-drilling

Вопрос **«Что такое Provide/Inject?»** на собеседовании — это ==проверка вашего умения управлять состоянием приложения и решать проблему **Prop Drilling (прокидывания пропсов)** без бездумного использования глобальных хранилищ вроде Pinia==.

Если отвечать на инженерном уровне, то **Provide/Inject — это встроенный во Vue механизм контекста**, который реализует паттерн _«Издатель-Подписчик»_ на уровне дерева компонентов, позволяя родителю предоставлять данные любым своим потомкам, независимо от глубины их вложенности.

## 1. Какую проблему решает Provide/Inject?

Представьте структуру, где в `Page.vue` лежат данные пользователя, а отобразить их нужно в глубоком дочернем компоненте `UserAvatar.vue`, который запрятан внутри пяти других UI-компонентов:  
`Page.vue ➡️ Layout.vue ➡️ Header.vue ➡️ Navbar.vue ➡️ UserMenu.vue ➡️ UserAvatar.vue`.

- **Решение через Props (Prop Drilling):** Вам придется прокидывать пропсы через _каждый_ промежуточный компонент. Это превращает код в спагетти: компоненты `Navbar` или `Header` вынуждены принимать и передавать дальше пропсы, которые им самим вообще не нужны.
- **Решение через Provide/Inject:** `Page.vue` один раз делает **`provide`** (делится данными), а `UserAvatar.vue` в любой момент делает **`inject`** (забирает данные). Все промежуточные компоненты про это даже не знают.

## 2. Как это работает в коде (Composition API)

**Компонент-родитель (высший уровень):**

```ts
<script setup>
import { provide, ref } from 'vue'

const theme = ref('dark')

// Предоставляем данные. Первый параметр — уникальный КЛЮЧ (строка), второй — само значение
provide('app-theme', theme)
</script>
```


**Компонент-потомок (любая глубина вложенности):**

```ts
<script setup>
import { inject } from 'vue'

// Забираем данные по ключу. 
// Второй параметр — значение по умолчанию, если родитель ничего не предоставил
const theme = inject('app-theme', 'light')
</script>

<template>
  <div :class="theme">Текущая тема приложения</div>
</template>
```

---

### Важный вывод

`provide/inject` хорошо подходит для **локального контекста поддерева**:

- тема конкретного UI-блока;
- состояние формы;
- API компонента-контейнера;
- настройки таблицы;
- состояние wizard/stepper;
- контекст модального окна;
- контекст дерева компонентов;
- сервис, относящийся к конкретной части UI.

Например:

```
FormProvider
│
├── FormHeader
├── FormFields
│   ├── Input
│   └── Select
└── FormActions
```

`FormProvider` может предоставить полный публичный API управления состоянием (как расширение [[#📜 Правило 2. Направление мутаций (Strict Unidirectional Data Flow)|Правила 2]]):

```ts
provide('form-context', {
  values,
  errors,
  setValue,
  validate
})
```

И все дочерние компоненты получают единый контекст - **потомок не знает и не должен знать о том, как именно хранится состояние**. 

Здесь `provide/inject` естественен.

## 3. Три важнейших правила использования на практике (Для Senior-ответа)

На собеседовании Middle/Senior обязательно спросят про подводные камни. Вот три золотых правила работы с Provide/Inject:

### 📜 Правило 1. Сохранение реактивности

Если вы передадите в `provide` обычную строку или число, они передадутся как статичные значения. Чтобы данные оставались реактивными, в `provide` нужно **всегда передавать `ref` или `reactive` целиком** (не извлекая `.value`). Тогда при изменении данных в родителе, потомок автоматически перерисуется.

### 📜 Правило 2. Направление мутаций (Strict Unidirectional Data Flow)

Потомок, который сделал `inject`, технически может написать `theme.value = 'light'`, и тема изменится во всем приложении. **Так делать не рекомендуется** — это ломает концепцию однонаправленного потока данных и затрудняет отладку.

- _Как правильно:_ Менять состояние должен только тот, кто его создал. Родитель вместе с данными должен передавать функцию-мутатор. А чтобы потомок ничего случайно не сломал, данные оборачивают в `readonly`.

```ts
// В Родителе:
provide('app-theme', {
  theme: readonly(theme), 
  changeTheme: (newTheme: 'light' | 'dark') => { theme.value = newTheme } 
})

// В Потомке
const { theme, changeTheme } = inject('app-theme')!
console.log(theme.value) // чтение 
changeTheme('dark') // изменение через публичный API
```



### 📜 Правило 3. Защита от конфликтов ключей (Injection Key)

Если использовать обычные строки в качестве ключей (`'theme'`), в большом проекте два разных разработчика могут случайно использовать один и тот же ключ, что приведет к перезаписи данных.

- _Инженерное решение:_ Использовать JavaScript-символы **`Symbol`** в качестве уникальных ключей.

```ts
// keys.ts (Общий файл ключей)
export const ThemeKey = Symbol('theme')

// В Родителе:
provide(ThemeKey, theme)

// В Потомке:
const theme = inject(ThemeKey)
```

## 4. Provide/Inject против Pinia: Когда что выбирать?

Это самый каверзный вопрос от тимлида. Если Provide/Inject такой крутой, зачем вообще нужна Pinia?

- **Выбирайте Provide/Inject**, если данные имеют локальный контекст и привязаны к конкретной ветке компонентов.
    - _Пример:_ Сложная UI-таблица (`<Table>`), внутри которой есть `<TableHeader>`, `<TableBody>`, `<TableCell>`. Ячейкам таблицы нужно знать настройки всей таблицы (например, активные фильтры), но глобальному приложению эти данные не интересны.
- **Выбирайте Pinia**, если данные являются **глобальным состоянием всего приложения**, не привязанным к конкретному дереву компонентов, или если логика требует сложного кэширования, работы с REST API и вызова экшенов из любой точки (например: сессия пользователя, корзина, список отелей).

### Архитектурный паттерн "мини-store"

Имеется форма, содержащая поля: _имя_ и _возраст_. Это состояние формы, и методы его мутаций должны быть переданы внутрь инпутов, которые могут отстоять от формы на несколько левелов. Создаем состояние и функции:

```ts
// состояние формы
const state = reactive({ 
	name: '', 
	age: 0, 
});
const setName = (name: string) => { 
	state.name = name,
};
const reset = () => { 
	state.name = '',
	state.age = 0,
}; 
provide('user-form', { 
	state: readonly(state), 
	setName, 
	reset, 
});
```

Потомок (инпут) **не знает и не должен знать**, как именно хранится состояние.

Он знает только контракт:

```ts
const {
  state,
  setName,
  reset,
} = inject(userFormKey)!
```

Это уже напоминает небольшой локальный store.

# 📥 Усредненный технический конспект по Provide/Inject для заметок

> **Вопрос интервьюера:** Что такое Provide/Inject во Vue и как им правильно пользоваться?
> 
> **Ваш ответ:**  
> _«Provide/Inject — это встроенный механизм Vue для передачи данных сквозь дерево компонентов, решающий проблему Prop Drilling без использования глобальных хранилищ._
> 
> *Родительский компонент объявляет данные через `provide(key, value)`, а любой дочерний компонент на любой глубине вложенности может получить их через `inject(key)`. *
> 
> _При работе с этим инструментом важно соблюдать три инженерных правила:_
> 
> 1. - **Реактивность:** Передавать в provide нужно `ref` или `reactive` объекты целиком, чтобы изменения синхронизировались.*
> 2. - **Однонаправленный поток данных:** Чтобы дочерние компоненты не мутировали стейт напрямую, данные следует оборачивать в `readonly()`, а для их изменения передавать из родителя явные функции-мутаторы.*
> 3. - **Безопасность ключей:** В крупных проектах вместо строк для ключей стоит использовать уникальные `Symbol`, чтобы избежать конфликтов имён.*
> 
> _Главное отличие от Pinia в том, что Provide/Inject ограничен контекстом конкретного дерева компонентов (например, подсистемы UI-компонентов таблицы), в то время как Pinia предоставляет сквозной глобальный стейт для всего приложения»_.
