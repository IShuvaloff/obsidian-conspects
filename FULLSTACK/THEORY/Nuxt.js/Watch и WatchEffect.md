# 1. Основная идея

Во Vue существует три основных способа работы с реактивностью.

|Инструмент|Назначение|Что делает|
|---|---|---|
|`computed`|Вычисление значения|Получает новое значение из существующих реактивных данных. Не имеет побочных эффектов.|
|`watch`|Реакция на изменение конкретного источника|Выполняет побочный эффект только после изменения указанных зависимостей.|
|`watchEffect`|Автоматический реактивный эффект|Сам определяет зависимости во время выполнения функции и автоматически подписывается на них.|

Главное правило:

> **computed вычисляет данные.  
> watch и watchEffect выполняют побочные эффекты (side effects).**

# 2. Что такое watch

**Определение**

> `watch` — механизм наблюдения за одним или несколькими реактивными источниками, который вызывает callback только после изменения наблюдаемого значения.

Можно наблюдать:

|Источник|Пример|
|---|---|
|ref|`watch(counter, callback)`|
|computed|`watch(totalPrice, callback)`|
|getter|`watch(() => route.params.id, callback)`|
|reactive объект|`watch(form, callback)`|
|массив источников|`watch([source1, source2], callback)`|

Лучшей практикой считается использовать **getter**, если наблюдается свойство объекта.

Например:

```ts
watch(
  () => route.params.id,
  loadUser
)
```

# 3. Что такое watchEffect

**Определение**

> `watchEffect` автоматически выполняет callback и подписывается на все реактивные зависимости, которые были прочитаны во время его выполнения.

Пример

```ts
watchEffect(() => {
  console.log(user.value)
  console.log(locale.value)
})
```

Vue автоматически определит зависимости:

- user
- locale

И будет повторно запускать callback при изменении любой из них.

# 4. Сравнение watch и watchEffect

|Возможность|watch|watchEffect|
|---|---|---|
|Нужно перечислять зависимости|✅ Да|❌ Нет|
|Vue сам определяет зависимости|❌ Нет|✅ Да|
|Выполняется сразу после создания|Только с `immediate: true`|Всегда|
|Есть `oldValue`|✅ Да|❌ Нет|
|Есть `newValue`|✅ Да|❌ Нет|
|Можно точно контролировать, что отслеживается|✅ Да|❌ Нет|
|Хорошо подходит для сложной логики|✅ Да|⚠️ Только если зависимости очевидны|
|Хорошо подходит для небольших реактивных эффектов|⚠️ Иногда|✅ Да|

# 5. Плюсы и минусы 

|Группа|Плюсы|Минусы|
|---|---|---|
||||
|**watch**|Явно указаны зависимости|Нужно вручную перечислять все зависимости|
||Есть `oldValue` и `newValue`|Код может становиться многословным|
||Можно наблюдать несколько источников|Легко начать использовать его там, где нужен `computed`|
||Легко читать через год|При большом количестве watch логика становится разбросанной|
||Предсказуемое поведение|Возможны циклические обновления при плохом проектировании|
||||
|**watchEffect**|Минимум кода|Не всегда очевидно, какие зависимости используются|
||Не нужно перечислять зависимости|Нет `oldValue`|
||Очень удобно для небольших эффектов|Сложнее читать большие функции|
||Автоматически реагирует на новые зависимости|Зависимости могут меняться в зависимости от условий внутри callback|

# 6. Когда использовать watch

Использовать рекомендуется, если:

* ✅ нужно знать старое значение (использовать `oldValue`)
* ✅ нужно реагировать только на конкретное поле объекта (использовать геттер)
* ✅ нужно наблюдать несколько зависимостей (использовать массив)
* ✅ нужно отменять предыдущие асинхронные операции

```ts
watch(id, async (id, _, onCleanup) => {
  const controller = new AbortController()
  ... // асинхронная операция, куда передается { param: signal: controller.signal }
  onCleanup(() => controller.abort())
})
```

# 7. Когда использовать watchEffect

Лучше подходит для реактивных эффектов.

Например

```ts
watchEffect(() => {
  document.title = title.value
  localStorage.setItem(...)
  analytics.identify(user.value.id)
})
```

# 8. Когда НЕ использовать watch

Самый популярный вопрос на Senior.

### ❌ Не использовать вместо computed

Если можно вычислить значение без побочных эффектов — почти всегда нужен `computed`.

---

### ❌ Не использовать для синхронизации двух реактивных переменных

Плохо

```ts
watch(a, () => b.value = a.value)
watch(b, () => a.value = b.value)
```

Можно получить циклические обновления.

---

### ❌ Не использовать огромное количество watch

Если в компоненте 10–15 watch, скорее всего архитектуру стоит пересмотреть.

# 9. Параметры наблюдателя

### `deep`

```ts
watch(
  () => user,
  callback,
  {
    deep: true
  }
)
```

|✅Плюсы|❌Минусы|
|---|---|
|реагирует на вложенные изменения|Vue рекурсивно обходит объект|
||дорого на больших структурах|

Использовать только если действительно необходимо.

---

### `flush`

|Режим|Когда вызывается|
|---|---|
|pre (по умолчанию)|До обновления DOM|
|post|После обновления DOM|
|sync|Немедленно после изменения|

Практически всегда используется `pre`.

`post` нужен, если callback работает с уже обновленным DOM.
`sync` лучше не использовать, возможны каскадные изменения

---

### `immediate`

|значение `immediate`|создали watch|значение изменилось|
|---|---|---|
|`false` (по умолчанию)|ничего|callback|
|`true`|callback|callback|


---

### `cleanup`

Очень любят спрашивать на Senior.

```
watch(id, (id, _, onCleanup) => {

})
```

Позволяет

- отменять fetch
- очищать таймеры
- удалять подписки

# 10. Загрузка данных при изменении route.params.id

Для загрузки данных страницы лучше использовать

```ts
// Nuxt-функционал useFetch с реактивным ключом:
const { data } = await useFetch(
  () => `/api/users/${route.params.id}`
)
```

или

```ts
await useAsyncData(
  () => `user-${route.params.id}`,
  ...
)
```

Потому что Nuxt автоматически обеспечивает:

- SSR
- гидратацию
- кэширование
- deduplication запросов
- pending
- error
- refresh
- повторную загрузку при изменении реактивного URL или ключа

То есть использует встроенную инфраструктуру Nuxt.

---

### Поэтому считается хорошей практикой

|Сценарий|Что использовать|
|---|---|
|Загрузка данных страницы|`useFetch` или `useAsyncData`|
|Реакция на изменение маршрута|`watch`|

Например, здесь `watch` полностью оправдан:

1. изменение аналитики:
	```ts
	watch(
	  () => route.fullPath,
	  () => analytics.track()
	)
	```
2. сброс выделенных строк:
	```ts
	watch(
	  () => route.query.page,
	  () => selectedRows.value = []
	)
	```
3. скролл до якоря:
	```ts
	watch(
	  () => route.hash,
	  scrollToAnchor
	)
	```

---

### Исключение

Если приложение построено вокруг моделей или Pinia.

Например

```ts
watch(
  () => route.params.id,
  id => usersModel.load(id)
)
```

Это тоже хороший код.

Почему?

Потому что watch не занимается HTTP-запросом.

Он лишь сообщает доменной модели:

> Контекст изменился — обнови своё состояние.

# 11. Хорошие практики

|Хорошая практика|Почему|
|---|---|
|Использовать getter `() => route.params.id`|Явное наблюдение конкретного свойства|
|Использовать `computed` вместо watch для вычислений|Декларативнее, кэшируется, проще поддерживать|
|Использовать `watch` только для side effects|Соответствует архитектуре Vue|
|Использовать `useFetch`/`useAsyncData` для загрузки данных страниц Nuxt|Используется встроенная инфраструктура SSR, кэширования и гидратации|
|Использовать `onCleanup` для отмены запросов|Предотвращает гонки запросов и утечки ресурсов|
|Делать callback небольшим|Повышает читаемость|
|Использовать `deep` только при необходимости|Избегает лишней нагрузки|

<br>

<br>

# 12. Плохие практики

|Плохая практика|Почему плохо|
|---|---|
|Использовать watch вместо computed|Нарушается декларативность|
|Загружать данные страниц через watch вместо useFetch/useAsyncData|Теряются преимущества Nuxt|
|Создавать десятки watch в одном компоненте|Логика становится размазанной|
|Использовать deep без необходимости|Лишние вычисления|
|Менять собственные зависимости внутри watchEffect|Может привести к трудноотлаживаемым повторным срабатываниям или циклам|
|Синхронизировать два ref через взаимные watch|Риск бесконечных циклов|

                        [   watch()   ]              [ watchEffect() ]

_«У меня простая ментальная карта. Если мне нужно **трансформировать** данные — это всегда `computed`. Если нужно запустить **побочный эффект** — я смотрю на контекст. Если это **Nuxt и API** — я беру `useFetch/useAsyncData`. Если это **клиентская логика** (синхронизация с локальным хранилищем или анимации) — я смотрю на зависимости. Если они четко определены и мне нужно старое значение — я пишу `watch`. Если код зависит от пачки переменных динамически — я пишу `watchEffect`»_.

# 14. Что обычно хотят услышать на собеседовании уровня Middle+/Senior

> `watch` и `watchEffect` предназначены для выполнения побочных эффектов, а не для вычисления новых значений. Если значение можно получить из других реактивных данных без побочных эффектов, следует использовать `computed`. Для загрузки данных страницы в Nuxt предпочтительнее использовать `useFetch` или `useAsyncData`, поскольку они интегрированы с SSR, гидратацией, кэшированием и повторной загрузкой данных. `watch` лучше применять для реакции на изменения состояния или маршрута (например, аналитика, сброс локального состояния, синхронизация с внешними API), а `watchEffect` — для небольших реактивных эффектов, когда явное перечисление зависимостей только усложнит код. Такое разделение ответственности делает код более декларативным, предсказуемым и соответствующим архитектуре Vue и Nuxt.
