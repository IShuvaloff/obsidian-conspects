# TypeScript in Vue 3 / Nuxt 3

> Короткий production-oriented конспект по TypeScript в Vue 3 / Nuxt 3.
>
> **SFC = Single File Component** — обычный `.vue`-файл, в котором вместе живут `<script>`, `<template>` и `<style>`.

---

## 1. `defineProps<T>()`

Типизируем входной API компонента.

```vue
<script setup lang="ts">
interface Props {
  userId: number
  title?: string
}

const props = defineProps<Props>()
</script>
```

Если поле optional:

```ts
title?: string
```

внутри компонента его тип:

```ts
string | undefined
```

### Defaults через `withDefaults`

```ts
const props = withDefaults(
  defineProps<Props>(),
  {
    title: 'Default title'
  }
)
```

Теперь внутри компонента `props.title` — `string`.

Для массивов/объектов в defaults обычно используют factory:

```ts
withDefaults(
  defineProps<{ items?: string[] }>(),
  {
    items: () => []
  }
)
```

## 2. `defineEmits<T>()`

Типизируем события и payload.

```ts
const emit = defineEmits<{
  save: [id: number]
  close: []
}>()
```

Корректно:

```ts
emit('save', 42)
emit('close')
```

Ошибки типизации:

```ts
emit('save', '42')
emit('delete')
```

**Смысл:** публичный событийный API компонента становится частью TypeScript-контракта.

## 3. `defineModel<T>()`

Современный способ типизировать `v-model`.

```ts
const model = defineModel<string>()
```

Это заменяет ручной стандартный контракт:

```text
modelValue
update:modelValue
```

То есть отдельно писать `modelValue` в `defineProps` уже не нужно.

```ts
model.value = 'new value'
```

обновит родительский `v-model`.

### Несколько моделей

Родитель:

```vue
<MyComponent
  v-model:title="title"
  v-model:count="count"
/>
```

Ребёнок:

```ts
const title = defineModel<string>('title')
const count = defineModel<number>('count')
```

### Обязательная модель

```ts
const count = defineModel<number>({
  required: true
})
```

TypeScript проверяет контракт на этапе type-check, но это не runtime-validation.

## 4. `ref<T>` и `reactive<T>`

### `ref`

```ts
const user = ref<User | null>(null)
```

Важно: если написать только:

```ts
const user = ref(null)
```

TypeScript может вывести слишком узкий тип `Ref<null>`.

### `reactive`

```ts
interface State {
  user: User | null
  loading: boolean
}

const state = reactive<State>({
  user: null,
  loading: false
})
```

### Практическая эвристика

- `ref` — одиночные значения и состояние, которое удобно заменять целиком;
- `reactive` — связанный объект состояния, который удобно менять по полям.

## 5. `computed<T>`

Чаще всего generic писать не нужно:

```ts
const fullName = computed(
  () => `${firstName.value} ${lastName.value}`
)
```

TypeScript выведет:

```ts
ComputedRef<string>
```

Явный generic полезен, когда хотим закрепить публичный compile-time контракт:

```ts
const status = computed<'idle' | 'loading'>(() => {
  return 'idle'
})
```

Если callback вернёт `'done'`, TypeScript выдаст ошибку.

## 6. Composables и типизация return

Для внутренних composables inference часто лучше ручной типизации:

```ts
function useUser() {
  const user = ref<User | null>(null)
  const loading = ref(false)

  async function load() {
    // ...
  }

  return {
    user,
    loading,
    load
  }
}
```

Явный return type полезен, когда:

- composable — публичный API;
- нужен стабильный контракт;
- нужно специально скрыть часть внутренней реализации.

Пример:

```ts
interface UseUserReturn {
  user: Readonly<Ref<User | null>>
  loading: Readonly<Ref<boolean>>
  load: () => Promise<void>
}
```

## 7. Generic composables

```ts
function useAsyncData<T>(
  loader: () => Promise<T>
) {
  const data = ref<T | null>(null)

  return { data }
}
```

Если:

```ts
function fetchUsers(): Promise<User[]> {
  // ...
}
```

то:

```ts
const result = useAsyncData(fetchUsers)
```

даст:

```ts
T = User[]
```

и:

```ts
result.data
// Ref<User[] | null>
```

Главная идея generics та же, что и в чистом TypeScript: **сохраняем связь типов между входом и выходом**.

## 8. Pinia setup store

В setup-store обычно нет необходимости вручную типизировать весь store.

```ts
export const useUserStore = defineStore('user', () => {
  const user = ref<User | null>(null)
  const loading = ref(false)

  const isAuthorized = computed(
    () => user.value !== null
  )

  async function loadUser() {
    // ...
  }

  return {
    user,
    loading,
    isAuthorized,
    loadUser
  }
})
```

Vue/Pinia inference обычно достаточно.

### Ограничение внешней мутации

Если наружу не хочется отдавать mutable ref:

```ts
const userData = ref<User | null>(null)

const user = computed(() => userData.value)

return {
  user,
  loadUser
}
```

Внутри store остаётся mutable `userData`, а наружу отдаётся getter-only computed.

## 9. `InjectionKey<T>` для `provide/inject`

Ключ удобно хранить как один экспортируемый `Symbol`:

```ts
// injectionKeys/user.ts

import type {
  InjectionKey,
  Ref
} from 'vue'

export const userKey:
  InjectionKey<Ref<User | null>> =
    Symbol('user')
```

Provider:

```ts
provide(userKey, user)
```

Consumer:

```ts
const user = inject(userKey)
```

Тип:

```ts
Ref<User | null> | undefined
```

`InjectionKey<T>` гарантирует тип значения, **если provider найден**, но TypeScript не может доказать, что `provide()` действительно был вызван выше по дереву.

### Обязательная dependency через composable

```ts
export function useInjectedUser() {
  const user = inject(userKey)

  if (!user) {
    throw new Error('User provider is missing')
  }

  return user
}
```

Теперь callers получают:

```ts
Ref<User | null>
```

без `undefined`.

**Почему composable, а не generic util:** функция напрямую использует Vue Composition API (`inject`), поэтому это Vue-specific reusable logic.

## 10. DOM events

Базовый DOM event:

```ts
function onInput(event: Event) {
  // ...
}
```

`event.target` имеет тип:

```ts
EventTarget | null
```

`EventTarget` не гарантирует `.value`.

### Через assertion

```ts
const target =
  event.target as HTMLInputElement

console.log(target.value)
```

### Через runtime narrowing

```ts
const target = event.target

if (target instanceof HTMLInputElement) {
  console.log(target.value)
}
```

Иногда семантически лучше использовать `currentTarget`, если нужен именно элемент, на котором зарегистрирован handler.

## 11. Template refs

```ts
const inputRef =
  ref<HTMLInputElement | null>(null)
```

`null` нужен потому что:

- до `mounted` DOM-элемента ещё нет;
- после mount Vue положит туда `HTMLInputElement`;
- после unmount ссылка снова может стать `null`.

### Ref на дочерний компонент

```ts
const modalRef =
  ref<InstanceType<typeof MyModal> | null>(null)
```

В дочернем компоненте:

```ts
defineExpose({
  open
})
```

Использование:

```ts
modalRef.value?.open()
```

## 12. Typed scoped slots: `defineSlots<T>()`

`defineSlots` типизирует **не то, что родитель рисует внутри слота**, а **данные, которые дочерний компонент передаёт slot-контенту родителя**.

### Child

```vue
<script setup lang="ts">
interface User {
  id: number
  name: string
  email: string
}

defineProps<{
  users: User[]
}>()

defineSlots<{
  default(props: {
    user: User
    index: number
  }): any
}>()
</script>

<template>
  <div
    v-for="(user, index) in users"
    :key="user.id"
  >
    <slot
      :user="user"
      :index="index"
    />
  </div>
</template>
```

### Parent

```vue
<UserList :users="users">
  <template #default="{ user, index }">
    <div>
      {{ index }}.
      {{ user.name }}
      {{ user.email }}
    </div>
  </template>
</UserList>
```

Ментальная модель:

```ts
slot({
  user,
  index
})
```

Scoped slot похож на **render callback**:

- child решает, **когда** вызвать slot и какие данные передать;
- parent решает, **как** эти данные отрисовать.

## 13. Generic SFC components

> **SFC = Single File Component**.

Generic-параметр объявляется прямо в `<script setup>`:

```vue
<script
  setup
  lang="ts"
  generic="T"
>
```

Без этого:

```ts
defineProps<{
  items: T[]
}>()
```

не скомпилируется, потому что `T` нигде не объявлен.

Это аналог:

```ts
function identity<T>(value: T): T
```

### Constraint

```vue
<script
  setup
  lang="ts"
  generic="T extends { id: number }"
>
```

Теперь `T` обязан иметь:

```ts
id: number
```

## 14. Универсальный generic-компонент: props + slot + emit + model

```vue
<script
  setup
  lang="ts"
  generic="T extends { id: number }"
>
defineProps<{
  items: T[]
}>()

const selected =
  defineModel<T | null>()

defineSlots<{
  item(props: {
    item: T
    selected: boolean
  }): any
}>()

const emit = defineEmits<{
  select: [item: T]
}>()

function selectItem(item: T) {
  selected.value = item
  emit('select', item)
}
</script>

<template>
  <div
    v-for="item in items"
    :key="item.id"
    @click="selectItem(item)"
  >
    <slot
      name="item"
      :item="item"
      :selected="selected?.id === item.id"
    />
  </div>
</template>
```

Родитель:

```vue
<script setup lang="ts">
const users = ref<User[]>([])
const selectedUser =
  ref<User | null>(null)

function handleSelect(user: User) {
  console.log(user.name)
}
</script>

<template>
  <GenericList
    v-model="selectedUser"
    :items="users"
    @select="handleSelect"
  >
    <template #item="{ item, selected }">
      <UserCard
        :user="item"
        :selected="selected"
      />
    </template>
  </GenericList>
</template>
```

Если передан:

```ts
User[]
```

TypeScript выводит:

```text
T = User
```

и один `T` связывает:

```text
props.items    → T[]
v-model        → T | null
slot.item      → T
emit('select') → T
```

Это главный смысл generic-компонента: **сохранять типовую связь между частями публичного API компонента**.

## 15. Generic-компонент для одинаковых списков разных сущностей

Хороший production-кейс:

- одинаковая сетка;
- 3 карточки в ряд;
- 12 элементов на страницу;
- одинаковая пагинация;
- общие loading/empty/error states;
- отличается только карточка.

Тогда вместо 10 почти одинаковых list-компонентов можно сделать один:

```text
GenericList
  ├─ layout
  ├─ pagination
  ├─ loading
  ├─ empty state
  ├─ common controls
  └─ slot<T>
       ├─ ProductCard
       ├─ UserCard
       ├─ HotelCard
       └─ ...
```

Родитель:

```vue
<GenericList :items="products">
  <template #item="{ item }">
    <ProductCard :product="item" />
  </template>
</GenericList>
```

Для `products: Product[]` TypeScript выводит:

```text
T = Product
```

и `item` в slot автоматически становится `Product`.

### Архитектурная граница

Не стоит превращать GenericList в универсальный бизнес-комбайн.

Хорошо держать внутри:

- layout;
- pagination shell;
- loading/error/empty state;
- общий selection/sort UI.

Domain-specific filtering/API/business rules лучше оставлять странице или composable.

## 16. Generic `T, K extends keyof T`

```vue
<script
  setup
  lang="ts"
  generic="T, K extends keyof T"
>
defineProps<{
  items: T[]
  labelKey: K
}>()
</script>
```

Если:

```ts
type User = {
  id: number
  name: string
  email: string
}
```

можно:

```vue
<GenericList
  :items="users"
  label-key="name"
/>
```

нельзя:

```vue
<GenericList
  :items="users"
  label-key="title"
/>
```

потому что `'title'` не входит в `keyof User`.

И:

```ts
item[props.labelKey]
```

имеет тип:

```ts
T[K]
```

То есть выбранный ключ связан с типом соответствующего значения.

## 17. Nuxt: generic в `useFetch<T>` — только compile-time контракт

```ts
const { data } =
  await useFetch<User>('/api/user')
```

Generic `User` не валидирует runtime-ответ сервера.

Если backend вернул неправильную структуру, TypeScript сам этого не заметит.

Для внешних данных по-прежнему применим общий принцип:

```text
external data
→ unknown
→ runtime validation
→ trusted TypeScript type
```

Например через custom type guard, Zod или Valibot.

## 18. Главное, что помнить

```text
defineProps
→ входной API

defineEmits
→ события

defineModel
→ v-model контракт

defineSlots
→ данные, передаваемые slot-контенту

generic="T"
→ generic-параметр всего SFC

InjectionKey<T>
→ типизированный provide/inject

ref<T> / reactive<T>
→ типизированное реактивное состояние

computed<T>
→ обычно inference, explicit generic для фиксированного контракта
```
