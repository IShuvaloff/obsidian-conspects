#nuxt-middlewares #defineNuxtRouteMiddleware

[Промежуточное ПО](https://nuxt.com/docs/guide/directory-structure/middleware) - **middleware** - функции, которые вызываются перед тем, как произойдет навигация между различными страницами приложения, т.е. срабатывает перед непосредственным переходом по маршрутом. Располагается в папке `middleware/`, это обычные js/ts-файлы, экспортирующие функции по умолчанию:

```ts
export default defineNuxtRouteMiddleware((to, from) => {
	...
});
```

==Особенности==:
* *Файлы с ПО подразделяются по смыслу, но глобальные ПО данную логику отрабатывают только для определенных маршрутов `to` и `from`*
* *Название файла будет представлять собой название middleware*^[правила нейминга - kebab-case, т.к. вызов специального ПО на нужных страницах производится именно с таким вариантом имени]. 
* *Параметры `to` и `from` являются необязательными для специального ПО*;
* Из миддлвара можно вызывать [[GROM-IT SOFT/Проект Завидово (Nuxt 3)/Композаблы|композаблы]], не боясь, что возникнет ошибка "вызова композабла не из плагина/сетапа/промежуточного ПО";
* ***Нельзя запускать в миддлваре асинхронные операции*** ^[`fetch.then(...)`]! Т.к. действия, производимые внутри `.then`/`.finally`, могут выпасть из контекста миддлвара, что приведет к ошибке вида: 
  ``A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function.``

==Варианты ПО==:
1. **Глобальное** - срабатывает всегда и для всех маршрутов. Требует в названии суффикс `.global`, например, `do-something.global.ts`;
2. **Специальное** - требует привязки к определенной странице и будет срабатывать перед переходом непосредственно на нее. Название произвольное. Вызов специального миддлвара ведется со страницы, к которой требуется его подключить, в скрипте `<script setup>`^[файл будет носить название `middleware/load-activities.ts`]. В примере ниже в миддлваре `load-activity` происходит загрузка данных в локальное хранилище:
	```ts
	<script setup>
	...
	definePageMeta({
	    middleware: "load-activities",
	});
	...
	</script>
	```

==Используемые функции маршрутизатора==:
1. `return navigateTo('pageName')` - делает немедленный переход по указанному маршруту (иметь в виду, что главная страница называется `index`), работа миддлвара при этом завершается^[если миддлвар глобальный, то после перехода по указанному маршруту параметр `from` останется тем же самым, изменится только параметр `to`];
2. `return abortNavigation()` - немедленно останавливает переход по указанному маршруту, останавливая выполнение миддлвара, позволяет остаться на исходной странице^[плохо работает для перехода по прямой ссылке на страницу, т.к. никакого рендеринга еще не было произведено, параметр `from` пустой];
3. `return` - позволяет игнорировать последующее содержимое миддлвара и немедленно продолжить переход по указанному маршуту.

### Сохранение позиций скролла на странице и плавный переход к ним при маршрутизации (см. проект Завидово)

Если при маршрутизации жмется "Назад" в браузере, то в предыдущей странице и так происходит скролл к тому месту, с которого на текущую страницу был осуществлен переход. Но для явных перемещений по маршрутам (только вперед) требуется другая логика:
1. добавить в тег html базового CSS-файла проекта (чаще всего `/assets/css/main.css`) **атрибут плавной прокрутки**:
   
	```css
	html {
		scroll-behavior: smooth;
	}
	```
   
2. создать **хранилище позиций по каждой странице** (по умолчанию `undefined`/`0`^[интерфейс простейший - объект с ключом-названием маршрута и числовым значением: `export interface IScrollPositions { [key: string]: number; }`]):
   
   ![[Pasted image 20240524192218.png]]
   
3. создать **утилиту-прослойку между хранилищем и маршрутами**, между которыми происходит переход (разместить в папке `/utils`, автоматически парсится накстом и не требует импорта), - это позволит проще и быстрее сохранять, загружать и очищать позиции:
   
   ![[Pasted image 20240524192809.png]]
   
4. создать **глобальное промежуточное ПО** (миддлвар) для предварительной очистки (и т.о. последующей загрузки и скролла, см. далее) сохраненных позиций в случаях, если переход с какой-то страницы не текущую страницу не требует скролла. ==Здесь можно разместить всю логику наличия/блокировки скроллов в зависимости от требований проекта==. В данном случае имеются *страницы списков* и *страницы элементов списка*, и скролл должен производиться в списке только тогда, когда переход осуществлен со страницы элемента, в остальных случаях идет очистка:
   
   ![[Pasted image 20240524193526.png]]

5. При клике на ссылку перехода на другую страницу добавить запуск функции сохранения текущей позиции на данной странице:
   
   ![[Pasted image 20240524211348.png]]

6. На нужных страницах (в нашем случае на страницах списков) при переходе на них запускается функция прокрутки в хуке `mounted` - это происходит уже после того, как сработало промежуточное ПО, следовательно, при отсутствии необходимости прокрутки позиция скролла будет обнулена и скролл не будет произведен:
   
   ![[Pasted image 20240524210556.png]]

### Использование миддлвара как хранилища (см. проект Завидово (useAuth) или ЗГК-Автоматизация (все миддлвары))

==В миддлваре размещаются==:
	* переменные с данными;
	* переменные с ошибками загрузки;
	* булевы переменные, указывающие на процесс загрузки;
	* переменные для пагинации;
	* функции загрузки данных из API;
	* композаблы для фильтрации/мэппинга данных;
	* используемые константы.
