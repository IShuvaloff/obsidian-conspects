# 4. Backend и API

## Вопросы

### Как frontend взаимодействует с backend?

Нужно выяснить:

-   **REST**? → ==запрос ресурсов через HTTP==
> [!INFO]- Подробнее
> REST — это самый распространённый вариант взаимодействия frontend с backend через HTTP API.
> Обычно frontend обращается к URL-ресурсам, используя стандартные HTTP-методы:
> - *GET* /users/42  — получить данные
> - *POST* /orders  — создать
> - *PUT* /profile  — полностью обновить
> - *PATCH* /profile  — частично обновить
> - *DELETE* /cart/15  — удалить
> 
> Для frontend это обычно означает обычные HTTP-запросы через `fetch`, `$fetch`, `axios`, `useFetch` и работу с JSON.
> **Пример:**
> ```ts
> const user = await $fetch('/api/users/42')
> ```
> **Что важно уточнять на собеседовании:**
> - насколько API стабильно;
> - есть ли Swagger/OpenAPI;
> - кто определяет структуру request/response;
> - есть ли версионирование API;
> - как обрабатываются ошибки.

-   **GraphQL**? → ==frontend сам описывает необходимые данные==
> [!INFO]- Подробнее
> GraphQL — это подход, при котором frontend обращается обычно к одной точке API и сам описывает, **какие именно данные ему нужны**.
> 
> Вместо нескольких REST-запросов:
> - *GET* /user/42
> - *GET* /user/42/orders
> - *GET* /user/42/profile
> 
> может быть один GraphQL query:
> 
> ```ts
> query {
>   user(id: 42) {
>     name
>     email
>     orders {
>       id
>       price
>     }
>   }
> }
> ```
> 
> Backend возвращает именно запрошенные поля.
> 
> |Плюсы для frontend|Минусы|
> |---|---|
> |<ul style="margin:0;"><li>можно получать только нужные данные;</li><li>удобно работать со сложными связанными сущностями;</li><li>меньше зависимость UI от жёстко заданных REST endpoints.</li></ul>|<ul style="margin:0;"><li>сложнее инфраструктура;</li><li>кэширование может быть сложнее;</li><li>нужна GraphQL schema;</li><li>появляются отдельные инструменты вроде Apollo или urql.</li></ul>|
  
-   **RPC**? → ==frontend вызывает backend-операции / процедуры==
> [!INFO]- Подробнее
> RPC — Remote Procedure Call.
> 
> Идея здесь немного другая, чем у REST.
> 
> REST обычно говорит:
> 
> «Вот ресурс `/users/42`».
> 
> RPC говорит:
> 
> «Вызови удалённую функцию `getUser(42)`».
> 
> Условно API может выглядеть так:
> - *POST* /api/createOrder
> - *POST* /api/changePassword
> - *POST* /api/calculatePrice
> 
> То есть endpoint отражает **операцию**, а не ресурс.
> 
> Современные варианты RPC:
> 
> - gRPC;
> - tRPC;
> - JSON-RPC.
> 
> Например, в tRPC frontend может почти как обычную TypeScript-функцию вызвать backend-процедуру:
> 
> ```ts
> const user = await api.user.getById.query({ id: 42 })
> ```
> 
> Особенно интересен tRPC в TypeScript-проектах, потому что frontend и backend могут иметь общий type-safe контракт.

-   **WebSocket**? → ==постоянная двусторонняя связь==
> [!INFO]- Подробнее
> WebSocket — это постоянное двустороннее соединение между клиентом и сервером.
> 
> В обычном HTTP:
> 
> ```
> frontend → запрос
> backend  → ответ
> ```
> 
> При WebSocket соединение остаётся открытым:
> 
> ```frontend ⇄ backend```
> 
> И сервер может сам отправлять данные клиенту без нового HTTP-запроса.
> 
> Используется там, где нужны данные в реальном времени:
> - чаты;
> - уведомления;
> - биржевые котировки;
> - live-мониторинг;
> - статус серверов;
> - совместное редактирование;
> - progress длительных операций.
> 
> Например, в панели хостинга это может быть:
> 
> ```
> сервер создаётся
> 	↓
> backend отправляет status: creating
> 	↓
> backend отправляет status: configuring
> 	↓
> backend отправляет status: ready
> ```
> 
> Frontend получает обновления без постоянного polling.

-   **Server events**? → ==сервер постоянно отправляет события клиенту==
> [!INFO]- Подробнее
> Здесь лучше в документе написать именно **Server-Sent Events (SSE)**, потому что «Server events» слишком расплывчато.
> 
> SSE — это механизм, при котором сервер держит HTTP-соединение открытым и периодически отправляет события клиенту.
> 
> Главное отличие от WebSocket:
> 
> |WebSocket|SSE|
> |---|---|
> |`frontend ⇄ backend`|`backend → frontend`|
> 
> То есть SSE в основном односторонний канал.
> 
> Frontend подключается примерно так:
> 
> ```ts
> const source = new EventSource('/api/events')
> 
> source.onmessage = event => {
>   console.log(event.data)
> }
> ```
> 
> Хорошо подходит для:
> - уведомлений;
> - логов;
> - прогресса задач;
> - статусов операций;
> - стриминга результатов;
> - обновления dashboard.
> 
> Например:
> 
> ```
> deploy started
> deploy 30%
> deploy 70%
> deploy finished
> ```
> 
> Для такого сценария WebSocket может быть избыточным, а SSE — достаточно.

### Кто владеет API-контрактами?

Что означает:

Кто отвечает за структуру запросов и ответов.

Например:

Frontend ожидает:

``` json
{
  "name": "User",
  "role": "admin"
}
```

А backend меняет поле:

``` json
{
  "username": "User"
}
```

Если нет процесса согласования --- frontend ломается.

# Универсальная формула ответа на архитектурный вопрос

Если спрашивают:

"Спроектируйте личный кабинет"

Не начинать:

"Возьму Nuxt и Pinia".

1.  Уточнить пользователей.
2.  Уточнить сценарии.
3.  Определить требования.

-   Frontend участвует в решениях.
-   Есть обсуждение архитектуры.
-   Есть стабильные API-контракты.
-   Есть понятные процессы разработки.
