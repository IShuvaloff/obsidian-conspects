5. ==Загрузку данных для серверного рендеринга (SSR)== нужно проводить не в хранилище Pinia, а *в самом файле, где нужно данные отобразить*. Причины:
	1. поскольку данные первый раз выгружаются на сервере, а хранилище работает только на клиенте, возникнет `hydration warning`: содержимое сервера не соответствует содержимому клиента. Это не ошибка, но лучше так не делать;
	2. как вариант, можно оборачивать html-содержимое списков/данных, загружаемых по api-запросу, в тег **`<client-only>...</client-only>`**, но в этом случае загрузка начнется только после отрисовки страницы на клиенте, а в этом случае лучше добавить иконку производимой загрузки. Особенности:
		* *Следует иметь в виду, что если мы используем SSR и работаем с какими-либо данными, то первый рендеринг производится на сервере, но и на клиенте это тоже отрабатывает. Поэтому если у нас используется, например, рандомная сортировка списка, загружаемого на сервере, то при повторной отрисовке на клиенте произойдет новая отрисовка (тоже рандомная), но данные будут отличаться! Здесь лучше завернуть блок с рандомными данными в `<client-only>`, либо, если это важно для SEO, придумать что-то другое. ДЛЯ ПРИМЕРА см. проект "Завидово", файл `src/pages/index.vue`, где идет подгрузка рандомного списка недвижимости в нижней части главной страницы;*
	3. еще один вариант - использовать атрибут **`data-allow-mismatch`** для тега, отрисовка которого на сервере и клиенте может отличаться. Этот атрибут допускает ошибку гидратации и не выводит варнинги в консоли. *Использовать с осторожностью*!
	4. пользователь не любит иконки загрузки, а данные на сервере скорее всего загрузятся значительно быстрее, чем на клиенте, т.к. у клиента все зависит от скорости подключения к сети!

7. ==**Порядок работы в веб-приложении Nuxt**==:
	1. разработка бэкенда (БД, серверная настройка и т.д.);
	2. создание админки (в нашем случае на OctoberCMS - способ интерфейсного и быстрого редактирования данных на сайте);
	3. создание полноценных API-адресов для выполнения запросов к админке;
	4. загрузка первичных данных по API-запросам в SSR на сервере (**важно** то, что первичная загрузка данных производится на сервере, поэтому даже если мы заходим с локального хоста, первый раз все прогрузится. Но при выполнении переходов по маршрутам, запуска загрузок средствами DOM и пр. *api-сервер будет блокировать запросы с localhost средствами CORS*, если наш адрес не добавлен в список избранных, либо не установлены SSH-ключи (см. проект "Завидово"));
	5. повторная загрузка данных по API-запросам с клиента;
	6. **при необходимости отследить выполнение API-запросов** с сайта нужно:
		1. открыть DevTools, вкладку **Network**;
		2. если первой была загружена текущая страница, то при активном SSR все запросы были выполнены на сервере, поэтому группа Fetch/XHR будет пуста (без требуемых для проверки запросов);
		3. чтобы отследить выполнение запросов требуется не перезагружать страницу, а перейти с нее на другую и вернуться назад - в этом случае все загрузки будут производиться уже на клиенте (так как у нас SPA-приложение) и можно увидеть все запросы:

1. ==КЭШИРОВАНИЕ==:
	1. кэширование в браузере - стандартная функция, отключается в DevTools во вкладке Network, галочка "Disable Cache" (в верхней панели);
	2. кэширование на сервере - обычно работает в проектах, подключаемых к БД, срабатывает при первом обращении к серверу за некоторыми данными, например, за списком тех или иных объектов. Порядок:
		1. если БД не менялась, следующее извлечение данных будет производиться из кэша;
		2. если БД поменялась, то при первом обращении будет вновь произведено повторное кэширование;
		3. "**Прогрев сервера**" - намеренная процедура пробежки по всем маршрутам на сайте для того, чтобы после изменений в базе произвести предварительное кэширование новых данных^[обычно этим занимается разработчик];
	3. проверка загрузки данных на сервере (**правильной работы SSR**) - перезагрузить страницу и нажать *Ctrl + U* (либо "*Открыть код страницы*"): если не будут найдены теги требуемой страницы (любые теги из `<template>`), значит, рендеринг идет на клиенте, и, следовательно, SSR не работает. Такое может быть в следующих случаях:
		1. в модуле вызвана асинхронная функция ==**без `await`**==, например, с `.then`. Тогда на сервере не успеет произойти загрузка, которая будет выполнена уже на клиенте. Требуется вызывать все асинхронные функции с ожиданием результата! 
		2. кроме того, вызов некоторых композаблов, как например `useHttp` в проекте "Завидово", в SSR-режиме может приводить к ошибке 500 с [[GROM-IT SOFT/Проект Завидово (Nuxt 3)/Композаблы|описанием того, что системная функция вызывается вне плагина, setup-функции и middleware]]. Пример: если в списке "Чем заняться" попытаться загрузить асинхронно (см. п.1) список активностей функцией `getLoadCategoriesActivities` из `services/service.ts`, возникнет такая ошибка, тогда как обработка того же самого содержимого внутри модуля списка (откуда изначально функция и вызывалась) выполняется без ошибок;

14. ==Чтобы добавить класс через `v-bind`==, можно воспользоваться несколькими способами:
	1. привязать класс, взятый из переменной:
	   
		```ts
		const className = 'block';
		```
		```html
		<div :class='className'></div>
		```
	   
	2. привязать несколько классов:
	   
		```ts
		const class1 = 'block';
		const class2 = 'blog';
		```
		```html
		<div :class='[ block, blog]'></div>
		```
	   
	3. привязать класс по условию (класс припишется, если условие будет равно `true`):
	   
		```ts
		const className = 'block';
		const isPossible = true;
		```
		```html
		<div :class='{ className: isPossible}'></div>
		```
	   
	4. привязать несколько классов, некоторые по условию, другие постоянно (аналогично п.2 и п.3):
	   
		```ts
		const class1 = 'block';
		const class2 = 'blog';
		const isPossible = true;
		```
		```html
		<div :class='[ class1, { class2: isPossible } ]'></div>
		```
	   
	5. во всех предыдущих случаях имя класса должно быть переменной с конкретным значением (не динамическим). Если требуется задать имя класса, зависящее от каких-либо условий - составное^[*например, навешивание класса в цикле `v-for`, внутри которого классы нужно называть по-разному*], нужно обернуть составную строку с условием в квадратные скобки:
	   
		```ts
		const className = 'block';
		const isPossible = true;
		```
		```html
		<div :class="{ [`class--${className}`]: isPossible }"></div>
		```
	   
1. **==Управление шаблонами== `<template></template>`** - в шаблон можно оборачивать любое содержимое. Особенности:
	1. при рендеринге контейнер `<template>` пропадает - вместо него вырисовывается только содержимое, поэтому нет смысла навешивать на шаблон классы;
	2. шаблону можно приписать любые атрибуты, например, `v-if`: в этом случае содержимое шаблона будет отображено на странице по условию;
2. Если требуется дождаться применения изменений после, например, изменения значения переменной, прежде чем выполнять следующие действия (такое бывает, когда какие-то данные должны быть использованы сразу после их изменения в той или иной части кода), следует после изменений вызывать асинхронную функцию `await nextTick()`. 
3. Использование асинхронных вызовов функций через `await` внутри компонентов (кроме компонентов страниц в папке `/pages`) **==КРАЙНЕ НЕЖЕЛАТЕЛЬНО==**, т.к. *может вести к ошибкам рендеринга*. Пример: загрузка содержимого рекламы для рекламного баннера, высвечивающегося на всех страницах, в соответствующем компоненте - при переходе на любую страницу со страницы ошибки `/error.vue` возникает **проблема рендеринга DOM-компонентов**.
