# TypeScript Runtime Safety

## 1. Главная граница TypeScript

TypeScript обеспечивает compile-time type safety, но не валидирует реальные данные автоматически в runtime.

После компиляции исчезают:

- `type`
- `interface`
- generics
- utility types
- generic constraints

---

## 2. Почему `fetchData<T>` не валидирует API

```ts
async function fetchData<T>(
  url: string
): Promise<T> {
  const response = await fetch(url)
  return response.json()
}
```

```ts
const user =
  await fetchData<User>('/api/user/1')
```

не гарантирует, что backend реально прислал `User`.

Сервер может вернуть:

```json
{
  "foo": 123
}
```

а TypeScript этого сам не увидит.

---

## 3. Trust Boundary

Внешние данные лучше считать недоверенными:

- API
- localStorage
- URL/query params
- пользовательский ввод
- сторонние SDK

Хорошая модель:

```text
external data
↓
unknown
↓
runtime validation
↓
trusted domain type
```

---

## 4. Custom Type Guard

```ts
interface User {
  id: number
  name: string
}

function isUser(data: unknown): data is User {
  return (
    typeof data === 'object' &&
    data !== null &&
    'id' in data &&
    'name' in data &&
    typeof data.id === 'number' &&
    typeof data.name === 'string'
  )
}
```

---

## 5. Универсальный `fetchData<T>` с guard

```ts
async function fetchData<T>(
  url: string,
  guard: (data: unknown) => data is T
): Promise<T> {
  const response = await fetch(url)
  const data: unknown = await response.json()

  if (!guard(data)) {
    throw new Error('Invalid API response')
  }

  return data
}
```

Использование:

```ts
const user = await fetchData(
  '/api/user/1',
  isUser
)
```

Pipeline:

```text
JSON
↓
unknown
↓
isUser()
↓
User
```

---

## 6. Почему нельзя проверить generic `T` напрямую

Нельзя:

```ts
if (data instanceof T) {}
```

Потому что `T` существует только в compile-time.

Runtime validator должен быть реальным JavaScript-кодом.

---

## 7. Runtime Schema Validators

Для большого API ручные `isUser`, `isProduct`, `isOrder` быстро становятся неудобными.

Подходящие библиотеки:

- Zod
- Valibot
- аналогичные runtime schema validators

Идея:

```ts
const UserSchema = z.object({
  id: z.number(),
  name: z.string()
})
```

Плюс схем: runtime validation и TypeScript type могут опираться на один источник истины.

**Interview-формулировка:** TypeScript не валидирует внешние данные в runtime. На trust boundary разумно сначала считать данные `unknown`, затем провалидировать через type guard или schema validator и только потом считать их доменным типом.

## 8. `throw` vs `Result<T>`

### Exception

```ts
async function getUser(
  id: number
): Promise<User> {
  const response = await fetch(...)

  if (!response.ok) {
    throw new Error('Failed')
  }

  return response.json()
}
```

Ошибка не является возвращаемым значением.

### Явный бизнес-результат

```ts
type Result<T> =
  | {
      success: true
      data: T
    }
  | {
      success: false
      error: string
    }
```

```ts
async function getUser(
  id: number
): Promise<Result<User>> {
  // ...
}
```

Использование:

```ts
const result = await getUser(1)

if (result.success) {
  console.log(result.data.name)
} else {
  console.log(result.error)
}
```

Это discriminated union.

## 9. Почему `User | never` не моделирует ошибку

```ts
User | never
```

упрощается до:

```ts
User
```

Формула:

```text
T | never = T
```

---

## 10. Compile-time error != runtime error

Generic constraint:

```ts
function merge<T extends object>(value: T) {
}
```

не генерирует автоматически runtime-проверку:

```js
if (typeof value !== 'object') {
  throw ...
}
```

TypeScript может сообщить type error, но runtime-поведение определяется уже JavaScript-кодом и настройками сборки.

Например:

```json
{
  "noEmitOnError": true
}
```

может запретить emit JS при type errors.

---

## Interview-шпаргалка

```text
TypeScript -> compile-time safety
External data -> unknown
Type guard/schema -> runtime validation
Result<T> -> ошибка как ожидаемая часть результата
throw -> исключительная ветка
Generic <T> -> не runtime validator
```
