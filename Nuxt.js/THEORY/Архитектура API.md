### 2. Доменный слой

Важно разбивать на домены композаблы `/composables/users/useUserNames.ts`, в которых расположен весь требуемый API-функционал (CRUD) **без привязки к UI**, это ==только логика загрузки и обработки возвращаемых данных==:

![[Pasted image 20260415141857.png]]

1. обращаемся композаблу `useFetch`^[но не торопимся его вызывать, используя параметр `immediate: false`, это важно!] с обращением к серверному API (*см. п.3*), который имеет преимущества:
	- обладает реактивностью (внутренние поля `{ data, error, status, pending }` и пр. изменяются при изменении результатов запроса);
	- работает через `useAsyncData`;
	- поддерживается SSR - позволяет избежать ошибок гидратации при рендере на сервере и затем на клиенте;
	- кэширует загруженные данные, которые можно использовать на клиенте в композабле `useNuxtData('api-key')`^[важно добавить свойство `key: "api-key"` в запросе `useFetch`, чтобы кэш стал доступным, иначе ключ будет назначен автоматически]; 
	- **МИНУС**: реактивные данные `data` становятся доступны только после инициализации `useFetch`, поэтому могут иногда не успевать за другими действиями (особенно если стоит параметр `immediate: false` - в этом случае данные просто не подтягиваются, т.к. запрос не проводится);
2. если требуется исключить повторную загрузку (кроме принудительной загрузки), можно использовать композабл `useNuxtData`:
	* это реальный источник кэша, доступен в любой момент, где вызывается;
	* **МИНУС**: не обладает реактивностью!
3. обрабатываем полученные данные в соответствии с требованиями (фильтрация, сортировка и пр.);
4. обрабатываем ошибки в зависимости от требований (за исключением ошибок в рамках интерцепторов, например, ошибок авторизации).

### 4. Универсальный слой http-запросов к внешним API 

Это композабл из домена `/composables/api/useApi.ts`, в нем идет обработка всех http-запросов:

![[Pasted image 20260415124917.png]]

1. нормализация возможных ошибок (приведение их к единому виду для последующей обработки в высоких слоях);
2. создание рабочего API-клиента для выполнения http-запроса:
	* для SSR, где не имеем доступа к контексту `useNuxtApp`, используем специальную [[#Фабрика для создания API-клиента|фабрику (интерцепторы) создания API-клиента]] `createApiClient` и передаем внутрь контекст `event` типа H3Event (используемого в серверных хуках и апи в `/server` для отработки в SSR);
	* для клиентской части обращаемся к  [[#Плагин для создания|плагину]], который регистрирует тот же API-клиент из специальной утилиты, добавляющий его в контекст `useNuxtApp` в виде переменной `$api`. Принцип такой же: API-клиент создается аналогичным образом, но без передачи `event` в качестве параметра.
	* использование отдельного пункта для клиентской части необязательно, т.к. в рамках плагина мы все равно обращаемся к той же самой фабрике `createApiClient`, только без передачи `event` в качестве параметра, но для масштабирования проекта плагин полезен.

#### Фабрика для создания API-клиента

> Это утилита, которая позволяет добавить дополнительные настройки в хуках вокруг каждого HTTP-запроса (например, подключить любые данные к запросу, в первую очередь **базовый URL**, **заголовки** и **токены авторизации**, чтобы не дублировать в других местах). Другими словами - это функция расширения ОБЪЕКТА ЗАПРОСА на подмену обычному $fetch. 
> 
> ![[Pasted image 20260415130504.png]]
> 
> 1. добавление базового URL;
> 2. добавление/обработка данных в хуках `onRequest` (заголовки, токены), `onRequestError`, `onResponse`, `onResponseError` (обработки ошибки авторизации при возврате ответа 401) и т.д.

#### Плагин для создания API-клиента на глобальном уровне

> Создается во время инициализации приложения единоразово. Полезно для масштабирования и расширения возможностей приложения. 
> 
> ![[Pasted image 20260415131916.png]]
> 
> 1. позволяет обращаться к нему многократно, не дублируя постоянно одни и те же API-клиенты;
> 2. может использоваться в любом месте напрямую, путем подстановки параметра `$fetch: $api` в любой запрос `useFetch`, минуя серверный API.

## Важные нюансы
1. использование `$fetch` и `useFetch`:

	|где     | что    |
	| --- | --- |
	|  server/api   |   `$fetch`  |
	|  client (pages/composables)   |   `useFetch`  |
		
	💡 ключевая мысль:
	👉`useFetch` =  `$fetch` + SSR + hydration + кэш (`useNuxtData`)^[поэтому в клиентских хуках типа *onMounted* нет смысла использовать `useFetch`, заточенный под SSR]

2. если данная схема используется в авторизации, то при работе в той же сессии, логауте и последующем логине под другим пользователем старые данные могут остаться видимыми. Поэтому важно (на выбор):
	* в ключи запросов `useFetch` всегда передавать не только название запроса, но и код пользователя;
	* при логауте производить очистку кэшированных данных через универсальную и доступную везде функцию `clearNuxtData(key?: string)`, где опциональный параметр - ключ запроса;

3. кэшированные при каждом запросе данные могут быть недостаточными, и тогда используется Pinia. Основные триггеры:
	* данные мутируются;
	* активно используются фильтры, сортировки;
	* часто используются в разных местах;
	* требуют глобального состояния - текущий пользователь (авторизация) / настройки / тема / язык и пр.;
	* данные синхронизируются между различными компонентами;
	* создаются несколько инстансов загруженных данных (при использовании классов и объектов моделей), имеют сложную логику использования;
	* нужен ручной контроль состояния.
