# Аутентификация и авторизация в Vue 3 / Nuxt 3/4

## 1. Три понятия, которые нельзя смешивать

В обычной речи весь процесс входа пользователя часто называют «авторизацией». На техническом собеседовании лучше различать три понятия.

### Authentication — аутентификация

Проверка:

> Кто этот пользователь?

Например, пользователь передал email и пароль, а Backend подтвердил, что это действительно пользователь `id = 42`.

### Authorization — авторизация

Проверка:

> Что этому уже известному пользователю разрешено?

Например:

```text
user
→ просматривать свои заказы

manager
→ просматривать заказы подразделения

admin
→ управлять пользователями
```

### Session — сессия

Механизм, позволяющий серверу узнавать пользователя в последующих HTTP-запросах.

Получается:

```text
login/password
      ↓
AUTHENTICATION
Кто пользователь?
      ↓
создание/восстановление сессии
      ↓
последующие запросы
      ↓
AUTHORIZATION
Что пользователю разрешено?
```

---

# 2. Почему после логина вообще нужна сессия или токен

Пользователь отправляет:

```http
POST /auth/login
```

Backend проверяет пароль:

```text
Да, это user #42.
```

Через секунду браузер делает:

```http
GET /orders
```

HTTP-запрос сам по себе не говорит Backend:

> Это тот же человек, который только что правильно ввёл пароль.

Поэтому необходимо некоторое **доказательство уже пройденной аутентификации**.

Обычно используются:

```text
Session ID
```

или:

```text
Access Token
```

---

# 3. Session-based authentication

При классической серверной сессии Backend после логина создаёт запись:

```text
session abc123
    ↓
userId = 42
```

Браузеру отдаётся только идентификатор:

```http
Set-Cookie: session=abc123
```

При последующих запросах:

```http
Cookie: session=abc123
```

Backend получает ID сессии и определяет пользователя.

```text
Browser
   │
   │ session=abc123
   ▼
Backend
   │
   │ abc123
   ▼
Session Storage
   │
   └── userId = 42
```

Сам пользователь и его права остаются серверной информацией.

---

# 4. Token-based authentication

В другой архитектуре Backend после логина может выдать:

```json
{
  "access_token": "...",
  "refresh_token": "..."
}
```

Это два разных токена.

## Access Token

**Access Token — токен доступа.**

Используется для обычных защищённых API-запросов:

```http
GET /orders

Authorization: Bearer <access_token>
```

Он обычно живёт относительно недолго.

Например:

```text
15 минут
30 минут
1 час
```

Backend получает access token и определяет:

```text
кто пользователь
+
может ли он выполнить операцию
```

## Refresh Token

**Refresh Token — токен обновления.**

Он не предназначен для каждого API-запроса.

Его задача:

```text
access token истёк
        ↓
refresh token
        ↓
/auth/refresh
        ↓
новый access token
```

Refresh token обычно живёт дольше access token и должен защищаться особенно тщательно.

---

# 5. `runtimeConfig` НЕ хранит пользовательские токены

Это важно связать с темой конфигурации Nuxt.

Например:

```ts
runtimeConfig: {
  apiSecret: '',
  apiBase: ''
}
```

может содержать:

```text
apiBase
clientSecret
privateApiKey
applicationSecret
```

Это **конфигурация самого приложения**.

Она известна приложению независимо от конкретного вошедшего пользователя.

А:

```text
accessToken
refreshToken
sessionId
```

— это **динамическое состояние пользовательской сессии**.

Поэтому:

```text
runtimeConfig
≠
хранилище пользовательских токенов
```

Полезная модель:

```text
runtimeConfig
→ Как настроено приложение?


Session / Access Token
→ Кто сейчас пользователь?


Authorization
→ Что этому пользователю разрешено?
```

---

# 6. Где хранить пользовательскую аутентификацию

Технически browser позволяет хранить значения в:

```text
localStorage
sessionStorage
JavaScript memory
Pinia
Cookie
```

Но эти варианты имеют разную модель безопасности.

Для чувствительного authentication credential хороший вариант — **HttpOnly Cookie**.

Например:

```http
Set-Cookie:
authToken=abc123;
HttpOnly;
Secure;
SameSite=Lax;
Path=/
```

### HttpOnly

JavaScript не может прочитать значение cookie.

То есть:

```ts
document.cookie
```

не даст получить эту cookie.

### Secure

Cookie передаётся через HTTPS.

### SameSite

Ограничивает некоторые cross-site сценарии и является частью защиты от **CSRF (Cross-Site Request Forgery — подделки межсайтового запроса)**.

---

# 7. HttpOnly Cookie НЕ находится в localStorage

Это совершенно разные хранилища.

```text
localStorage
→ хранит данные браузера
→ доступен JavaScript


HttpOnly Cookie
→ хранится cookie-механизмом браузера
→ JavaScript не может прочитать значение
→ браузер автоматически отправляет её серверу
```

Поэтому невозможно:

```ts
const token = localStorage.getItem('httpOnlyToken')
```

или:

```ts
const token = document.cookie
```

получить настоящий HttpOnly authentication token.

---

# 8. Как вообще создаётся cookie

Ключевой механизм:

```http
Set-Cookie
```

Сервер отвечает браузеру:

```http
HTTP/1.1 200 OK

Set-Cookie: authToken=abc123; HttpOnly
```

Browser видит этот HTTP-заголовок и сохраняет cookie.

То есть:

```text
Server
  │
  │ Set-Cookie
  ▼
Browser
  │
  └── сохраняет cookie
```

Это важно:

```text
JSON с токеном
≠
Set-Cookie
```

Если Backend просто вернул:

```json
{
  "accessToken": "abc123"
}
```

browser НЕ создаст HttpOnly cookie автоматически.

Кто-то должен сформировать HTTP-заголовок:

```http
Set-Cookie
```

# 9. Три возможные архитектуры авторизации

Именно здесь находилась большая часть нашей путаницы.

Нужно разделять три разных варианта.

---

# 10. Архитектура №1: Browser напрямую вызывает Backend

Самая простая схема:

```text
Browser
   │
   │ POST /auth/login
   ▼
Backend API
```

Backend проверяет логин и пароль и отвечает:

```http
Set-Cookie: authToken=abc123; HttpOnly; ...
```

Ответ получает непосредственно браузер:

```text
Backend
   │
   │ Set-Cookie
   ▼
Browser
```

Browser автоматически сохраняет cookie.

Здесь никакой `$fetch.raw()` в Nuxt не нужен.

Можно сделать:

```ts
await $fetch('https://api.example.com/auth/login', {
  method: 'POST',
  body: {
    login,
    password
  },
  credentials: 'include'
})
```

Если Backend корректно выставляет cookie, browser получает `Set-Cookie` непосредственно.

### Главное

```text
Browser → Backend
Backend → Browser
```

Между ними нет промежуточного Nuxt Server.

Поэтому:

```text
Set-Cookie Backend
        ↓
сразу Browser
```

---

# 11. Архитектура №2: BFF, а cookie создаёт внешний Backend

**BFF (Backend for Frontend — Backend для Frontend)** — серверный слой между frontend-приложением и основным Backend API.

В Nuxt роль BFF может выполнять Nitro/server API.

Здесь login идёт:

```text
Browser
   │
   │ POST /api/auth/login
   ▼
Nuxt Server
   │
   │ POST /auth/login
   ▼
Backend API
```

Теперь существуют **два отдельных HTTP-запроса**.

### Запрос №1

```text
Browser → Nuxt
```

### Запрос №2

```text
Nuxt → Backend
```

И соответственно два ответа:

```text
Backend → Nuxt
```

и:

```text
Nuxt → Browser
```

Это фундаментально важно.

---

# 12. Почему здесь нужен `$fetch.raw()`

Предположим, внешний Backend отвечает:

```http
HTTP/1.1 200 OK

Set-Cookie: authToken=abc123; HttpOnly
```

Кто получил этот ответ?

**Nuxt Server.**

Не Browser.

Получается:

```text
Backend
   │
   │ Set-Cookie
   ▼
Nuxt
```

Browser пока ничего не получил.

Чтобы cookie оказалась в браузере, Nuxt должен взять:

```http
Set-Cookie
```

из ответа Backend и добавить его в **свой собственный ответ браузеру**.

Получается:

```text
Backend
   │
   │ Set-Cookie
   ▼
Nuxt
   │
   │ Set-Cookie
   ▼
Browser
```

Обычный:

```ts
await $fetch(...)
```

в первую очередь возвращает нам body ответа.

Например:

```json
{
  "user": {...}
}
```

Но для login нам требуется ещё HTTP metadata:

```text
response.headers
response.status
Set-Cookie
```

Поэтому используется:

```ts
const response = await $fetch.raw(...)
```

Теперь доступны:

```ts
response._data
response.headers
response.status
```

После этого:

```ts
const cookies = response.headers.getSetCookie()
```

и:

```ts
cookies.forEach(cookie => {
  appendResponseHeader(event, 'set-cookie', cookie)
})
```

передают `Set-Cookie` дальше браузеру.

---

# 13. Почему `requestRaw()` нужен именно в твоей архитектуре

В твоём проекте есть:

```text
request()
```

и:

```text
requestRaw()
```

Их смысл лучше понимать не как:

```text
request
→ обычные запросы

requestRaw
→ авторизация
```

а так:

```text
request()
→ нужен в основном BODY ответа


requestRaw()
→ нужен ПОЛНЫЙ HTTP RESPONSE
```

То есть:

```text
body
status
headers
Set-Cookie
```

Для:

```text
GET /hotels
GET /orders
GET /profile
```

обычно нужен только body.

Поэтому достаточно:

```ts
request()
```

Но для login внешний Backend возвращает важную информацию через:

```http
Set-Cookie
```

Поэтому нужен:

```ts
requestRaw()
```

---

# 14. Полный login flow с `$fetch.raw()`

```text
1. Browser

POST /api/auth/login
login + password

        │
        ▼

2. Nuxt BFF

requestRaw('/auth/login')

        │
        ▼

3. Backend API

проверяет credentials

        │
        ▼

4. Backend → Nuxt

200 OK
Set-Cookie: authToken=...

        │
        ▼

5. Nuxt

requestRaw видит response.headers

достаёт Set-Cookie

appendResponseHeader(
  event,
  'set-cookie',
  cookie
)

        │
        ▼

6. Nuxt → Browser

200 OK
Set-Cookie: authToken=...

        │
        ▼

7. Browser

сохраняет HttpOnly Cookie
```

Это именно то, что делает твой `requestRaw()`.

---

# 15. Что происходит после логина

Cookie уже находится в браузере.

Теперь пользователь делает:

```text
GET /profile
```

Browser автоматически прикладывает:

```http
Cookie: authToken=abc123
```

Получается:

```text
Browser
   │
   │ Cookie: authToken
   ▼
Nuxt
```

На Nuxt Server:

```ts
const token = getCookie(event, 'authToken')
```

получаем токен.

API client добавляет:

```http
Authorization: Bearer abc123
```

и отправляет:

```text
Nuxt
   │
   │ Authorization: Bearer abc123
   ▼
Backend
```

Полная схема:

```text
Browser
   │
   │ HttpOnly Cookie
   ▼
Nuxt BFF
   │
   │ читает Cookie
   │ превращает её в:
   │ Authorization: Bearer ...
   ▼
Backend API
```

Browser никогда не читает значение токена JavaScript-кодом.

---

# 16. Здесь `requestRaw()` уже обычно не нужен

После login Backend возвращает обычные данные:

```json
{
  "name": "Ivan",
  "email": "..."
}
```

Например:

```text
GET /profile
GET /orders
GET /favorites
```

Для них достаточно:

```ts
request()
```

Потому что:

```text
нам нужен body
```

и нет необходимости вручную проксировать `Set-Cookie`.

---

# 17. Архитектура №3: BFF сам создаёт Cookie

Есть ещё один вариант BFF.

И он очень важен.

Backend после login НЕ отвечает `Set-Cookie`.

Вместо этого он возвращает Nuxt:

```json
{
  "accessToken": "abc123",
  "refreshToken": "xyz987"
}
```

Схема:

```text
Browser
   ↓
Nuxt
   ↓
Backend
```

Backend отвечает:

```text
Backend
   │
   │ JSON с token
   ▼
Nuxt
```

Теперь **сам Nuxt** создаёт browser cookie.

Например:

```ts
const auth = await $fetch(...)

setCookie(event, 'authToken', auth.accessToken, {
  httpOnly: true,
  secure: true,
  sameSite: 'lax'
})
```

Получается:

```text
Backend
   │
   │ accessToken в JSON
   ▼
Nuxt
   │
   │ сам создаёт
   │ Set-Cookie
   ▼
Browser
```

---

# 18. Нужен ли здесь `$fetch.raw()`?

Нет, если от Backend тебе нужен только JSON.

Обычного:

```ts
const auth = await $fetch(...)
```

достаточно.

Почему?

Потому что тебе не нужно читать:

```text
response.headers.Set-Cookie
```

Backend вообще не создаёт browser cookie.

Он отдаёт Nuxt данные:

```json
{
  "accessToken": "...",
  "refreshToken": "..."
}
```

А Nuxt сам решает, какую cookie создать.

То есть:

```text
BFF + Backend Set-Cookie
→ нужен raw


BFF + Backend отдаёт token JSON
→ raw обычно НЕ нужен
→ Nuxt сам делает setCookie()
```

Это очень важное различие.

---

# 19. Два BFF-варианта рядом

## Вариант A — Backend владеет Cookie

```text
Browser
   ↓
Nuxt
   ↓
Backend
   │
   │ Set-Cookie
   ▼
Nuxt
   │
   │ ПРОКСИРУЕТ Set-Cookie
   ▼
Browser
```

Нужно:

```ts
$fetch.raw()
```

потому что нужно прочитать response headers Backend.

---

## Вариант B — Nuxt BFF владеет Cookie

```text
Browser
   ↓
Nuxt
   ↓
Backend
   │
   │ JSON:
   │ accessToken
   ▼
Nuxt
   │
   │ setCookie()
   ▼
Browser
```

Обычного:

```ts
$fetch()
```

достаточно.

Nuxt сам формирует `Set-Cookie`.

---

# 20. Какой BFF-вариант архитектурно чище

Если Nuxt действительно должен быть полноценным BFF, второй вариант часто выглядит концептуально чище:

```text
Backend
→ отвечает за authentication/tokens


Nuxt BFF
→ отвечает за browser session/cookies


Browser
→ вообще не знает Backend tokens
```

Backend не обязан знать:

```text
какой домен у frontend
какие cookie нужны браузеру
SameSite
Path
frontend session policy
```

Nuxt сам управляет browser-facing authentication.

Но это не означает, что вариант с проксированием `Set-Cookie` плохой.

Если существующий Backend уже:

```text
авторизует пользователя
+
возвращает правильно настроенные cookies
```

проксирование `Set-Cookie` через BFF — нормальная архитектура.

---

# 21. Прямая архитектура и два BFF-варианта — итоговая таблица

|Архитектура|Кто делает login request к Backend|Кто создаёт `Set-Cookie` для Browser|Нужен `$fetch.raw()` в Nuxt|
|---|---|---|---|
|Browser → Backend|Browser|Backend|Нет|
|Browser → Nuxt → Backend, Backend возвращает `Set-Cookie`|Nuxt|Backend, Nuxt проксирует|**Да**|
|Browser → Nuxt → Backend, Backend возвращает token JSON|Nuxt|**Nuxt**|Обычно нет|

Это одна из главных таблиц конспекта.

# 22. Почему браузер потом отправляет Cookie автоматически

После того как cookie была сохранена:

```text
Browser
└── authToken=...
```

при подходящих запросах Browser сам добавляет:

```http
Cookie: authToken=...
```

Поэтому после login:

```text
Browser
   │
   │ Cookie
   ▼
Nuxt
```

не требует `requestRaw`.

`requestRaw()` нужен не для **чтения входящей cookie**, а для особого случая:

> Nuxt получил `Set-Cookie` от другого сервера и должен перенести его в собственный HTTP-ответ браузеру.

Это два противоположных направления:

```text
LOGIN

Backend
   │ Set-Cookie
   ▼
Nuxt
   │ Set-Cookie
   ▼
Browser

↑ здесь может понадобиться raw
```

против:

```text
ПОСЛЕ LOGIN

Browser
   │ Cookie
   ▼
Nuxt
   │ Authorization
   ▼
Backend

↑ здесь browser отправляет cookie автоматически
```

# 23. `$fetch` или `useFetch` при Login

Сам login обычно является пользовательским действием:

```text
ввёл login/password
        ↓
нажал кнопку
        ↓
POST /login
```

Поэтому хороший default:

```ts
await $fetch('/api/auth/login', {
  method: 'POST',
  body: credentials
})
```

`useFetch` здесь обычно не нужен.

`useFetch` особенно полезен для данных, связанных с рендерингом:

```ts
const { data: user } =
  await useFetch('/api/auth/me')
```

Потому что он интегрирован с:

```text
SSR
Nuxt payload
hydration
reactive state
```

Упрощённое правило:

```text
$fetch
→ действие пользователя
→ login
→ logout
→ submit
→ create/update/delete


useFetch
→ данные страницы
→ profile
→ orders
→ current user
→ SSR + SPA
```

Это не абсолютный запрет, а хороший архитектурный default.

---

# 24. SSR и уже существующая авторизация

**SSR (Server-Side Rendering — серверный рендеринг)** не означает, что login выполняется на сервере автоматически.

Сам login происходит после пользовательского действия.

Но если cookie уже существует, пользователь может открыть:

```text
/account
```

Browser запрашивает страницу:

```text
Browser
   │
   │ GET /account
   │ Cookie: authToken
   ▼
Nuxt Server
```

Nuxt уже на этапе SSR может определить пользователя.

Например:

```ts
const { data: user } =
  await useFetch('/api/auth/me')
```

И сформировать HTML сразу в авторизованном состоянии.

---

# 25. SPA-навигация

**SPA (Single Page Application — одностраничное приложение)** навигация — переход между страницами без полной перезагрузки документа.

Например:

```text
/account
   ↓
/orders
```

На `/orders`:

```ts
const { data } = await useFetch('/api/orders')
```

Browser делает:

```text
Browser
   │
   │ /api/orders
   │ Cookie автоматически
   ▼
Nuxt
   │
   │ Authorization Bearer
   ▼
Backend
```

То есть одна и та же auth-система работает:

```text
hard reload
+
SSR
+
SPA navigation
```

Без необходимости читать token в Vue-компоненте.

# 26. Что хранить в Pinia

Pinia хорошо подходит для:

```text
user
isAuthenticated
roles
permissions
profile
```

Например:

```ts
authStore.user
authStore.isAuthenticated
```

Но если authentication построена на HttpOnly Cookie, необязательно и нежелательно дублировать сам токен:

```text
authToken
refreshToken
```

в Pinia.

Хорошее разделение:

```text
Cookie / server session
→ доказательство аутентификации


Pinia
→ frontend state пользователя
```

# 27. Access Token + Refresh Token

Если Backend использует пару:

```text
accessToken
refreshToken
```

то access token используется для:

```http
Authorization: Bearer ...
```

А refresh token — для:

```text
получения нового access token
```

при истечении старого.

Схема:

```text
Request
   ↓
Backend
   ↓
401 access token expired
   ↓
refresh
   ↓
new access token
   ↓
retry original request
```

Важно не создавать:

```text
401
→ refresh
→ retry
→ 401
→ refresh
→ ...
```

Исходный запрос должен повторяться ограниченно.

Если refresh token также недействителен:

```text
session ended
→ logout
→ /login
```

# 28. XSS и CSRF

**XSS (Cross-Site Scripting)** — внедрение вредоносного JavaScript.

Если token находится в:

```text
localStorage
Pinia
JavaScript memory
```

вредоносный JS потенциально может его прочитать.

HttpOnly Cookie делает **чтение значения через JavaScript невозможным**.

Но HttpOnly Cookie не решает всё.

Поскольку browser отправляет cookie автоматически, необходимо учитывать:

**CSRF (Cross-Site Request Forgery)** — попытку другого сайта заставить браузер выполнить авторизованный запрос.

Поэтому используются:

```text
SameSite
Secure
CSRF tokens при необходимости
проверка Origin/Referer в соответствующих архитектурах
```

Главная мысль:

```text
HttpOnly
→ снижает риск кражи token через XSS

SameSite / CSRF protection
→ снижает риск подделки запросов
```

  return navigateTo('/login')

# 32. Главное правило про `raw`

Не запоминай:

> Для авторизации всегда нужен `raw`.

Это неправильно.

Запомни:

> **`raw` нужен тогда, когда Nuxt должен анализировать или проксировать HTTP metadata ответа Backend — например `Set-Cookie`.**

Поэтому:

```text

        +
между Backend и Browser есть Nuxt BFF
        ↓

```

А:

```text

        +
Nuxt сам делает setCookie()
        ↓
raw обычно не нужен
```

И:

```text
Browser вызывает Backend напрямую
        +
Backend сам делает Set-Cookie
        ↓
raw в Nuxt вообще не нужен
```

# 33. Как восстанавливается авторизация при SSR после hard reload

Одна из ключевых идей, которую важно понимать в Nuxt:

> **HttpOnly Cookie физически хранится в браузере, но при полном HTTP-запросе страницы браузер автоматически отправляет подходящую cookie Nuxt-серверу. Поэтому Nuxt может восстановить пользовательскую сессию ещё до того, как HTML будет отправлен клиенту.**

Представим, что пользователь уже авторизован и в браузере сохранена cookie:

```text
authToken=...
```

с флагом:

```text
HttpOnly
```

Пользователь делает hard reload страницы:

```text
/account
```

Browser отправляет HTTP-запрос:

```text
Browser
   │
   │ GET /account
   │ Cookie: authToken=...
   ▼
Nuxt Server
```

То есть HttpOnly Cookie не остаётся «только внутри браузера».

JavaScript действительно не может прочитать её значение, но сам браузер умеет автоматически добавлять подходящие cookies в HTTP-запрос.

Важно: отправляются не буквально все cookies браузера, а только те, которые подходят запросу по таким параметрам, как:

```text
Domain
Path
Secure
SameSite
срок действия
```

Для обычной auth-cookie Nuxt-приложения схема выглядит так:

```text
Hard reload
      ↓
Browser отправляет GET страницы
      ↓
auth HttpOnly Cookie прикладывается автоматически
      ↓
Nuxt Server получает запрос вместе с Cookie
      ↓
Nuxt во время SSR читает authentication credential
      ↓
делает авторизованный запрос к Backend API
      ↓
Backend проверяет session / access token
      ↓
если credential валиден — возвращает данные
      ↓
Nuxt рендерит страницу уже как авторизованную
      ↓
Browser получает готовый HTML
      ↓
Hydration
```

Например, Nuxt может во время SSR получить текущего пользователя:

```ts
const { data: user } = await useFetch('/api/auth/me')
```

В BFF-архитектуре запрос концептуально проходит так:

```text
Browser
   │
   │ GET /account
   │ Cookie: authToken
   ▼
Nuxt SSR
   │
   │ /api/auth/me
   ▼
Nuxt server/api
   │
   │ читает authToken
   │
   │ Authorization: Bearer <token>
   ▼
Backend API
   │
   │ проверяет token
   ▼
user data
   │
   ▼
Nuxt SSR
   │
   │ рендерит HTML
   ▼
Browser
```

Повторного login/password при этом нет.

Пользователь **не проходит аутентификацию заново через форму**. Сервер просто проверяет уже существующее доказательство ранее выполненной аутентификации:

```text
sessionId
или
accessToken
```

Если токен или сессия валидны:

```text
SSR
→ user известен
→ защищённые данные могут быть получены
→ HTML рендерится сразу в авторизованном состоянии
```

Если credential истёк или недействителен:

```text
SSR
→ Backend возвращает 401
→ возможен refresh flow
→ либо пользователь считается неавторизованным
```

## Почему это особенно удобно при BFF

**BFF (Backend for Frontend)** означает, что Browser работает прежде всего с Nuxt Server:

```text
Browser
   ↓
Nuxt
   ↓
Backend
```

Если auth-cookie принадлежит Nuxt-приложению, при hard reload она приходит непосредственно Nuxt Server вместе с запросом страницы.

Поэтому Nuxt может восстановить пользователя ещё на SSR:

```text
Browser
   │ Cookie
   ▼
Nuxt SSR
   │ authentication известна
   ▼
Backend API
```

При прямой архитектуре:

```text
Browser
   ↓
Backend API
```

может возникнуть другая ситуация: cookie принадлежит только домену Backend API, а запрос HTML идёт на другой origin с Nuxt.

Например:

```text
frontend.example.com
api.example.com
```

Тогда Backend cookie может отправляться на:

```text
api.example.com
```

но не отправляться на:

```text
frontend.example.com
```

В таком случае Nuxt SSR не обязательно сможет определить пользователя при первоначальном запросе страницы.

Тогда возможна схема:

```text
SSR
→ user пока неизвестен
→ HTML как для guest

Hydration
→ Browser выполняет запрос к Backend
→ Browser отправляет Backend cookie
→ user определяется уже на клиенте
```

Поэтому для SSR-приложений BFF часто упрощает восстановление authentication state.

## Ключевая формула для памяти

> **HttpOnly означает «JavaScript не может прочитать cookie», а не «cookie существует только на клиенте».**

При HTTP-запросе браузер сам передаёт подходящую cookie серверу.

Поэтому:

```text
HttpOnly Cookie в Browser
        ↓
hard reload
        ↓
Cookie приходит Nuxt Server
        ↓
Nuxt SSR восстанавливает session
        ↓
Backend проверяет token
        ↓
готовый авторизованный HTML
```

Именно поэтому уже существующая пользовательская авторизация может полноценно работать во время SSR.

# 34. Ответ на Senior-собеседовании: зачем `$fetch.raw()` при BFF login

**Этот ответ стоит выучить практически целиком:**

> Если Nuxt выступает BFF и сам вызывает Backend API, то ответ Backend с `Set-Cookie` сначала приходит на сервер Nuxt, а не в браузер. Поэтому серверный слой должен явно прокинуть `Set-Cookie` в ответ клиенту. Для этого нужен доступ к полному HTTP response, например через `$fetch.raw()`. Если же браузер обращается напрямую к Backend API, то `Set-Cookie` приходит непосредственно браузеру, и дополнительное проксирование не требуется.

Если интервьюер спросит про второй BFF-вариант, можно добавить:

> Если Backend вместо `Set-Cookie` возвращает access/refresh tokens в body, а cookie создаёт уже сам Nuxt BFF через `setCookie`, `$fetch.raw()` для этой задачи не требуется — достаточно обычного `$fetch`, поскольку нам не нужно получать response headers Backend.

Это уже очень сильный ответ.

# 35. Senior-вопрос: «Как спроектировать Authentication в Nuxt?»

Хороший ответ:

> Сначала я определю границу между Browser, Nuxt Server и Backend API. Если Nuxt используется как BFF, browser работает только с Nuxt endpoints, а server-side слой занимается Backend authentication. Для browser session я предпочту HttpOnly, Secure и подходящую SameSite cookie, чтобы JavaScript не имел прямого доступа к credentials.
> 
> Далее архитектура зависит от контракта Backend. Если Backend сам возвращает `Set-Cookie`, Nuxt BFF должен получить полный response и проксировать этот заголовок браузеру; для этого удобно использовать `$fetch.raw()`. Если Backend возвращает tokens в JSON, Nuxt может самостоятельно создать HttpOnly cookie, и `raw` для этого не нужен.
> 
> При последующих запросах browser автоматически отправляет cookie Nuxt Server, Nuxt восстанавливает authentication context и при необходимости передаёт Backend access token через `Authorization`. Это работает одинаково для SSR и SPA-навигации. Pinia при этом хранит user/UI state, но не обязана содержать чувствительные credentials. Окончательная authorization всегда выполняется Backend.

# 38. Пять фраз, которые нужно запомнить

1. **HttpOnly Cookie сохраняется браузером после получения HTTP-заголовка `Set-Cookie`.**
    
2. **Если Backend отвечает непосредственно Browser — browser получает `Set-Cookie` сам, никакой `raw` в Nuxt не нужен.**
    
3. **Если между Browser и Backend находится Nuxt BFF, Backend response получает Nuxt, поэтому Backend `Set-Cookie` нужно явно перенести в Nuxt response.**
    
4. **`$fetch.raw()` нужен не потому, что запрос является авторизационным, а потому, что нам нужны headers/status полного HTTP response.**
    
5. **Если Nuxt BFF сам получает token из Backend JSON и сам создаёт HttpOnly Cookie через `setCookie()`, `$fetch.raw()` для cookie уже не требуется.**
    

Это и есть основная модель, вокруг которой стоит строить понимание authentication в твоей текущей Nuxt-архитектуре.
