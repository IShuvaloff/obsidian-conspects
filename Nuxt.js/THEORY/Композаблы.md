# Vue / Nuxt Composables — краткий архитектурный конспект

## 1. Что такое composable

**Composable** — функция, инкапсулирующая переиспользуемую **stateful/reactive логику** Vue.

Используется для:

- хранения локального реактивного состояния;
- computed-логики;
- watchers;
- lifecycle hooks;
- side effects;
- композиции нескольких логических блоков.

Пример:

```ts
export function usePagination() {
  const page = ref(1)

  const next = () => page.value++

  return {
    page,
    next
  }
}
```

---

# 2. Основные типы composables

|Тип|Где хранится state|Когда использовать|
|---|---|---|
|Local composable|внутри функции `ref()`|независимое состояние каждого вызова|
|Shared composable|module-level state / `useState()`|общее состояние приложения|
|Pinia store|через `defineStore()`|глобальный domain/application state|

---

# 3. Factory composable и closure

Типичный composable:

```ts
export function useCounter() {
  const count = ref(0)

  function increment() {
    count.value++
  }

  return {
    count,
    increment
  }
}
```

Это одновременно:

- **factory** — каждый вызов создаёт новый экземпляр;
- **closure** — `increment()` замыкает переменную `count`.

Например:

```ts
const a = useCounter()
const b = useCounter()
```

Получаем:

```ts
a.count !== b.count
```

# 4. Composable с параметрами

Composable может принимать:

- обычные значения;
- `ref`;
- computed;
- getter.

Лучше проектировать гибко.

```ts
// composables/useHotel.ts

export function useHotel(
  id: MaybeRefOrGetter<number>
) {
  const hotel = ref<Hotel | null>(null)
  const loading = ref(false)

  async function loadHotel(id: number) {
    loading.value = true

    try {
      hotel.value = await $fetch(`/api/hotels/${id}`)
    } finally {
      loading.value = false
    }
  }

  watch(
    () => toValue(id),
    newId => loadHotel(newId),
    { immediate: true }
  )

  return {
    hotel,
    loading,
    loadHotel
  }
}
```

Использование:

```ts
const route = useRoute()

const hotelId = computed(() =>
  Number(route.params.id)
)

const {
  hotel,
  loading
} = useHotel(hotelId)
```

### Что происходит

```
hotelId
   ↓
useHotel(hotelId)
   ↓
watch следит за hotelId
   ↓
loadHotel(newId)
   ↓
$fetch(...)
   ↓
hotel.value = результат
```

`toValue(id)` позволяет принимать разные типы параметров:

```ts
useHotel(10)                 // обычное значение
useHotel(ref(10))            // Ref
useHotel(computed(() => 10)) // ComputedRef
useHotel(() => 10)           // getter
```

Если `id` реактивный и изменится, `watch` загрузит новый отель.

Для такого случая я предпочёл бы именно `watch`, а не `watchEffect`: **мы явно знаем, за какой зависимостью следим**.

Ключевая мысль:

> `MaybeRefOrGetter + toValue()` позволяет сделать composable универсальным: он принимает как обычное значение, так и реактивный источник.

Идея:

> Хороший composable умеет работать не только с примитивами, но и с реактивными источниками данных.

# 5. Возврат ref / reactive из composable

## ref (рекомендуемый стиль)

```ts
export function useHotels() {

  const hotels = ref([])

  const loading = ref(false)

  return {
    hotels,
    loading
  }
}
```

Можно:

```ts
const {
  hotels,
  loading
} = useHotels()
```

✅ Реактивность сохраняется.

Проблема появляется не с `ref`, а с `reactive`.

---

## reactive

```ts
const state = reactive({
  count: 0
})

return state
```

После:

```ts
const { count } = useCounter()
```

❌ связь теряется.

Причина:

```ts
const count = state.count
```

получается обычное значение.

---

# 6. Pinia и destructuring

Store:

```ts
const store = useHotelsStore()
```

Правильно:

```ts
store.hotels
store.loading
```

Если нужно destructuring:

```ts
const {
  hotels,
  loading
} = storeToRefs(store)
```

Почему?

Pinia store — reactive object.

`storeToRefs()` превращает его свойства в refs.

# 7. Composable vs Directive

Это разные уровни абстракции.

| |Composable|Directive|
|---|---|---|
|Для чего|Reactive/stateful логика|Поведение конкретного DOM-элемента|
|Главная задача|stateful behavior|low-level DOM behavior|
|Где используется|`<script setup>`|template|
|Типичные инструменты|`ref`, `computed`, `watch`, lifecycle|`el`, DOM API|
|Пример|`useVisibility()`|`v-focus`|

## Composable

Нужен, если результат поведения используется дальше в логике компонента:

```ts
const target = ref(null)

const { isVisible } = useVisibility(target)
```

```html
<div ref="target">
  {{ isVisible }}
</div>
```

Здесь `isVisible` — реактивное состояние.

## Directive

Нужна, если надо просто применить поведение к элементу:

```ts
export default {
  mounted(el: HTMLInputElement) {
    el.focus()
  }
}
```

```
<input v-focus>
```

## Правило выбора

```
Нужен reactive state / логика
        → composable

Нужно поведение DOM-элемента
        → directive
```

Некоторые задачи можно решить обоими способами (`click-outside`, `intersection`, `tooltip`), но **composable удобнее для логики, directive — для декларативного DOM-поведения**.

# 💡Composables — 10 вопросов для Senior-собеседования

## 1. Что такое composable и чем он отличается от utility?

**Composable** — функция, инкапсулирующая и переиспользующая логику, связанную с Vue reactivity или Vue/Nuxt context: `ref`, `computed`, `watch`, lifecycle, stores, router и другие composables.

**Utility** обычно stateless: получает входные данные, преобразует их и возвращает результат, не завися от Vue.

```
Composable → reactive/stateful behavior
Utility    → input → transformation → output
```

---

## 2. Будет ли state обычного composable общим между вызовами?

Нет, если state создаётся внутри функции:

```ts
export function useCounter() {
  const count = ref(0)
  return { count }
}
```

Каждый `useCounter()` создаёт новый `ref`.

Методы внутри composable используют **closure** над state конкретного вызова.

Для shared state:

- `useState()` — небольшой Nuxt shared state;
- Pinia — полноценный application/domain state.

---

## 3. Почему можно деструктурировать `ref`, но опасно деструктурировать `reactive`?

Если composable возвращает:

```ts
const count = ref(0)

return { count }
```

то:

```ts
const { count } = useCounter()
```

получает тот же `Ref`-объект, поэтому реактивность сохраняется.

С `reactive`:

```ts
const state = reactive({ count: 0 })

const { count } = state
```

`count` становится обычным значением, отделённым от Proxy.

```
ref → destructuring безопасен
reactive property → destructuring ломает связь с Proxy
```

---

## 4. Почему для Pinia нужен `storeToRefs()`?

Pinia store — reactive object.

Поэтому:

```ts
const { hotels } = store
```

может потерять реактивную связь.

Используем:

```ts
const { hotels, loading } = storeToRefs(store)
```

Actions можно использовать напрямую:

```ts
store.loadHotels()
```

или деструктурировать:

```ts
const { loadHotels } = store
```

`storeToRefs()` нужен для **state и getters**, но не для methods/actions.

---

## 5. Как разделять Utils / API / Services / Store / Composable / Component?

|Слой|Ответственность|Hotels-пример|
|---|---|---|
|Utils|чистое преобразование|`filterHotelsByStars()`|
|API|взаимодействие с backend|`fetchHotels()`|
|Service|бизнес-сценарий / orchestration|`prepareHotelBooking()`|
|Store|shared state + actions + getters|`useHotelsStore()`|
|Composable|reactive behavior|`useHotelSearch()`|
|Component|отображение/UI|`HotelsList.vue`|

Принцип:

```
чистое вычисление → Utils
HTTP → API
use case → Service
shared state → Store
Vue reactive behavior → Composable
UI → Component
```

---

## 6. Что произойдёт при нескольких вызовах обычного `useHotels()`?

```ts
export function useHotels() {
  const hotels = ref([])
  const loadHotels = async () => { ... }

  return { hotels, loadHotels }
}
```

Каждый вызов создаёт независимый `hotels`.

Сам по себе вызов:

```ts
const { hotels, loadHotels } = useHotels()
```

ничего не загружает — `loadHotels()` ещё нужно вызвать.

Если список должен быть единым для приложения, лучше использовать Pinia:

```ts
const hotelsStore = useHotelsStore()
```

или для простого случая — `useState()`.

---

## 7. Почему module-level `ref` опасен при SSR?

Опасный вариант:

```ts
const user = ref(null)

export function useUser() {
  return { user }
}
```

Переменная создаётся на уровне ES-модуля и может жить в памяти Node.js между HTTP-запросами.

Получается риск:

```
Request User A
      ↓
shared server memory
      ↑
Request User B
```

Для пользовательских данных это может привести к **cross-request state leakage**.

Используем SSR-safe `useState()` или корректно интегрированную Pinia.

---

## 8. Почему `onMounted()` не подходит для SSR data fetching?

```ts
onMounted(() => {
  loadHotels()
})
```

`onMounted()` существует в SSR-приложении, но **на сервере не выполняется**.

Следовательно, сервер отдаст HTML без этих данных, а запрос начнётся после гидратации клиента.

Для данных, нужных при SSR, обычно применяют:

```ts
useFetch()
```

или:

```ts
useAsyncData()
```

Они интегрированы с SSR и Nuxt payload.

---

## 9. Зачем composable принимать `MaybeRefOrGetter`?

Например:

```ts
function useHotel(
  id: MaybeRefOrGetter<number>
)
```

Это позволяет передать:

```ts
useHotel(10)
useHotel(ref(10))
useHotel(computed(() => 10))
useHotel(() => 10)
```

`toValue(id)` получает текущее значение независимо от типа источника.

Для реактивного параметра:

```ts
watch(
  () => toValue(id),
  newId => loadHotel(newId),
  { immediate: true }
)
```

Если `id` изменится, например при SPA-навигации, composable автоматически выполнит нужную операцию повторно.

## 10. Как организовать много composables в большом Nuxt-проекте?

Группировать преимущественно по **feature/domain**:

```
composables/
├── hotels/
│   ├── useHotelSearch.ts
│   └── useHotelFilters.ts
│
├── booking/
│   ├── useBooking.ts
│   └── useBookingPrice.ts
│
└── common/
    ├── usePagination.ts
    └── useModal.ts
```

Для вложенных директорий можно явно настроить auto-import:

```ts
imports: {
  dirs: [
    'composables/hotels',
    'composables/booking',
    'composables/common',
  ]
}
```

Явный список директорий предпочтительнее бесконтрольного `composables/**`: структура и публичные зависимости проекта остаются понятными и предсказуемыми.
