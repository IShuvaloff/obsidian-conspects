==Реактивность во Vue 3== — это автоматическая система отслеживания зависимостей. Она построена на базе встроенного в JavaScript объекта **`Proxy`** и паттерна **«Publisher-Subscriber»**.

Система работает за счет трех сущностей: **Proxy** (перехватчик), **Track** (сборщик зависимостей) и **Trigger** (запускатор обновлений).

# Часть 1. Три этапа работы реактивности (`Proxy`, `Track`, `Trigger`)

### 1. Инициализация (Создание Proxy)

Когда мы пишем `reactive(obj)` или `ref(obj)`, Vue превращает объект в `Proxy`. Это обертка-перехватчик, которая шпионит за объектом. Она перехватывает две операции:

- Чтение любого свойства объекта (ловушка `GET`).
- Изменение любого свойства объекта (ловушка `SET`).

### 2. Сбор зависимостей (`Track`)

Когда Vue начинает собирать HTML-шаблон (рендерить компонент), он запускает этот процесс в специальном контексте «эффекта».

- Шаблон читает переменную: `state.count`.
- Proxy перехватывает это чтение (`GET`) и вызывает функцию **`track()`**.
- `track()` смотрит, какой компонент сейчас рендерится, и записывает его в глобальный реестр зависимостей `targetMap` типа `WeakMap`, в которой ключом является ref-переменная (в т.ч. может быть и объект), а значением - список компонентов-подписчиков (при очистке списка сборщик мусора JS полностью удаляет из `targetMap` эту запись, исключая утечку памяти);
- _Итог фазы:_ Vue четко зафиксировал связь: **«Компонент Х зависит от переменной count»**.

### 3. Запуск обновлений (`Trigger`)

Когда в коде происходит изменение данных (например, по клику на кнопку): `state.count = 5`.

- Proxy перехватывает эту запись (`SET`) и вызывает функцию **`trigger()`**.
- `trigger()` мгновенно открывает реестр зависимостей, находит там измененную переменную `count` и смотрит список её «подписчиков».
- Vue находит там наш Компонент Х и отправляет ему команду на перерисовку.

# Часть 2. Как работает цепочка зависимостей с `Computed`

Свойство [[Computed-свойства|computed]] уникально: оно одновременно является и **подписчиком** (зависит от исходных данных), и **издателем** (от него зависит шаблон компонента).

Представим цепочку: `Шаблон компонента ➡️ зависит от computed (double) ➡️ зависит от ref (count)`.

### 🔄 Фаза 1: Первая отрисовка страницы

1. Компонент начинает рендериться и читает значение `double`. Функция `track()` записывает: **Компонент зависит от `double`**.
2. В этот же миг `computed` запускает свою внутреннюю функцию вычисления (`count * 2`).
3. В процессе вычисления код читает исходный `count`. Срабатывает Proxy переменной `count`. Функция `track()` записывает: **`double` зависит от `count`**.
4. Значение вычисляется, сохраняется в кэш `computed`, а страница успешно отрисовывается.

### ⚡ Фаза 2: Изменение исходных данных (`count = 5`)

1. Мы меняем исходный `count`. Включается функция `trigger()`.
2. Vue видит в реестре, что от `count` зависит `double`. Он идет к `computed` и говорит: _«Исходные данные изменились. Сбрось свой кэш»_.
3. `computed` сбрасывает кэш (помечает себя как «грязный»), но **не пересчитывает математику сразу**, оставляет это *на момент следующего чтения* (здесь используются ленивые вычисления, lazy evaluation);
4. Волна обновлений идет по реестру дальше: Vue видит, что от `double` зависит Компонент, и пинает Компонент на перерисовку.
5. Компонент перерисовывается, снова запрашивает `double`. Тот видит, что кэш пуст, быстро пересчитывает значение, отдает его в HTML и снова кэширует.

# Часть 3. Различия между `ref` от `reactive`

### 1. Техническая база (различия на уровне ядра)

Нативный JavaScript-объект `Proxy` имеет жесткое ограничение: он может оборачивать **только объекты** `{}`. Обычную строку, число или boolean (примитивы) обернуть в `Proxy` невозможно.

- **`reactive`** — это чистый `Proxy`. Он работает только со сложными объектами.
- **`ref`** — это специальный класс-обертка. Vue создает объект с единственным полем `{ value: ... }`.
    - Если мы передаем в `ref` примитив (число, строку), Vue отслеживает его чтение и запись через стандартные геттеры и сеттеры этого поля `.value`.
    - Если мы передаем в `ref` объект, то Vue берет это поле `.value` и внутренне прогоняет его через `reactive()`, превращая в `Proxy`.

Поэтому `ref` — это универсальный инструмент, который сам решает, как отслеживать данные в зависимости от их типа.

### 2. Почему в реальной практике `reactive` НЕ нужен (Главный аргумент)

В современной разработке (Vue 3 / Nuxt 3) от ручного написания `reactive` массово отказываются по трем причинам:

1. **Консистентность (однообразие) кода:** Когда всё объявлено через `ref()`, у разработчика нет ментальной нагрузки «что выбрать». Код пишется одинаково.
2. **Проблема деструктуризации:** Если разбить `reactive`-объект на переменные (например, `const { name } = state`), реактивность **сломается**. Чтобы безопасно деструктурировать объект и сохранить реактивность (но после этого к переменным все равно добавятся `.value`, так что об удобстве `reactive` можно забыть), нужно использовать:
	- **`toRefs(переменная)`** — для обычных `ref`/`reactive` в компонентах.
	- **`storeToRefs(store)`** — для хранилищ Pinia. Но в п.3 добавляется удобство использования.
3. **Синтаксический сахар Pinia:** Главный плюс `reactive` — отсутствие раздражающего `.value`. Но хранилище **Pinia берет эту рутину на себя** (которое сейчас является официальным вместо Vuex). Мы пишем `ref()` внутри стора, а Pinia под капотом превращает его в `reactive`. В итоге в компонентах мы пишем чистый код `store.hotels` без `.value`, вообще не объявляя `reactive` руками.

### 3. «А есть ли минусы у ref?»

Если тимлид спросит: _"Ну хорошо, а в каких редких случаях `ref` может вести себя хуже, чем `reactive`?"_ — отвечай честно и открыто, это покажет твою зрелость:

> *"В теории, в документации пишут, что `reactive` лучше дружит со сторонними тяжелыми JS-библиотеками (вроде карт или графиков), потому что он передает чистый Proxy, а `ref` передает обертку со свойством `.value`. Из-за этого при копировании объекта внутри чужой библиотеки Vue якобы может потерять триггеры обновления. *
> 
> _Но скажу честно: я на практике в проектах с такими специфическими библиотеками не сталкивался. В моих задачах (работа с API, вывод списков, фильтрация, формы, корзины) связка `ref` + `Pinia` полностью закрывал все вопросы реактивности.

# Часть 4. Замена `ref` на `useState` в SSR

📌 Главное отличие (Коротко)

- **`ref()`** — стандартный инструмент Vue 3. Живет изолированно в памяти того окружения, где запустился. Ничего не знает про перенос данных между сервером и браузером.
- **`useState()`** — SSR-безопасная обертка над `ref` от команды Nuxt 3. Умеет **сериализовать** (сохранять в скрытый JSON внутри HTML) данные на сервере и автоматически «воскрешать» их в браузере во время гидратации.

### 🚨 Три правила использования (Где и что выбирать)

1. В локальных UI-компонентах (Кнопки, Инпуты, Модалки)

	- **Что использовать:** `ref()`
	- **Почему:** Если состояние компонента нужно только на клиенте (например, `const isOpen = ref(false)` для выпадающего меню), серверный рендеринг на него не влияет. Использовать здесь `useState` — избыточно и бессмысленно.

2. На страницах (`/pages`) при загрузке данных с сервера

	- **Что использовать:** 
		- `useState()` + хук `await callOnce('key', () => { store.getRandom(10); })` для получения недетерминированных данных: *рандомных списков*, *дат*, *случайных ID* или встроенный `useFetch()` для получения их с бэка (который под капотом сам создает `useState`);
		- `ref` для технических локальных переменных;
	- **Почему:** Если использовать обычный `ref()`, то данные, загруженные на сервере Node.js, **потеряются** при запуске кода в браузере. Произойдет _Hydration Mismatch_ (ошибка гидратации) — интерфейс моргнет, а браузер будет вынужден делать повторный дублирующий API-запрос на бэкенд. `useState` перенесет данные с сервера на клиент без повторных запросов.

3. В глобальных Composables (Общее состояние приложения)

	- **Что использовать:** `useState()` внутри функции (композабла, возвращающего это состояние) или **Pinia**.
	- **Смертельная опасность `ref`:** Если объявить `const user = ref(null)` на корневом уровне файла (вне функций) в composable, этот реф зависнет в **общей памяти сервера Node.js**. Когда авторизуется Вася, его данные запишутся в этот глобальный `ref`. Следующий зашедший пользователь (Петя) получит HTML-страницу с данными Васи. Это называется **утечкой состояния между запросами** (Cross-Request State Pollution).
	- **Как спасает `useState`:** Он привязывается к контексту конкретного HTTP-запроса. Для каждого пользователя Nuxt создает изолированную ячейку памяти по уникальному ключу: `useState('user-session', () => null)`. Данные Васи и Пети никогда не пересекутся.
	- **Исключение (Pinia):** Внутри `defineStore` использовать `ref()` **можно и нужно**. Pinia в Nuxt 3 сама изолирует хранилища для каждого запроса и под капотом использует механизмы, аналогичные `useState`.


### 💡 Шпаргалка для собеседования: Как отвечать на вопрос про `useState`

> _«В Nuxt 3 обычный `ref()` на страницах или в composable может привести к двум проблемам SSR: потере данных при гидратации (клиент не увидит то, что отрендерил сервер) или к утечке данных между пользователями в общей памяти Node.js._
> 
> _`useState()` — это SSR-безопасный аналог `ref`. Он принимает уникальный ключ и автоматически прокидывает состояние с сервера на клиент через сериализацию в HTML. Я использую его для локального стейта страниц, зависящего от сервера, или в composables для шеринга данных. Если же в проекте есть Pinia, я пишу `ref()` внутри сторов, так как Pinia сама берет на себя всю изоляцию и SSR-гидратацию под капотом»_.

# Часть 5. `nextTick` и ререндеринг проксированных данных

**Вопрос интервьюера:** Как работает планировщик обновлений во Vue и зачем нужен `nextTick()`?

> **Ваш ответ:**  
> _«Vue не обновляет интерфейс мгновенно при каждом изменении реактивных данных. Вместо этого он использует **батчинг (группировку)**. Когда данные меняются, функция `trigger()` не перерисовывает DOM сразу, а ставит задачу на обновление компонента в очередь микрозадач JavaScript._
> 
> _Благодаря этому, если мы изменим переменную 100 раз подряд в одном цикле, Vue выполнит тяжелую перерисовку интерфейса всего один раз, когда синхронный код завершится._
> 
> _Из-за этой асинхронности, если мы попытаемся прочитать данные напрямую из DOM сразу после изменения реактивной переменной, мы увидим старый HTML. Чтобы дождаться реального обновления экрана, используется хук **`nextTick()`**. Он возвращает промис, который разрешается (`resolve`) ровно в тот момент, когда Vue успешно очистил очередь микрозадач и применил изменения к DOM»_.

==Пример==:
```html
<template> 
	<p ref="textRef">{{ count }}</p> 
</template>

<script setup>
const count = ref(0); 
const textRef = ref(null);

async function updateAndLog() { 
	count.value = 1000; 
	// Ждем, пока Vue выполнит свою микрозадачу и обновит DOM, иначе был бы выведен 0!
	await nextTick(); 
	console.log(textRef.value.innerText); // Теперь железно выведет "1000"! 
}
</script>
```

# Хук callOnce

`callOnce` — это composable Nuxt для выполнения кода только один раз. Он особенно полезен при SSR и гидратации, чтобы избежать повторной загрузки данных или повторной инициализации. Чаще всего используется вместе с Pinia для вызова действий (`actions`) вроде `fetchCurrentUser()` или `fetchSettings()`. В отличие от `useAsyncData`, он не хранит результат и не управляет состоянием загрузки — он лишь контролирует кратность выполнения переданного кода. Также важно понимать различие между режимами `render` и `navigation`, которые определяют, будет ли код выполняться только один раз за время работы приложения или один раз при каждой клиентской навигации.

Когда стоит использовать:
- Загрузка данных в Pinia;
  `await callOnce(() => usersStore.fetch())`
- Загрузка текущего юзера;
  `await callOnce(() => authStore.loadUser())`
- Получение настроек приложения;
  `await callOnce(() => settingsStore.fetch())`
- Инициализация SDK;
  `await callOnce(() => analytics.init())`
