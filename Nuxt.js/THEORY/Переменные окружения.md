#runtimeConfig #env 

## 1. Назначение параметров конфигурации

Если отбросить все термины, `runtimeConfig` (**параметры конфигурации**) решает одну простую задачу:

==**Позволяет приложению получать настройки, которые можно изменить в зависимости от окружения, в котором приложение запущено, не меняя исходный код приложения.**==

Например, у тебя есть один и тот же Nuxt-проект.

* Локально Backend API находится здесь:

	```
	http://localhost:8000
	```

* На тестовом сервере:

	```
	https://staging-api.example.com
	```

* На production:

	```
	https://api.example.com
	```

Ты не хочешь писать в коде:

```ts
if (environment === 'production') {
  ...
}
```

и тем более не хочешь пересобирать приложение только потому, что изменился адрес API.

Вместо этого приложение получает значение конфигурации **из окружения, в котором оно запущено**.

Именно здесь появляются:

- environment variables — переменные окружения;
- `runtimeConfig` — конфигурация, доступная приложению во время выполнения;
- `NUXT_*` — специальный механизм Nuxt для переопределения `runtimeConfig` через переменные окружения.

## 2. Три понятия, которые нельзя смешивать

Это самое важное место всей темы.

### Переменная окружения

Например:

```
NUXT_PUBLIC_BASE_API=https://api.example.com
```

Это **значение, которое передаётся приложению извне**.

Переменная окружения не является частью Vue и не является особенностью `runtimeConfig`.

Это просто данные, которые операционная система или среда запуска предоставляет процессу приложения.

Условно:

```
Окружение сервера
      │
      │ NUXT_PUBLIC_BASE_API=...
      ▼
Nuxt-приложение
```

---

### `runtimeConfig`

Это **структура конфигурации приложения Nuxt**.

Например:

```json
runtimeConfig: {
  apiSecret: '',

  public: {
    baseApi: ''
  }
}
```

Она говорит:

> «У моего приложения есть такие конфигурационные параметры».

Теперь код приложения может получить их через:

```ts
const config = useRuntimeConfig()
```

и использовать:

```ts
config.apiSecret
config.public.baseApi
```

---

### `NUXT_*`

Это соглашение Nuxt, позволяющее **переопределять значения `runtimeConfig` переменными окружения**.

Например:

```json
runtimeConfig: {
  public: {
    baseApi: ''
  }
}
```

сопоставляется с:

```
NUXT_PUBLIC_BASE_API=https://api.example.com
```

И приложение получает:

```ts
config.public.baseApi
```

со значением:

```
https://api.example.com
```

Главная мысль:

> **Переменная окружения — источник значения. `runtimeConfig` — конфигурация приложения, через которую код получает это значение.**

## 3. Зачем вообще нужен `runtimeConfig`

Можно спросить:

> «Почему просто не писать везде `process.env.BASE_API`?»

Потому что `runtimeConfig` даёт Nuxt **единую систему конфигурации приложения**.

Вместо того чтобы по проекту искать:

```ts
process.env.BASE_API
process.env.API_SECRET
process.env.APP_NAME
process.env.SOME_OTHER_SETTING
```

ты работаешь через единый интерфейс:

```ts
const config = useRuntimeConfig()
```

и получаешь:

```ts
config.apiSecret
config.public.baseApi
config.public.appName
```

Кроме того, `runtimeConfig` позволяет разделить конфигурацию на:

```
private
public
```

Это особенно важно в Nuxt, потому что приложение может выполняться и на сервере, и в браузере.

## 4. Private и Public

Вот здесь нужно запомнить очень простое правило.

```json
runtimeConfig: {
  apiSecret: '',

  public: {
    baseApi: ''
  }
}
```

означает:

```
apiSecret
→ приватная конфигурация

public.baseApi
→ публичная конфигурация
```

### 🔒 Приватная конфигурация

Доступна серверному коду.

Например:

```ts
config.apiSecret
```

Она предназначена для:

- секретных ключей;
- токенов;
- паролей;
- API Secret;
- других данных, которые нельзя показывать браузеру.

### 🔓 Публичная конфигурация

Может быть доступна клиентскому JavaScript.

Например:

```ts
config.public.baseApi
```

Поэтому сюда можно помещать:

- URL публичного API;
- название приложения;
- публичные идентификаторы;
- feature flags — флаги включения/выключения функциональности, если они не являются секретом.

Но **никогда не следует помещать секрет в `public`**.

---

### ⚠️ Важное уточнение

`public` означает не:

> «это обязательно прямо видно пользователю на странице».

А:

> **«это значение разрешено передавать клиентской части приложения, поэтому оно не должно считаться секретом».**

Если значение доступно браузеру, технически пользователь может его исследовать.

Поэтому:

```
apiSecret
→ private

baseApi
→ public, если браузеру действительно нужен этот URL
```

## 5. Что видит сервер и что видит браузер

Представим:

```json
runtimeConfig: {
  apiSecret: 'secret',

  public: {
    baseApi: 'https://api.example.com'
  }
}
```

На сервере:

```ts
const config = useRuntimeConfig()
```

доступно:

```ts
config.apiSecret
config.public.baseApi
```

То есть сервер видит всю конфигурацию.

В браузере клиентская часть получает только публичную часть:

```ts
config.public.baseApi
```

Приватный:

```ts
config.apiSecret
```

клиенту не передаётся.

Поэтому концептуально:

```
SERVER
├── apiSecret       ✅
└── public.baseApi  ✅

BROWSER
└── public.baseApi  ✅
```

А:

```
BROWSER
└── apiSecret       ❌
```

## 6. Самая важная разница: `process.env` и runtime environment variables

Вот здесь была твоя главная путаница.

Рассмотрим:

```json
runtimeConfig: {
  public: {
    baseApi: process.env.BASE_API
  }
}
```

и:

```
BASE_API=https://api.example.com
```

Ты напрямую читаешь `process.env.BASE_API` во время формирования конфигурации.

Упрощённо можно представить:

```
process.env.BASE_API
         ↓
  nuxt.config.ts
        ↓
  runtimeConfig
        ↓
      build
        ↓
готовое приложение
```

Если после сборки ты изменишь:

```
BASE_API=https://new-api.example.com
```

то уже собранное приложение **не получает автоматически новое значение только потому, что ты изменил `.env` и перезапустил его**.

Чтобы новое значение попало в результат сборки, потребуется новая сборка.

То есть:

```
изменили BASE_API
        ↓
      build
        ↓
     restart
```

---

### Runtime-вариант

Теперь:

```json
runtimeConfig: {
  public: {
    baseApi: ''
  }
}
```

и:

```
NUXT_PUBLIC_BASE_API=https://api.example.com
```

Nuxt может использовать переменную окружения как runtime-переопределение.

Теперь логика:

```
один build
    │
    ├── запуск с NUXT_PUBLIC_BASE_API=api-1
    │
    ├── остановили
    │
    ├── изменили NUXT_PUBLIC_BASE_API=api-2
    │
    ├── запустили снова
    │
    └── приложение работает с api-2
```

То есть:

> **Изменили конфигурацию → перезапустили приложение. Новая сборка не нужна.**

Это и есть ключевое преимущество runtime-конфигурации.

## 7. Важное уточнение про значения по умолчанию

Ты спрашивал:

> «Зачем писать `baseApi: ''`, если есть `NUXT_PUBLIC_BASE_API`?»

И действительно, в простом случае это выглядит как дублирование.

Но значение в `runtimeConfig` — это **default**, то есть значение по умолчанию.

Например:

```json
runtimeConfig: {
  public: {
    baseApi: 'http://localhost:8000'
  }
}
```

А production запускается с:

```
NUXT_PUBLIC_BASE_API=https://api.example.com
```

Получаем:

```
LOCAL
→ http://localhost:8000

PRODUCTION
→ https://api.example.com
```

То есть можно сделать:

```
локальная разработка
→ работает сразу с default

production
→ runtime environment variable переопределяет default
```

Это нормальная практика.

Но если отсутствие production-конфигурации критично, лучше не позволять приложению молча использовать неправильный default — нужно валидировать конфигурацию.

## 8. Как выбирать `public` или private для `baseApi`

Здесь важно не запомнить:

> «URL API всегда public».

Правильное правило:

> **Если браузеру нужен URL API — он может находиться в `public`. Если API вызывается только сервером Nuxt — URL не обязательно делать public.**

### Вариант 1. Браузер вызывает API напрямую

```
Browser
   │
   │ https://api.example.com/users
   ▼
Backend API
```

Тогда:

```json
runtimeConfig: {
  public: {
    baseApi: ''
  }
}
```

### Вариант 2. Nuxt выступает посредником

```
Browser
   │
   │ /api/users
   ▼
Nuxt Server
   │
   │ https://api.example.com/users
   │ + secret
   ▼
Backend API
```

Тогда:

```json
runtimeConfig: {
  apiBase: '',
  apiSecret: ''
}
```

`apiBase` браузеру вообще не нужен.

## 9. BFF — что это такое

**BFF (Backend for Frontend)** — «бэкенд для фронтенда».

Это архитектурный подход, при котором между браузером и основным Backend API появляется специальный серверный слой, адаптированный под нужды конкретного frontend-приложения.

В твоём случае Nuxt может выполнять роль BFF:

```
                 Browser
                    │
                    │ /api/users
                    ▼
              Nuxt Server
                    │
                    │ apiSecret
                    │ apiBase
                    ▼
              Backend API
```

Зачем это нужно?

Например, чтобы:

- скрыть секреты;
- не отдавать браузеру внутренние API;
- объединить несколько backend-запросов;
- адаптировать ответ backend под нужды frontend;
- централизовать авторизацию;
- выполнять серверную бизнес-логику.

Но не нужно считать, что **любой `server/api` автоматически является полноценным BFF**. Это архитектурная роль, а не просто название папки.

## 10. 🔴 Почему секрет нельзя использовать непосредственно в браузере

Предположим:

```json
runtimeConfig: {
  apiSecret: ''
}
```

Нельзя делать:

```ts
const config = useRuntimeConfig()

fetch('https://api.example.com/users', {
  headers: {
    Authorization: `Bearer ${config.apiSecret}`
  }
})
```

если этот код выполняется в браузере.

Причина проста:

```
Browser
→ не имеет доступа к private runtimeConfig
```

Но важнее другое:

> **Секрет вообще не должен попадать в браузер.**

Если сервер передаст его клиенту каким-либо способом, секрет перестанет быть секретом.

Правильная архитектура:

```
Browser
   │
   │ /api/users
   ▼
Nuxt Server
   │
   │ config.apiSecret
   ▼
Backend API
```

## 11. SSR и CSR

Здесь тоже важно знать два термина.

**SSR (Server-Side Rendering)** — серверный рендеринг.

Страница сначала формируется на сервере, а браузер получает уже подготовленный HTML.

**CSR (Client-Side Rendering)** — клиентский рендеринг.

JavaScript в браузере сам выполняет необходимую работу и формирует интерфейс.

В Nuxt используются оба подхода.

Поэтому нужно понимать:

```
SSR
→ код выполняется на сервере
→ доступен private runtimeConfig

CSR
→ код выполняется в браузере
→ доступна только public часть
```

Это особенно важно при проектировании запросов.

## 12. `$fetch` и `useFetch`

**`$fetch`** — утилита Nuxt для выполнения HTTP-запросов.

Например:

```ts
const data = await $fetch('/api/users')
```

Она просто выполняет запрос.

**`useFetch`** — Nuxt composable, то есть специальная функция Composition API, интегрированная с механизмами Nuxt.

Например:

```ts
const { data } = await useFetch('/api/users')
```

Для получения данных страницы `useFetch` обычно удобнее, потому что Nuxt умеет интегрировать его с SSR и hydration.

**Hydration (гидратация)** — процесс, при котором клиентский Vue подключается к HTML, уже созданному сервером, и делает его интерактивным.

Упрощённо:

```
             SSR
			  ↓
    сервер получил данные
			  ↓
		 создал HTML
			  ↓
передал данные через Nuxt payload
			  ↓
     браузер получил HTML
			  ↓
   Vue гидратирует страницу
```

`useFetch` помогает Nuxt не выполнять один и тот же запрос бессмысленно дважды при первоначальной загрузке.

Но:

> `$fetch` сам по себе не «плох для SSR».

Он прекрасно может использоваться на сервере.

Разница в том, что `useFetch` имеет дополнительную интеграцию с механизмами Nuxt для получения данных страницы.

## 13. Правильная архитектура для секретного Backend API

Представим:

```json
runtimeConfig: {
  apiBase: '',
  apiSecret: ''
}
```

Server API:

```ts
export default defineEventHandler(async (event) => {
  const config = useRuntimeConfig(event)

  return await $fetch(`${config.apiBase}/users`, {
    headers: {
      Authorization: `Bearer ${config.apiSecret}`
    }
  })
})
```

Vue:

```ts
const { data } = await useFetch('/api/users')
```

Получается:

```
┌───────────────┐
│    Browser    │
└───────┬───────┘
        │
        │ /api/users
        ▼
┌───────────────┐
│  Nuxt Server  │
│               │
│ apiBase       │
│ apiSecret     │
└───────┬───────┘
        │
        │ Authorization
        ▼
┌───────────────┐
│  Backend API  │
└───────────────┘
```

Секрет:

```
Browser  ❌
Nuxt     ✅
Backend  ✅
```

Это очень важная схема, которую стоит запомнить.

## 14. Nitro — что это такое

Ты спрашивал об этом ранее, поэтому включаю в итог.

**Nitro** — серверный движок, на котором работает серверная часть Nuxt.

Упрощённо:

```
Nuxt
├── Vue
│   └── интерфейс
│
└── Nitro
    └── серверная часть
```

Nitro отвечает за такие вещи, как:

- `server/api`;
- серверные маршруты;
- серверный middleware;
- обработку HTTP-запросов;
- работу серверной части Nuxt-приложения.

Поэтому когда мы говорим:

```
Nuxt Server
```

мы фактически говорим о серверной части приложения, которая работает на основе Nitro.

## 15. Что такое production artifact

**Production artifact** — результат сборки приложения, который затем запускается в production.

Для Nuxt это, в частности, каталог:

```
.output
```

Условно:

```
   Исходный код
        ↓
   npm run build
        ↓
     .output
        ↓
запуск приложения
```

Поэтому важно понимать:

```
build-time
→ во время сборки

runtime
→ во время работы уже собранного приложения
```

Главная идея `runtimeConfig`:

> **Настройки окружения можно менять во время запуска приложения, не меняя сам собранный production artifact.**

## 16. ⚠️ Самая важная таблица

|Что|Что это|Когда используется|
|---|---|---|
|`process.env`|доступ к переменным окружения процесса|обычно при конфигурации/сборке или непосредственно на сервере|
|`runtimeConfig`|конфигурация Nuxt-приложения|во время выполнения приложения|
|`NUXT_*`|соглашение Nuxt для runtime-переопределения конфигурации|при запуске|
|`runtimeConfig.public`|публичная конфигурация|сервер + браузер|
|private `runtimeConfig`|приватная конфигурация|сервер|
|`.env`|файл, из которого могут загружаться переменные окружения|преимущественно локальная разработка; production зависит от способа запуска|
|`$fetch`|выполнение HTTP-запроса|сервер или клиент|
|`useFetch`|Nuxt composable для получения данных с интеграцией SSR|обычно данные страниц и компонентов|

## 17. Главная ловушка: `.env` ≠ runtimeConfig

Это очень важно.

Нельзя мыслить так:

```
    .env
      ↓
runtimeConfig
```

Лучше:

```
           CONFIGURATION

       runtimeConfig приложения
                 │
                 │
       получает значения
                 │
        ┌────────┴────────┐
        │                 │
     defaults        environment
                          │
                          ▼
                     NUXT_* vars
```

`.env` — это **один из способов предоставить environment variables**.

А `runtimeConfig` — **конфигурация приложения**.

## 18. 💡Что я бы ответил на Senior-собеседовании

### 💬 Вопрос:

**Что такое `runtimeConfig` в Nuxt?**

Ответ:

> `runtimeConfig` — это механизм Nuxt для хранения конфигурации приложения, которая доступна во время выполнения. Конфигурация может содержать приватные значения, доступные только серверу, и `public`-значения, которые могут быть доступны клиентскому коду. Значения runtime-конфигурации могут переопределяться переменными окружения с соглашением `NUXT_*`, что позволяет менять настройки окружения без пересборки приложения.

---

### 💬 Вопрос:

**Зачем нужен `NUXT_*`?**

> Это соглашение именования переменных окружения, с помощью которого Nuxt может сопоставить переменную окружения с соответствующим полем `runtimeConfig` и переопределить его значение при запуске приложения.

Например:

```
    NUXT_PUBLIC_BASE_API
             ↓
runtimeConfig.public.baseApi
```

---

### 💬 Вопрос:

**Чем `runtimeConfig` отличается от `process.env`?**

> `process.env` — это механизм доступа к переменным окружения процесса. `runtimeConfig` — это конфигурация самого Nuxt-приложения с разделением на private и public части. Если напрямую использовать `process.env` при формировании `nuxt.config.ts`, значение может быть зафиксировано на этапе сборки. Использование поддерживаемого Nuxt механизма `NUXT_*` позволяет переопределять runtime-конфигурацию при запуске уже собранного приложения.

---

### 💬 Вопрос:

**Почему секрет нельзя хранить в `runtimeConfig.public`?**

> Потому что `public`-конфигурация может быть передана клиентской части приложения. Любое значение, доступное браузеру, нельзя считать секретом.

---

### 💬 Вопрос:

**Как скрыть API Secret от пользователя?**

> Запрос к Backend API выполняется серверной частью Nuxt. Клиент обращается к `server/api` endpoint Nuxt, а сервер получает секрет из private `runtimeConfig` и добавляет его в запрос к Backend API.

---

### 💬 Вопрос:

**Что такое BFF?**

> BFF, Backend for Frontend, — это серверный слой, расположенный между frontend и основным Backend API и адаптированный под конкретный frontend. В Nuxt роль BFF может выполнять серверная часть приложения, например `server/api`, скрывая секреты и адаптируя запросы и ответы Backend API.

---

### 💬 Вопрос:

**Можно ли изменить переменную окружения после сборки без новой сборки?**

> Да, если приложение использует runtime-конфигурацию Nuxt и значение переопределяется поддерживаемой переменной окружения `NUXT_*`. В таком случае достаточно изменить конфигурацию окружения и перезапустить приложение. Если же значение напрямую внедряется через `process.env` при формировании конфигурации на этапе сборки, изменение переменной после сборки не даст того же runtime-поведения.

## 19. Моя короткая «карта в голове»

Если тебе нужно **за минуту восстановить всю тему**, вспоминай эту последовательность:

```
1. Мне нужна конфигурация приложения
        ↓
2. Я описываю её через runtimeConfig
        ↓
3. Секреты кладу вне public
        ↓
4. То, что можно показать браузеру, кладу в public
        ↓
5. Значения могу переопределить через NUXT_*
        ↓
6. Это позволяет менять конфигурацию при запуске
   без пересборки приложения
        ↓
7. Секретный Backend API вызываю с сервера Nuxt
        ↓
8. Браузер → Nuxt Server → Backend API
```

И самая короткая формула:

> **`runtimeConfig` — где приложение хранит свою runtime-конфигурацию.**
> 
> **`NUXT_*` — как передать или переопределить её значения из окружения при запуске.**
> 
> **`public` — то, что может попасть в браузер.**
> 
> **private — то, что остаётся на сервере.**
> 
> **Если нужен секрет — запрос выполняет Nuxt Server, а не браузер.**

## 20. Три вещи, которые я особенно хочу, чтобы ты НЕ перепутал

### ❌ Неправильно

> `runtimeConfig` — это просто способ прочитать `.env`.

### ✅ Правильно

> `runtimeConfig` — конфигурация приложения. Переменные окружения — один из способов задать её значения.

---

### ❌ Неправильно

> `public` означает «можно показать на странице».

### ✅ Правильно

> `public` означает «можно передать клиентской части». Поэтому секретом это значение быть не должно.

---

### ❌ Неправильно

> `$fetch` нельзя использовать с SSR.

### ✅ Правильно

> `$fetch` может выполняться и на сервере, и на клиенте. `useFetch` дополнительно интегрирован с Nuxt SSR и payload/hydration, поэтому часто удобнее для получения данных страницы.

## Финальная модель

Если ты на собеседовании увидишь задачу:

> «Есть Nuxt-приложение. Есть внешний Backend API. Для обращения к нему нужен секрет. URL API должен отличаться на локальном, тестовом и production окружениях. Как спроектируете?»

Твой ответ теперь должен быть примерно таким:

```
runtimeConfig
├── apiBase       private, если браузеру не нужен
├── apiSecret     private
└── public
    └── ...       только действительно публичные настройки
```

Значения передаются через:

```
NUXT_API_BASE
NUXT_API_SECRET
```

или через `NUXT_PUBLIC_*`, если значение действительно должно быть доступно браузеру.

Клиент делает:

```
useFetch('/api/users')
```

Nuxt Server делает:

```
$fetch(`${apiBase}/users`, {
  Authorization: apiSecret
})
```

И получается:

```
Browser
   │
   │ публичный запрос к Nuxt
   ▼
Nuxt / Nitro
   │
   │ private runtimeConfig
   ▼
Backend API
```

**Вот это, на мой взгляд, и есть те 25–30% информации о `runtimeConfig`, которые дадут тебе 70–80% практической пользы и позволят уверенно отвечать на большинство вопросов по этой теме на Senior-собеседовании.**
