```text
Promise

↓
fulfilled(value)

```

## `async / await`

```text
async function
→ всегда возвращает Promise
```

```text
await
→ НЕ блокирует весь JavaScript
→ приостанавливает только текущую async-функцию
→ продолжение после await идёт через microtask
```

Rejected Promise:

```text
без await
→ rejection

с await
→ в точке await воспринимается как throw
→ можно поймать try/catch
```

> [!WARNING] rejection без await:
> Отловить через try/catch нельзя, т.к. он не проникает внутрь промиса, сам [[4. Async JavaScript#6. `throw` vs `Promise.reject`|промис уже возвращен без ошибок]] и код выполняется дальше.

# Быстрое восстановление за 2–3 минуты

## 1. Что такое синхронное и асинхронное выполнение

JavaScript на main thread выполняет JS-код через один Call Stack.

```text
синхронный код
→ выполняется прямо сейчас
→ следующая строка ждёт окончания текущего кода
```

Асинхронность означает не «два JS-кода исполняются одновременно», а:

```text
JS запускает внешнюю операцию
↓
не блокирует Call Stack в ожидании
↓
выполняет другой код
↓
когда операция завершена
→ продолжение выполняется позже
```

Например:

```js
const promise = fetch('/api/users')
```

Синхронно:

```text
fetch() вызван сейчас
Promise получен сейчас
```

Но сетевой результат может появиться позже.

Важно:

```text
Promise НЕ выполняет работу "в фоне"
```

Promise — объект, представляющий результат.

Саму работу может выполнять среда:

```text
browser APIs
network
timer subsystem
I/O
```

## 2. Promise как объект состояния

```js
const promise = new Promise((resolve, reject) => {
  // ...
})
```

Состояния:

```text
pending               // запущен...
├── fulfilled(value)  // выполнен успешно
└── rejected(reason)  // завершен с ошибкой
```

После `fulfilled` / `rejected` Promise считается:

```text
settled  // завершен
```

---

## 3. Executor Promise выполняется синхронно

==Критически важно==:

```js
console.log('1')

new Promise((resolve) => {
  console.log('2')
  resolve()
  console.log('3')
})

console.log('4')
```

Вывод:

```text
1
2
3
4
```

Почему:

```text
new Promise(executor)
→ executor запускается СРАЗУ
```

Не всё внутри Promise является microtask.

Microtasks — это, например:

```js
promise.then(...)
promise.catch(...)
promise.finally(...)
```

## 4. `.then()` и Promise chaining

```js
Promise.resolve(5)
  .then((value) => {
    return value * 2
  })
  .then((value) => {
    return value + 1
  })
```

Модель:

```text
5
↓
return 10
↓
новый Promise fulfilled(10)
↓
return 11
↓
новый Promise fulfilled(11)
```

Главное:

```text
каждый .then()
→ возвращает НОВЫЙ Promise
```

Если внутри:

```js
throw new Error('boom')
```

то новый Promise становится:

```text
rejected
```

---

## 5. Ошибки в Promise chain

```js
Promise.resolve(5)
  .then(() => {
    throw new Error('boom')
  })
  .then(() => {
    // пропускается
  })
  .catch(() => {
    return 100
  })
  .then((value) => {
    console.log(value)
  })
```

Вывод:

```text
100
```

Почему:

```text
throw
→ rejected
↓
цепочка прыгает до ближайшего catch
↓
catch успешно обработал ошибку
↓
return 100
↓
цепочка снова fulfilled
```

## 6. `throw` vs `Promise.reject`

Синхронный вариант:

```js
function a() {
  throw new Error('A')
}
```

```text
throw
→ обычный try/catch
```

Promise-вариант:

```js
function b() {
  return Promise.reject(new Error('B'))
}
```

```text
b()
→ функция нормально вернула объект Promise
→ сам вызов ничего синхронно не бросил
```

Поэтому:

```js
try {
  b()
} catch (e) {
}
```

не ловит rejection.

Нужно:

```js
b().catch(...)
```

или:

```js
try {
  await b()
} catch (e) {
}
```

Ключевая модель:

```text
без await
→ rejection остаётся rejection

с await
→ rejection проявляется как throw
  в точке await
```

```js
async function run() {
  console.log('A')
```


Важно:

```text
await НЕ блокирует весь JavaScript
```

## 9. Microtasks и Tasks

### Call Stack

> **Call Stack — стек execution contexts выполняемого JavaScript-кода. Он показывает, какая функция выполняется сейчас и какие функции вызвали её. Работает по принципу LIFO.**

Важно:

```text
в Call Stack попадает НЕ каждая строка кода
```

А stack frames / execution contexts вызванных функций.

Строки выполняются внутри текущего execution context.

---

### Microtask Queue

> **Microtask Queue — очередь высокоприоритетных отложенных продолжений JS, которые выполняются после текущего синхронного кода и перед следующей task.**

Типичные источники:

```text
.then callback
.catch callback
.finally callback
queueMicrotask callback
продолжение async function после await
```

---

### Task / Macrotask Queue

> **Task Queue — очередь задач от механизмов среды, например таймеров и пользовательских событий. Следующая task выполняется только после завершения текущей работы и очистки microtask queue.**

Типичные источники:

```text
setTimeout callback
setInterval callback
DOM event callback
```

---

## 10. Что такое Event Loop

> **Event Loop — механизм среды выполнения JavaScript, который координирует Call Stack и очереди асинхронных задач. После завершения текущего JS-кода он выполняет все готовые microtasks, затем берёт следующую task, запускает её callback через Call Stack, снова очищает microtasks и повторяет цикл.**

Коротко:

```text
Event Loop
→ следит за Call Stack
→ Stack свободен
→ выполняет все microtasks
→ берёт следующую task
→ цикл повторяется
```

---

## 11. Круговорот Call Stack / Microtasks / Tasks

Очень важно:

```text
microtask или task
→ сама выполняется через Call Stack
```

Во время выполнения callback может:

```text
вызвать обычную функцию
→ новый stack frame

создать Promise reaction
→ новая microtask

вызвать queueMicrotask
→ новая microtask

вызвать setTimeout
→ новая task
```

То есть очереди постоянно пополняются.

Схема:

```text
Task
↓
Call Stack
↓
может породить:
  sync calls
  microtasks
  tasks
↓
Stack пуст
↓
очистить ВСЕ microtasks
↓
каждая microtask снова выполняется через Call Stack
↓
она тоже может создать новые microtasks/tasks
↓
microtasks пусты
↓
следующая task
```

# Главная таблица Event Loop

| Механизм | Куда относится | Когда выполняется |
|---|---|---|
| обычный вызов функции | Call Stack | сразу |
| `new Promise(executor)` | Call Stack | executor сразу |
| `.then(callback)` | Microtask | после settlement Promise и освобождения текущего stack |
| `.catch(callback)` | Microtask | аналогично |
| `.finally(callback)` | Microtask | аналогично |
| код после `await` | Microtask | когда awaited Promise settled |
| `queueMicrotask(callback)` | Microtask | после текущего sync-кода, до следующей task |
| `setTimeout(callback)` | Task/Macrotask | позже, после microtasks |
| `setInterval(callback)` | Task/Macrotask | каждая готовая итерация позже |
| DOM event callback | Task/Macrotask | когда событие произошло и очередь дошла до него |

## 12. Важное правило microtask queue

```text
Event Loop очищает ВСЮ Microtask Queue
до перехода к следующей task
```

Например:

```js
setTimeout(() => {
  console.log('T')
}, 0)

Promise.resolve().then(() => {
  console.log('M1')

  queueMicrotask(() => {
    console.log('M2')
  })
})
```

Вывод:

```text
M1
M2
T
```

Новая microtask `M2` выполняется до timer task.

## 13. Promise combinators

### `Promise.all`

```js
const [user, orders] = await Promise.all([
  fetchUser(),
  fetchOrders()
])
```

```text
все fulfilled
→ общий Promise fulfilled

хотя бы один rejected
→ общий Promise rejected
```

Fail-fast.

---

### `Promise.allSettled`

```text
ждёт settlement ВСЕХ
→ возвращает статус каждого
```

Пример:

```js
[
  { status: 'fulfilled', value: ... },
  { status: 'rejected', reason: ... }
]
```

Полезно, когда операции независимы и ошибка одной не должна скрыть результаты остальных.

---

### `Promise.race`

```text
первый SETTLED
→ определяет результат
```

То есть первый:

```text
fulfilled
ИЛИ
rejected
```

---

### `Promise.any`

```text
первый FULFILLED
→ определяет результат
```

Если все rejected:

```text
AggregateError
```

---

<details>
<summary><strong>Практический кейс: timeout через Promise.race</strong></summary>

```js
await Promise.race([
  fetchData(),
  timeoutPromise()
])
```

Логика:

```text
fetchData первым fulfilled
→ получили данные

timeoutPromise первым rejected
→ получили timeout error
```

Важно:

```text
Promise.race НЕ отменяет проигравшую операцию автоматически
```

Например, проигравший `fetch()` может продолжить выполняться, если отдельно его не отменить.

</details>

## 14. Последовательный `await` vs конкурентный запуск

Последовательно:

```js
const user = await fetchUser()
const orders = await fetchOrders()
const settings = await fetchSettings()
```

```text
request #1
↓ wait
request #2
↓ wait
request #3
```

Если запросы независимы — обычно медленнее.

Конкурентно:

```js
const [user, orders, settings] = await Promise.all([
  fetchUser(),
  fetchOrders(),
  fetchSettings()
])
```

```text
все операции стартуют почти сразу
↓
ждём всех
```

Главное правило:

```text
операции независимы
→ Promise.all

операция B зависит от результата A
→ последовательный await
```

Пример:

```js
const user = await fetchUser()

const [orders, settings] = await Promise.all([
  fetchOrders(user.id),
  fetchSettings()
])
```

## 15. `finally`

```js
try {
  await fetchData()
} catch (error) {
  // ...
} finally {
  loading.value = false
}
```

`finally` выполняется:

```text
и после success
и после error
```

Типичный use case:

```text
cleanup
loader off
resource cleanup
```

В Promise chain:

```js
Promise.resolve(10)
  .finally(() => {
    return 999
  })
  .then(console.log)
```

выведет:

```text
10
```

Обычный `return` из `finally` не подменяет исходный successful result.

Но:

```js
finally(() => {
  throw new Error(...)
})
```

может сделать цепочку rejected.

## 16. Async iteration

### Вариант 1 — последовательный

```js
for (const item of items) {
  await save(item)
}
```

Модель:

```text
save #1
↓
ждём
↓
save #2
↓
ждём
↓
save #3
```

Порядок гарантирован.

---

### Вариант 2 — `forEach(async ...)`

```js
items.forEach(async (item) => {
  await save(item)
  console.log('saved', item)
})

console.log('DONE')
```

Важно:

```text
forEach НЕ ждёт async callbacks
```

Происходит:

```text
save(1) стартовал
save(2) стартовал
save(3) стартовал
DONE
```

Операции идут конкурентно.

Порядок завершения НЕ гарантирован:

```text
DONE
saved 2
saved 1
saved 3
```

Это нормально, если `save(2)` завершился раньше остальных.

---

### Вариант 3 — конкурентно + дождаться всех

```js
await Promise.all(
  items.map(async (item) => {
    await save(item)
    console.log('saved', item)
  })
)

console.log('DONE')
```

Модель:

```text
save(1) ─────────────►
save(2) ───────►
save(3) ──────────►
```

Операции запускаются конкурентно.

Важно:

```text
порядок завершения НЕ гарантирован
```

Но:

```text
DONE
```

гарантированно будет после завершения всех.

---

## 17. Конкурентность ≠ гарантированная параллельность JS

Лучше говорить:

```text
операции запускаются конкурентно
```

а не автоматически:

```text
JS выполняет их параллельно
```

Потому что обычный JS на main thread выполняется через один Call Stack.

Однако внешние операции:

```text
network
browser APIs
I/O
```

могут выполняться независимо от Call Stack.

---

## 18. Очень важная особенность `Promise.all`

Хотя completion order операций не гарантирован:

```js
const result = await Promise.all([
  slowPromise,
  fastPromise,
  mediumPromise
])
```

массив `result` сохраняет порядок входных элементов:

```text
result[0]
→ результат slowPromise

result[1]
→ результат fastPromise

result[2]
→ результат mediumPromise
```

То есть:

```text
completion order
≠
result array order
```

# Финальная таблица Promise combinators

| Метод | Что ждёт | Когда rejected |
|---|---|---|
| `Promise.all` | все fulfilled | хотя бы один rejected |
| `Promise.allSettled` | settlement всех | не падает из-за отдельных входных rejection |
| `Promise.race` | первый settled | если первым settled был rejected |
| `Promise.any` | первый fulfilled | если все rejected |
