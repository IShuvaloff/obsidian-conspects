#DI

## 1. Суть паттерна "Инъекция зависимостей"

**Dependency Injection** (Внедрение зависимостей) — это архитектурный паттерн проектирования, цель которого — сделать код модульным, слабосвязанным (loosely coupled) и легко тестируемым.

- Что такое зависимость? Если Классу А для работы нужен Класс Б (например, сервису заказов нужен сервис отправки SMS), то Класс Б является _зависимостью_ для Класса А.
- В чем главная идея паттерна? Класс не должен сам создавать свои зависимости (через `new MyService()`). Вместо этого он должен получать инструменты для работы извне в готовом виде.
- Аналогия из жизни: Строитель и инструменты. Плохой подход: строитель приходит на объект и сам начинает ковать себе молоток из железа (класс сам создает зависимость). Хороший подход (DI): прораб приносит строителю уже готовый профессиональный молоток и выдает его в руки. Строителю плевать, где прораб взял этот молоток, его задача — просто забивать гвозди.
- Связь с принципами SOLID: DI является прямой реализацией Dependency Inversion Principle (Принцип инверсии зависимостей — буква D в [[SOLID]]). Он гласит: модули верхних уровней не должны зависеть от модулей нижних уровней; оба типа модулей должны зависеть от абстракций (интерфейсов).

## 2. Разница подходов: Процедурный (Method Injection) vs Классический DI (через Конструктор)

При проектировании логики часто возникает дилемма: не проще ли сделать статическую функцию и передавать сервис аргументом в момент вызова?

### А. Передача через метод / Статические функции (Method Injection)

```typescript
OrderProcessor.completeOrder(orderData, smsService, databaseService, paymentGateway);
```

- Плюсы: Идеально для маленьких скриптов, утилит (форматирование дат, математика) или небольших Vue-компонентов. Не плодит лишних сущностей.
- Минусы на масштабе: Приводит к «раздуванию аргументов». Если методу завтра помимо данных заказа понадобятся новые инструменты (например, кэш или сервис логирования), вам придется переписать вызов метода во всех 10-20 местах приложения, где он использовался. Это нарушает инкапсуляцию, так как вызывающий код (например, кнопка на фронтенде) обязан сам знать, настраивать и прокидывать все внутренние тяжелые сервисы бэкенда.

### Б. Классический DI через конструктор (Constructor Injection)

Инфраструктурные инструменты передаются один раз при создании экземпляра класса. Метод принимает только чистые бизнес-данные.

```typescript
class OrderProcessor {
  // Инструмент (notifier) передается ОДИН РАЗ при рождении класса
  constructor(private notifier: NotificationService) {}
  
  completeOrder(orderData) {
    // Метод принимает ТОЛЬКО бизнес-данные (orderData).
    // Ему не нужно просить инструмент отправки аргументом — он берет его из класса.
    this.notifier.send(`Заказ ${orderData.id} готов!`); 
  }
}
```

- Плюсы: Инкапсуляция скрыта. Внешний код просто вызывает `processor.completeOrder(orderData)`, не зная, какие инструменты используются под капотом. Если внутри добавятся новые сервисы (база данных, кэш), мы поменяем _только_ конструктор. Вызывающий метод код не изменится ни на одну букву.

### ⚠️Важное замечание

Когда мы говорим, что при DI метод больше _«не просит сервис аргументом»_, имеется в виду следующее:

1. Инфраструктурные сервисы (То, ЧЕМ мы делаем работу)

Это базы данных, логгеры, API-клиенты, SMS-шлюзы. Метод `completeOrder` не должен просить их в качестве аргументов. Они уже лежат внутри класса благодаря конструктору.

- ❌ Без DI: `completeOrder(orderData, smsService, databaseService)` — метод требует инструменты для работы.
- ✅ С DI: `completeOrder(orderData)` — метод использует инструменты `this.notifier`, которые тихо сидят внутри класса.

2. Бизнес-данные (То, НАД ЧЕМ мы делаем работу)

А вот `orderData` (содержимое корзины, ID заказа, email клиента) — это чистые динамические данные. Метод `completeOrder` обязан их принимать, потому что каждый раз данные новые: сейчас заказывает Иван, через минуту — Петр. Класс не может хранить их в себе статически, он должен получить их в момент вызова.

## 3. Расширение темы: Как это работает на практике (IoC-контейнеры и Синглтоны)

В реальной промышленной разработке никто не пишет `new OrderProcessor(new EmailNotification())` вручную. Эту рутину берет на себя фреймворк.

### 1. IoC-контейнер (Inversion of Control)

Это специальный встроенный «движок» фреймворка (например, в NestJS, Angular или Nuxt 4). При старте приложения этот контейнер:

1. Сканирует конструкторы всех ваших классов.
2. Видит, что классу `OrderProcessor` для работы нужен инструмент `NotificationService`.
3. Сам создает экземпляр `NotificationService`.
4. Сам «впрыскивает» (инжектирует) его в конструктор `OrderProcessor`.  
    Разработчик вообще освобождается от ручного создания объектов.

### 2. Паттерн Синглтон (Singleton) по умолчанию

IoC-контейнеры создают экземпляры сервисов ровно один раз при старте приложения (или при первом запросе). Этот единственный экземпляр затем «раздается» всем компонентам и контроллерам. Это экономит оперативную память: объекты-инструменты не плодятся в памяти при каждом клике пользователя или HTTP-запросе.

## 4. Практические примеры реализации DI

### Пример 1. Классический DI на классах и интерфейсах (Архитектурный подход)

Показывает, как легко менять логику (Email на SMS), вообще не трогая код обработчика заказов.

```typescript
// 1. Абстрактный контракт для инструмента
interface NotificationService {
  send(message: string): void;
}

// 2. Реализация №1: Через Email
class EmailNotification implements NotificationService {
  send(message: string) { console.log(`Email отправлен: ${message}`); }
}

// 3. Реализация №2: Через SMS
class SmsNotification implements NotificationService {
  send(message: string) { console.log(`SMS отправлено: ${message}`); }
}

// 4. Главный класс бизнес-логики. Он зависит только от ИНТЕРФЕЙСА.
class OrderProcessor {
  private notifier: NotificationService;

  // Внедряем инструмент через конструктор
  constructor(notifier: NotificationService) {
    this.notifier = notifier;
  }

  // Принимаем только бизнес-данные (orderData)
  completeOrder(orderData: { id: string }) {
    this.notifier.send(`Ваш заказ #${orderData.id} готов!`);
  }
}

// Мы сами управляем тем, какой инструмент "внедрить" сегодня:
const emailService = new EmailNotification();
const processor = new OrderProcessor(emailService); // Внедряем email

// Передаем в метод только чистые данные
processor.completeOrder({ id: '123' });
```

### Пример 2. Современный DI в экосистеме Nuxt 3 / Nuxt 4 (Без классов)

Авторы Nuxt ушли от классов к функциональному стилю, но сохранили DI через механизмы Плагинов и паттерн Provide / Inject. Фреймворк сам решает, какой сервис создать в зависимости от того, где запущен код (в разработке или в продакшене).

```typescript
// 1. Интерфейс и реализации инструментов (utils/notification.ts)
export interface NotificationService { send(msg: string): void }

export class DevNotificationService implements NotificationService {
  send(msg: string) { console.log(`[DEV LOG]: ${msg}`); }
}
export class ProdNotificationService implements NotificationService {
  send(msg: string) { console.log(`[PROD API]: Реальная отправка: ${msg}`); }
}

// 2. РЕГИСТРАЦИЯ ЗАВИСИМОСТИ (plugins/notification.ts)
// Nuxt выступает в роли IoC-контейнера
export default defineNuxtPlugin(() => {
  const isProd = process.env.NODE_ENV === 'production';

  // Создаем сервис ОДИН раз при старте приложения
  const notificationService = isProd 
    ? new ProdNotificationService() 
    : new DevNotificationService();

  return {
    provide: {
      notifier: notificationService // Публикуем под ключом "notifier"
    }
  };
});
```

Использование во Vue-компоненте (Внедрение/Inject):

```ts
// pages/checkout.vue
<script setup>
// Извлекаем внедренный инструмент из контекста Nuxt
const { $notifier } = useNuxtApp()

function handleOrder() {
  const orderData = { id: '777' }; // Наши бизнес-данные
  
  // Кнопка передает только данные. Инструмент отправки уже сидит внутри $notifier.
  // Код страницы одинаков и для DEV, и для PROD среды!
  $notifier.send(`Заказ ${orderData.id} оформлен!`)
}
</script>
```

## 5. Шпаргалка для собеседования

### 💬 Что такое Dependency Injection (Внедрение зависимостей)?

> Ответ: Это паттерн проектирования и архитектурный подход, при котором класс или функция не создают свои инфраструктурные зависимости (сервисы, базы данных) самостоятельно, а получают их извне в готовом виде (обычно через конструктор или систему плагинов фреймворка). Это делает код слабосвязанным и гибким.

### 💬 Какую главную проблему решает DI?

> Ответ: Он решает проблему жесткой связанности кода (tight coupling) и упрощает тестирование. Без DI, если класс `A` внутри себя вызывает `new B()`, вы не сможете протестировать класс `A` изолированно от класса `B` (например, подменить реальную базу данных или платежный шлюз на фейковый «мок» в тестах). DI позволяет легко подсовывать любые реализации, соответствующие общему интерфейсу.

### 💬 В чем разница между DI и IoC (Inversion of Control)?

> Ответ: IoC (Инверсия управления) — это глобальный архитектурный принцип, когда управление потоком программы передается фреймворку (не ваш код вызывает функции фреймворка, а фреймворк вызывает ваш код). А DI (Внедрение зависимостей) — это конкретный паттерн, один из способов реализации принципа IoC, отвечающий именно за создание и доставку объектов-инструментов в нужные места.

### 💬 Зачем использовать DI через конструктор, если можно передавать сервисы аргументами в статические методы?

> Ответ: Передача инструментов через методы (Method Injection) хороша только на малых масштабах. При усложнении логики это приводит к лавинообразному раздуванию аргументов функции (ей нужно будет передавать БД, логгер, кэш, платежный шлюз при каждом вызове). DI через конструктор разделяет ответственность: мы настраиваем инструменты один раз при инициализации объекта, а внешние методы остаются чистыми и принимают только бизнес-данные (айдишники, массивы, объекты данных).
