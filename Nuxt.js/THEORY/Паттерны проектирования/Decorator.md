#decorator 

## 1. Суть паттерна «Декоратор»

**Декоратор** (Decorator) — это структурный паттерн проектирования, который позволяет динамически добавлять объектам или функциям новые обязанности, не меняя их исходный код и структуру.

- Аналогия из жизни: Умная насадка на кнопку дверного звонка. Сама кнопка умеет только звенеть. Насадка перехватывает нажатие, отправляет уведомление на телефон хозяина, а затем сама жмет на физическую кнопку.
- Связь с принципами [[SOLID]]: Паттерн является идеальным воплощением **Open-Closed Principle** (Принцип открытости/закрытости): код класса или функции открыт для расширения (мы можем накинуть сколько угодно декораторов), но закрыт для модификации (исходный код функции не меняется).

## 2. Две ипостаси декораторов в экосистеме JS/TS

Исторически и технически в веб-разработке под словом «декоратор» понимают две разные вещи.

## А. Функциональный декоратор (на чистых замыканиях)

Это классический подход, существующий в JavaScript с момента его создания. Декоратор представляет собой функцию высшего порядка (HOF), которая принимает оригинальную функцию как параметр, оборачивает её в свою логику и возвращает новую, модифицированную функцию.

- Параметры: Обычно принимает один параметр — саму `originalFn`.
- Где используется: Везде, где код пишется в функциональном стиле: Nuxt 3/4, React (HOC), утилиты (`lodash/debounce`), чистый JS.

## Б. Синтаксический декоратор классов (через символ `@`)

Это официальная синтаксическая фича языка (спецификация ECMAScript / возможности TypeScript). Декоратор применяется к классам, их методам, свойствам или параметрам.

- Параметры: Движок JS/TS насильно передает 3 параметра при применении к методу:
    
    1. `target`: Сам класс (прототип), где объявлен метод.
    2. `propertyKey`: Имя метода в виде строки (например, `"getProfile"`).
    3. `descriptor`: Системный объект настроек свойства. Внутри `descriptor.value` как раз и «сидит» оригинальная функция. Изменяя этот дескриптор, мы официально перепрошиваем метод.
    
- Где используется: Enterprise-фреймворки с классовой архитектурой (Nest.js, Angular).

## 3. Расширение темы: Фабрики, Метаданные и Цепочки

Для полного понимания декораторов на продвинутом уровне необходимо знать три концепта:

### 1. Фабрика декораторов (Декораторы с параметрами)

Если декоратор должен принимать аргументы (например, `@Roles('admin')` или `@HttpCode(201)`), обычная функция не подойдет. Используется Фабрика — функция, которая сначала принимает ваши аргументы, а возвращает _настоящий_ декоратор.

### 2. Цепочки декораторов (Принцип матрешки)

Когда на один метод вешается несколько `@`-декораторов, они работают по принципу луковицы:

```typescript
@Delete('/:id') // Вызовется ПЕРВЫМ (внешний слой)
@Roles('admin') // Вызовется ВТОРЫМ (внутренний слой)
remove() { ... } // Сам метод (ядро)
```

Они последовательно наслаиваются друг на друга на этапе инициализации приложения, оборачивая одну и ту же функцию.

### 3. Метаданные (Reflect Metadata) — Главная сила в TS

В TypeScript декораторы могут не просто менять поведение, но и навешивать на классы «скрытые ярлыки» (метаданные). Библиотека `reflect-metadata` позволяет в момент компиляции считать типы TypeScript (например, что аргумент должен быть `string`) и сохранить их в рантайме. На этом построена автоматическая генерация документации API (Swagger/OpenAPI): генератор просто сканирует файлы, считывает декораторы вроде `@Roles('admin')` и сам строит карту безопасности в документации. Обычный хелпер внутри метода так сделать не может, так как генератор не умеет читать исполняемый код функции.

## 4. Связь с темой Замыканий (Коротко)

Любой декоратор — как функциональный, так и синтаксический (`@`) — целиком и полностью базируется на замыканиях.  
Когда декоратор оборачивает оригинальную функцию, создается новая область видимости. Оригинальная функция, а также любые конфигурационные параметры (например, `'admin'` или `timeoutId` для `debounce`) бережно складываются в «невидимый рюкзак» (замыкание) новой функции. Они остаются доступны там вечно, даже если родительская функция-декоратор уже отработала.

## 5. Полный банк практических примеров

### Примеры функциональных декораторов (Чистый JS / Замыкания)

#### Пример 1: Защита от спама кликов (`Debounce`)

Используется на фронтенде для ограничения частоты вызовов тяжелых функций (например, при вводе в поиск).

```javascript
function debounce(originalFunc, delay) {
  let timeoutId; // Хранится в замыкании

  return function (...args) {
    clearTimeout(timeoutId); // Сбрасываем прошлый таймер

    timeoutId = setTimeout(() => {
      originalFunc.apply(this, args); // Запускаем оригинал при наступлении тишины
    }, delay);
  };
}

// Использование
const smartSend = debounce(() => console.log('Запрос ушел!'), 500);
smartSend(); smartSend(); smartSend(); // Сработает только последний вызов через 500мс
```

#### Пример 2: Проверка прав доступа без классов

```javascript
const globalUser = { role: 'editor' };

function requireAdmin(originalFunc) {
  return function (...args) {
    if (globalUser.role !== 'admin') {
      console.error('Ошибка 403: Нет прав!');
      return; // Прерываем выполнение, оригинал не вызовется
    }
    return originalFunc.apply(this, args);
  };
}

// Использование
const deleteArticle = (id) => console.log(`Статья ${id} удалена`);
const safeDelete = requireAdmin(deleteArticle);
safeDelete(105); // Ошибка 403: Нет прав!
```

### Примеры синтаксических декораторов (TypeScript / Классы)

#### Пример 3: Логирование метода класса (Без параметров)

```typescript
function LogRoute(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value; // Сохраняем оригинал

  // Перепрошиваем дескриптор своей функцией
  descriptor.value = function (...args: any[]) {
    console.log(`--> Вызван метод: ${propertyKey}`); // Наше действие
    return originalMethod.apply(this, args); // Запуск оригинала
  };
}

class UserController {
  @LogRoute
  getProfile(userId: string) {
    return { id: userId, name: 'Alex' };
  }
}
```

#### Пример 4: Проверка ролей (Фабрика декораторов с параметрами)

```typescript
// Фабрика принимает параметр 'admin'
function Roles(allowedRole: string) {
  // Возвращает сам декоратор, который замыкает в себе allowedRole
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const originalMethod = descriptor.value;

    descriptor.value = function (...args: any[]) {
      const currentUser = { role: 'guest' }; // Имитация сессии

      if (currentUser.role !== allowedRole) {
        throw new Error(`Доступ запрещен. Требуется: ${allowedRole}`);
      }
      return originalMethod.apply(this, args);
    };
  };
}

class AdminController {
  @Roles('admin') // Применение фабрики
  dangerZone() {
    return 'Секретные данные';
  }
}
```

## 6. Шпаргалка для собеседования

### 💬 Что такое паттерн «Декоратор»?

> Ответ: Это структурный паттерн проектирования, который позволяет динамически расширять логику функции или класса, не изменяя их исходный код. Он реализует принцип Open-Closed из SOLID.

### 💬 В чем разница между обычным вызовом функции-хелпера внутри метода и декоратором?

> Ответ: Есть три ключевых отличия:
> 
> 1. Инверсия управления (AOP): Декоратор изолирует вызываемый метод от сквозной логики (валидация, логи, безопасность). Метод становится «слепым» и занимается только своей бизнес-логикой.
> 2. Управление потоком: Декоратор перехватывает вызов _до_ выполнения метода и может полностью отменить его запуск снаружи, не заходя в тело функции.
> 3. Метаданные: Декораторы классов могут навешивать метаданные (`reflect-metadata`), по которым сторонние инструменты (например, Swagger) могут автоматически строить документацию API. Обычный хелпер внутри кода функции для таких парсеров невидим.

### 💬 Как декораторы связаны с замыканиями?

> Ответ: Прямо пропорционально. Под капотом любого декоратора (и функционального, и синтаксического через `@`) лежит механизм замыкания. Декоратор создает функцию-обертку, которая «в рюкзаке» своей области видимости сохраняет ссылку на оригинальную функцию и конфигурационные параметры, делая их доступными при каждом вызове.

### 💬 Зачем нужна «Фабрика декораторов»?

> Ответ: Обычный синтаксический декоратор принимает строго три системных параметра от движка JS (`target`, `key`, `descriptor`). Если нам нужно передать в декоратор свои кастомные настройки (например, `@Roles('admin')`), мы создаем функцию-фабрику. Она принимает наши параметры, а возвращает функцию декоратора, которая за счет замыкания помнит эти параметры.
